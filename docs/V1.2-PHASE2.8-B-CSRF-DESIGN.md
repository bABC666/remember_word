# 拾词 V1.2 · Phase 2.8-B · CSRF 同源校验设计与实现

> 阶段：Phase 2.8 Batch 2A（**S-2 实现**）
> 基线：分支 `feat/v1.2-phase1-safe`，起点 HEAD `1d5f9f9`（Batch 1 完成 F-1 / F-7）
> 目标：为写请求建立**同源校验**这一层纵深防御，使 CSRF 不再只依赖 `SameSite=Lax`
> 证据口径：**[源码]** = 代码位置；**[实测]** = 本机可复现的观察；**[推断]** = 由源码/实测推导
> 上游依据：`docs/PROJECT_ROADMAP.md` §4.1 S-2、§6.1 T4；`docs/PROJECT_HANDOFF.md` §9.1

---

## 0. 结论摘要

1. **采用方案 A：写请求 Origin/Referer 同源校验**，不引入 CSRF Token、不新增数据库字段、不做 migration。
2. **保护范围**：所有非安全方法（`POST`/`PUT`/`PATCH`/`DELETE`，共 **30 个端点**）；`GET`/`HEAD`/`OPTIONS` 一律放行。
3. **判定规则**：`Origin`（缺失时回落 `Referer`）的 **host:port** 必须等于请求 `Host` 的 host:port；缺失两个头默认 **403**，仅当 `VOCAB_CSRF_ALLOW_MISSING_ORIGIN=true` 时放行；字面量 `null` 永不接受。
4. **不比较 scheme**：Caddy 终止 TLS 后浏览器说 https、FastAPI 看到 http，比较 scheme 会造成必然误报。
5. **不豁免 `POST /api/auth/login` 与 `/api/auth/logout`**：登录 CSRF 会把受害者登入攻击者账号，强制登出是骚扰型 DoS。
6. **中间件在认证之前拒绝**：被拒绝的写请求不会解析会话、不会写 `last_seen_at`、不会写任何审计行（有测试断言）。
7. **零前端改动**：浏览器对非安全方法**总是**附带 `Origin`（含同源请求），现有 `api.ts` 无需修改。

## 1. 为什么是"三层防御"，而不是单层

本项目的写请求今天受到三层互相独立的保护，本阶段补齐的是第三层。

| 层 | 机制 | 能挡住什么 | 挡不住什么 |
|---|---|---|---|
| 1 | 会话 Cookie 的 `SameSite=Lax` | 跨站请求**不携带** Cookie（跨站表单、跨站 fetch、`<img>`/`<iframe>` 子资源） | **同站不同源**（`other.example.com` → `vocab.example.com`，SameSite 按可注册域判定，Cookie 照发）；**Chromium 的 "Lax+POST" 2 分钟窗口**；未来把 `SameSite` 放宽；不支持 SameSite 的旧浏览器 |
| 2 | 请求体只接受 `application/json`（FastAPI `strict_content_type` 默认）**[实测]**：`routing.py:428-450` 仅在 `Content-Type` 为 `application/json` 或 `*+json` 时解析 body，其余走原始字节分支 → Pydantic 校验失败 → 422 | 跨站 HTML 表单**造不出合法写请求**（表单只能发 urlencoded / multipart / text-plain） | 两处 **multipart** 端点（`POST /api/imports`、`POST /api/imports/{batch_id}/images`）；未来任何接受表单体的端点 |
| 3 | **本阶段的 Origin/Referer 同源校验** | 以上全部；且不依赖内容类型、不依赖浏览器对 SameSite 的实现细节 | XSS（同源脚本可伪造请求头） |

这三层的独立性是关键：第 2 层是既有实现的**隐式**性质，任何人加一个 `Form(...)` 就会静默消失；第 1 层依赖浏览器行为与站点边界。第 3 层把"请求来自哪里"变成**服务端可判定**的事实，并把上面所有"挡不住"的栏位一次性覆盖。

## 2. 攻击面（实测口径）

| 向量 | Cookie 是否随请求发出 | 结果 |
|---|---|---|
| 跨站 `<form method=POST>` | ❌ | 401（第 1 层）；即便带上 Cookie，非 JSON 端点也会 422（第 2 层） |
| 跨站 `fetch()` | ❌ | 401；`application/json` 会触发预检，**无 CORS → 预检被浏览器拒绝** |
| `<img>` / `<script>` / `<link>` | ❌ | 只能发 GET，且不携带 Cookie |
| `<iframe>` | ❌ | 同上 |
| 跨站顶级导航 GET | ✅ | 仅能触发 GET 副作用：`touch_session`（自己的 `last_seen_at`）与 `ensure_user_settings`（首次访问建自己的设置行）——自作用域、幂等 |
| **Chromium "Lax+POST"**（Cookie 设置后 2 分钟内，跨站顶级 POST 携带 Lax Cookie） | ✅ | 第 3 层拦为 403；若没有第 3 层，两个 multipart 端点在此窗口内**可被真实执行** |
| **同站不同源**（子域） | ✅ | 第 3 层拦为 403；这是 SameSite 在原理上无法覆盖的一类 |

**危害排序**（"若 Cookie 被带上"）：`POST /api/users`、`PATCH /api/users/{id}`（管理员、**无口令** → 持久后门/接管）> `PUT /api/settings`（管理员可改 `deepseek_base_url` → **Key 外泄**）> `POST /api/imports/{id}/confirm`（违反"未确认内容不进词库"）> AI/OCR 端点（**花钱**）> 复习端点（污染 append-only 的 `review_event`）> 登出（骚扰）。

## 3. 方案取舍

| 维度 | **A：Origin/Referer 校验（采用）** | B：CSRF Token | C：混合 |
|---|---|---|---|
| 安全性 | 覆盖跨源与同站不同源；不依赖内容类型与浏览器启发式 | 理论最强（SameSite 放宽也不怕） | 最高 |
| 实现复杂度 | **低**：1 个纯函数模块 + 1 个中间件 + 2 个配置项 | 中高：令牌签发/轮换/失效；若绑定会话则需 **migration 0008**（触碰 §7.1 四闸门） | 高 |
| 对 React+FastAPI 影响 | **零前端改动**（浏览器自动带 `Origin`）；无 CORS 交互 | 需改前端请求层；引入令牌过期这类新失败模式 | 前端与后端都要动 |
| 测试成本 | 中：新增 45 项；既有套件用 conftest 单点注入 `Origin` | 高 | 最高 |
| 结论 | **采用**：与"同源 SPA + 无 CORS + 单一部署"的形态精确对齐 | 不采用 | 不采用 |

**为什么 token 不适合当前形态**：本应用由 FastAPI 直接托管 `frontend/dist`，前后端同源；token 的收益（无需可信来源头）在"同源 + 无 CORS"下是零，成本却是一个必须跨登录/登出/改密保持一致的服务端秘密，且若落在会话行上就要 migration。

## 4. 判定规则（`backend/app/csrf.py`）

```
1. method ∈ {GET, HEAD, OPTIONS}            → 放行（安全方法）
2. origin = Origin（非空）否则 Referer（非空）
3. origin 为空                              → 仅当 VOCAB_CSRF_ALLOW_MISSING_ORIGIN=true 才放行，否则 403
4. origin 字面量为 "null"                    → 403（即使上一开关为 true）
5. authority(origin) == authority(Host, 请求 scheme)  → 放行
6. authority(origin) ∈ VOCAB_CSRF_TRUSTED_ORIGINS    → 放行
7. 否则                                     → 403
```

实现要点（均为纯函数，无数据库、无网络、无模块状态）：

- `authority_of(url)`：取 `(host, port)`，host 小写，缺端口时按 `http→80`、`https→443` 归一；URL 不可解析时返回 `None`（一律视为不可信）。
- `request_authority(host_header, scheme)`：`Host` 头为空、含空白/`/`/`@`/`\` 时返回 `None`（浏览器不会产生这种头，宽容解析是头混淆的起点）。
- `request_origin(origin, referer)`：空头视为"缺失"；`Referer` 只在 `Origin` 缺失时使用（因此 `Referrer-Policy: no-referrer` 不影响本校验）。
- 端口必须比较，scheme 不比较。**唯一的部署耦合**：当 `Host` 是裸域名且请求 scheme 为 http 时，https 的 `Origin` 隐含 443 而请求隐含 80 → 403。这是**响亮且可修**的失败，且代理部署本就要求 `uvicorn --proxy-headers`（见 §6）。

## 5. 中间件

`backend/app/main.py::_same_origin_write_check`，注册在既有 `_no_store_auth_responses` 之后（因此是最外层）：

- **在认证之前拒绝**：不解析会话、不写 `last_seen_at`、不写审计。
- **GET/静态资源/SPA 兜底不受影响**（全部是 GET）；`/docs` 的 "Try it out" 是同源，照常可用。
- **`POST /api/auth/login` 同样受检**（该请求本身没有 Cookie 可被别的东西保护）。
- 403 响应体为固定文案 `请求来源不可信，已拒绝`，**不回显、不记录**调用方提供的值（含 Origin），并带 `Cache-Control: no-store`。

## 6. 环境变量（`.env.example` 已记录）

| 变量 | 默认 | 用途 |
|---|---|---|
| `VOCAB_CSRF_ALLOW_MISSING_ORIGIN` | `false` | 允许既无 `Origin` 又无 `Referer` 的写请求（脚本客户端逃生口）。**一旦开启，所有客户端同时失去这层防护**，仅在对端确实无法设置请求头时使用 |
| `VOCAB_CSRF_TRUSTED_ORIGINS` | 空 | 额外可信来源（逗号分隔）。仅用于"请求 Host 与浏览器地址栏来源不一致"：代理改写 Host、或第二入口（域名 + 局域网 IP） |

**部署要求（Phase 4 必须在部署脚本中固化）**：`uvicorn --proxy-headers --forwarded-allow-ips <代理地址>`。否则 TLS 终止后请求 scheme 仍是 http，裸域名 `Host` 会被解释为 80 端口，导致 https 来源的写请求被 403。这条要求与 S-4（反向代理后 IP 判定）本就同源，属同一处配置。

## 7. 测试

- `backend/tests/test_csrf.py`（**45 项**）：判定表（安全方法、端口、scheme、裸 Host + https、Referer 兜底与跨源、缺失、`null`、可信来源、畸形 URL/Host、大小写与 IPv6）+ 应用级接线（同源放行；跨源 403 且**会话、审计、数据零变化**；不豁免 login/logout；两个 multipart 端点受检且同源对照成功；管理员建号被拦；两个配置开关生效；403 不刷新会话行）。
- `backend/tests/conftest.py`：以 session 级 autouse fixture 给**所有 `TestClient`** 注入 `Origin: http://testserver`（httpx 会把客户端级头并入每个请求）。**这不是绕过**：校验逻辑照常执行，测试跑在"校验开启"的真实路径上；需要不同来源的测试逐请求覆盖该头（`test_csrf.py` 即如此），`Origin: ""` 表示"无来源"。

## 8. 边界与明确不做的事

- **不防 XSS**：同源脚本可同时伪造请求与请求头。当前前端无 `dangerouslySetInnerHTML`/`innerHTML`（[源码] grep），但这不是本机制的功劳，写在这里是为了避免"上了 CSRF 就安全"的错觉。
- **不替代 S-1**：`POST /api/users` 与 `PATCH /api/users/{id}` 仍是"高影响 + 仅凭会话"。本阶段关闭的是**跨站**这条路径，纵深仍需管理员二次认证（下一阶段）。
  > **2026-09-23 补注（不改写上文，本文件其余内容保持冻结）**：S-1 **已实现并验收**——提交 `c3a6106`，设计见 `docs/V1.2-PHASE2.8-A-ADMIN-REAUTH-DESIGN.md`。两个管理员端点现在**每次调用**都要求管理员输入自己的当前口令。本条只作历史边界记录，接手者不必再实现一次。
- **不引入 token / 不改 schema / 不改认证模型**（本任务明令禁止）。
- **GET 并非绝对无副作用**：`touch_session` 与 `ensure_user_settings` 会写库，但都是自作用域且幂等，因此"GET 一律放行"成立；这条写进文档是为了防止未来有人据此把有破坏性的操作塞进 GET。
