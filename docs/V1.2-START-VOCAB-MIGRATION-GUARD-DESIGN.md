**部署一个含新 migration 的版本后发生什么**：双击启动 → `upgrade head` **隐式应用新 migration** → 拉起 uvicorn。**四闸门一个都没有**：没有 rehearsal、没有备份、没有显式 revision、没有迁移后核验。而且因为应用自己的启动校验是"代码 head == 数据库 revision"，迁移完成后**恰好通过**——没有任何地方会提示"刚刚发生了一次迁移"。

**更尖的一点（实测）**：SQLite 上 Alembic 输出 `Will assume non-transactional DDL`。若新 migration 的多条 DDL 在中途失败，会留下**部分建表 + revision 未推进**的状态；下次启动重试即 `table already exists`，应用起不来，而此时**没有迁移前备份**可退。这正是一个"重试反而更糟"的状态。

## 2. 方案对比与取舍

| 方案 | 优点 | 不足 | 裁定 |
|---|---|---|---|
| A 保持现状 + 文档提醒 | 零改动 | 纯程序性，依赖每个操作者记得读 runbook；本项目已有因隐式迁移造成的永久数据丢失前科 | 不选 |
| B 启动器完全不迁移 | 最安全 | **全新安装无法启动**（数据库不存在时 schema 永远不会被创建） | 不选 |
| **C 按数据库状态分流** | 正常路径**零变化**；只有"真实数据将被隐式修改"这一状态被拒；全新安装仍可用 | 需要一个可独立测试的判定单元 | **采用** |

### 2.1 状态机

判定逻辑在 `backend/app/db.py::migration_state()`（只读报告）与 `schema_action()`（决策），由 `python -m app.cli migration-status` 暴露为 JSON，PowerShell 侧 `scripts/prepare-database.ps1` 只负责"按结论做事 + 打印指引"。

| 数据库状态 | 动作 | 理由 |
|---|---|---|
| 文件不存在 | `initialise` → 建目录并 `upgrade head` | 全新安装，没有内容可失去，且没有 schema 服务器根本起不来 |
| 文件存在但**零张表** | `initialise` | 空文件等价于全新安装 |
| revision **等于**代码 head | `current` → **完全不碰 schema**，连 alembic 都不调用 | 正常路径，行为与"本来就没事"一致 |
| revision **落后** head 且**有数据行** | `refuse` | ← **本设计的核心**：有人真实数据即将被一个没有预演、没有备份、没有人看着的步骤改变 |
| revision **落后** head 但**无数据行** | `initialise` | 没有内容可失去 |
| revision 不是 head 的**祖先**（数据库更新、或不属于这条链） | `refuse` | `upgrade head` 帮不上忙，猜测是错的 |
| 有表但**没有 `alembic_version`** | `refuse` | 无法判断它处于哪个 revision；**不知道不等于许可** |
| `alembic_version` 行数 ≠ 1 或为空 | `refuse` | 版本表损坏，状态不可知 |
| 代码 head 无法确定（多个 head 等） | `refuse` | 同上 |

**"有数据"的定义**：除 `alembic_version` 之外任意用户表的总行数 > 0。只按 `count(*)` 判定，不做内容判断。

### 2.2 为什么不给启动器加"逃逸参数"

一个 `-AllowMigration` / `-MigrationRevision` 开关会把"拒绝"变回"只要记得加参数就行"，而那正是现状的问题。发布窗口需要显式迁移时，操作者按 runbook 在命令行用**显式 revision** 迁移；完成后启动器看到 `current`，直接放行。启动器永远不是执行迁移的那一方。**这是刻意的**，也是"拒绝自动 upgrade head"与"给出显式迁移指引"两件事的分工。

## 3. 失败模式与**挡不住什么**

**挡得住**：有数据的落后数据库被隐式迁移；未知/损坏/超前状态被"猜着迁"；半迁移状态被重试放大；把 `upgrade head` 打真实库这条路径从**程序性缓解**变成**机械上不可能**。

**挡不住**：

- **绕过启动器**：操作者仍可直接运行 `alembic upgrade head`。这不是本设计的目标（那需要改 Alembic 本身），但启动器不再替他做这件事。
- **`.env` 里的 `VOCAB_DATABASE_PATH`**：启动器沿用**原有**的解析方式（进程环境 → `VOCAB_DATA_DIR`/`VOCAB_DATABASE_PATH` → 默认 `data/vocab.db`），未新增偏差，也未修正 uvicorn `--env-file` 与启动器进程环境之间**既有**的可能不一致。**本次不扩大范围**；见 §6。
- **迁移本身的正确性**：本守卫只决定"要不要现在动手"，不评价 migration 内容。
- **并发**：判定与迁移之间若另一个进程改了数据库，守卫不会察觉（SQLite 单写者、单实例部署下不可达）。

## 4. 测试策略

`backend/tests/test_start_vocab_migration_guard.py`，**22 项**，用真实 PowerShell 子进程 + **pytest 临时目录里的真实迁移数据库**（不是手写 schema 近似）。覆盖用户要求的三类场景与边界：

| 场景 | 测试 |
|---|---|
| **正常启动** | `…at_the_code_head_starts_without_touching_the_schema`：exit 0，且**文件逐字节未变**（连 alembic 都没跑） |
| **落后 revision** | `…behind_the_code_with_rows_is_refused`：exit 3、不迁移、文件逐字节未变；`…names_both_revisions_and_the_likely_cost`：输出含两个 revision、行数与指引 |
| **迁移失败后再次启动** | `…restart_after_a_failed_migration_does_not_retry`：构造"新表已建、revision 未推进"的半迁移态，要求 exit 3 且**残留物原样保留** |
| 边界（集成） | 未知版本表被拒而非猜测；**有表但没有 `alembic_version` 表**被拒；全新库（含**目录不存在**）被初始化；空文件被初始化；`migration-status` 只读且三态正确 |
| 决策函数逐条 | `test_schema_action_decides_each_state_for_its_own_reason`（8 组参数）把**每条规则绑到它存在的那个状态**，并断言**原因文本**——因为原因文本正是告诉操作者"哪条规则生效了"的东西 |
| 启动器本身 | 启动器的**可执行行**不含 `alembic`（注释可以解释为什么不做）；守卫是全仓唯一执行迁移的地方；两个运维脚本保持 ASCII |

### 4.1 一个测试设计上的教训

集成测试断言的是**结果**，而本设计里若干输入的结果是**刻意过度决定**的：一个损坏的版本表会被**三条独立规则**分别拒绝（`problem` 规则、"没有 revision 记录"规则、"不是 head 祖先"规则）。这意味着**破坏其中一条规则，操作者看到的结果不变**——变异验证因此无法定位回归，测试也失去了分辨力。

处理办法不是删掉多余规则（纵深防御是刻意的），而是**在决策函数层逐条 pin 住每条规则及其原因文本**。加上这一层之后，原来两个"变异无法证明"的守卫都变成可证明的。

**变异验证**（本轮实测，5/5 全部证明）：分别破坏——①"有数据也允许迁移"②"`problem` 规则失效"③"没有 revision 记录也允许迁移"④"把 `migration-status` 放回 schema 闸门之后"⑤"启动器重新加上 `upgrade head`"——**每项都让对应测试失败**，恢复实现后全部通过。**未证明 0 项。**

**一个真实的坑（值得记下）**：`prepare-database.ps1` 最初用中文输出，而 Windows PowerShell 把**无 BOM** 的脚本按 ANSI 读取，多字节序列被拆成了引号，直接导致 `Missing closing '}'` 解析错误（不是显示乱码，是**解析失败**）。仓库现有的运维脚本（`stop-vocab.ps1` 全文、`start-vocab.ps1` 其余部分）都是纯 ASCII 英文，中文消息一律在 Python CLI 侧。已按此约定重写，并加了一条测试固定它。

## 5. 回滚 / 逃生口

- **代码回滚**：把 `start-vocab.ps1` 恢复成直接 `upgrade head` 即可；`prepare-database.ps1` 与 `app/db.py` 的新增函数都是纯增量，留着也不影响启动。

- **不提供**"忽略守卫继续启动"的开关（§2.2）。
- **数据面逃生口**：本守卫从不修改数据库（只有 `initialise` 那一条路径会，且仅当没有数据行），所以它本身不需要数据回滚。
