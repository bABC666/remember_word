## 1. 当前能力分析（实测）

### 1.1 `user_session` 表结构（[源码 `models.py:366-390`]）

| 列 | 类型/约束 | 会话管理用途 |
|---|---|---|
| `id` | PK | 唯一可暴露的标识（见 §4.1） |
| `user_id` | FK→`user.id` CASCADE，**已索引** | 按用户列出（索引就绪） |
| `token_hash` | String(64) UNIQUE，已索引 | **不得对外暴露**（见 §4.1/§4.2） |
| `created_at` | NOT NULL | "登录时间" |
| `expires_at` | NOT NULL，**已索引** | 绝对过期（签发时固定、**永不续期**） |
| `last_seen_at` | 可空 | "最近活动"（写入被节流，见 §1.3） |
| `revoked_at` | 可空，**已索引** | 撤销标记（`prune` 依此清理） |
| `user_agent` | String(300)，默认 '' | **唯一可用于"区分设备"的线索** |

**没有**任何客户端地址列（全仓库 grep `remote_addr|client_host|client_ip|ip_address|x_forwarded` = 0 命中，Phase 2.5 已确认这是**有意的现状**），也**没有**设备名/设备标签、没有撤销原因列。

### 1.2 逐问回答（四个能力）

| 问题 | 结论 | 证据 |
|---|---|---|
| **查询当前用户的 session？** | ❌ **完全没有**。`api/` 下**没有任何路由引用 `UserSession`**（grep 0 命中）；只有服务层能取到行（`revoke_all_sessions`、`find_session_record`）。数据在库里、可查，但没有读模型与接口 | [实测 c] [源码 grep] |
| **区分设备？** | ⚠️ **只能近似**。仅有 `user_agent` 与时间戳。实测：同一用户 5 次登录（5 种 UA，其中 2 次相同）→ **4 个不同 UA / 5 条会话**，两条同 UA 的会话（id 1 与 4）在数据上**完全无法区分** | [实测 2、3] |
| **主动撤销？** | ⚠️ **仅"自己的当前会话"**：`POST /api/auth/logout`（Phase 2.4-b 起幂等、匿名安全）。不存在"按会话撤销某一个设备"的接口 | [实测 a、b、d] |
| **批量撤销？** | ⚠️ **服务层有、接口层没有**：`revoke_all_sessions(user)`（`services/auth.py:273`）被"改密码 / 管理员停用 / 管理员改角色"触发，且**连当前会话一起撤销**（Phase 2.3 已记录为 I1）。没有"退出其他设备"这种"保留当前"的能力，也没有对应用户入口 | [源码 `api/auth.py:270,352,355`] |

### 1.3 生命周期与既有机制（设计时必须沿用）

```
登录 → create_session（签发 expires_at = now + VOCAB_SESSION_DAYS，last_seen_at = NULL）
请求 → resolve_session（撤销/绝对过期/闲置 三者任一即 401）→ touch_session（写 last_seen_at，节流 5 分钟）
登出 → revoke_session（幂等，保留首次 revoked_at）+ 删除 Cookie
启动/CLI → prune_sessions（删除"永不可再用"的行：已撤销/已过期/已闲置）
```

- **实测 6**：`last_seen_at` 在首个请求被写入，紧随其后的第二个请求**不再更新**（节流生效）。
- **实测 7**：因此"最近活动"的**最坏陈旧度为 5 分钟**（`TOUCH_INTERVAL`）——UI 文案不得宣称秒级精度。
- **实测 10**：`expires_at` 是绝对上限且从不续期，所以"本次登录将在 X 天后失效"是可准确展示的。
- **实测 5**：明文 token 只在 HttpOnly Cookie 中；库里只有 `sha256`。

### 1.4 无上限（实测 1）

同一用户 5 次登录 → **5 条同时存活的会话**，无任何上限；Phase 2.3 的探针（`D3b`）在同一用户上曾一次性观察到 **6 条**并存。**新增会话必须有有效口令**（与登录滥用不同，此处不可被未认证者放大），所以风险主要是"自己的脚本/多设备累积"与"已获密码者的长期占用"，详见 §5。

## 2. 缺失能力清单

| # | 缺失 | 影响 | 本设计是否覆盖 |
|---|---|---|---|
| 1 | 没有"我的登录设备"读模型 | 用户无法自查是否有陌生会话；账号疑似泄露时无从下手 | ✅ 覆盖（§3.1） |
| 2 | 无法撤销**单个**其他会话 | 只能"要么不动、要么全踢" | ✅ 覆盖（§3.2） |
| 3 | 没有"退出其他设备"（保留当前） | 同上，且全踢会把自己也踢掉（`revoke_all_sessions` 含当前） | ✅ 覆盖（§3.3） |
| 4 | 会话数量无上限 | 无界增长；无"挤掉最旧"的策略 | ✅ 覆盖（§5，可选实施） |
| 5 | 无"撤销原因" | UI 只能说"已失效"，无法解释"因为改了密码 / 被新设备挤掉" | ⚠️ 需 schema，见 §6（**可选**） |
| 6 | 无设备名/IP/位置 | 只能显示 UA 原文（需前端解析成友好标签） | ❌ 需 schema + 隐私决策，**建议不做**（§6） |
| 7 | 审计未落"谁撤销了什么" | `login_failed`/`user_login` 已有，撤销动作尚无事件 | ✅ 覆盖（§3 的审计要求，**无需 schema**） |

## 3. API 设计建议

三个端点，全部挂在 `/api/auth/sessions` 下（与既有 auth 路由同前缀，自动继承 Phase 2.4-a 的 `Cache-Control: no-store` 中间件）。

### 3.1 `GET /api/auth/sessions` —— 列出**自己**的会话

```
200 OK
{
  "sessions": [
    {
      "id": 12,                       // user_session.id（非凭据，见 §4.1）
      "current": true,                // 是否为发起本次请求的会话
      "created_at": "2026-09-22T14:53:01.618202Z",
      "last_seen_at": "2026-09-22T14:53:01.828900Z",   // 可能为 null（登录后从未使用）
      "expires_at": "2026-10-22T14:53:01.618202Z",     // 绝对上限，不续期
      "user_agent": "Mozilla/5.0 (Windows NT 10.0; ...)",
      "user_agent_truncated": false                    // 原文被 300 字符截断时置 true
    }
  ]
}
```

| 设计点 | 决定与理由 |
|---|---|
| 只返回**存活**会话 | 已撤销/已过期的行对用户无操作价值，且 `prune` 随时会删除它们——展示它们等于承诺一个不存在的历史 |
| 排序 | `COALESCE(last_seen_at, created_at) DESC`：最近活动的在最前，因此**当前会话通常排第一**；不需要新索引（`user_id` 索引已够，单用户会话数是十位数量级） |
| `last_seen_at` 可为 null | 登录后从未发过请求的会话；UI 应显示"尚未使用"，而不是伪造一个时间 |
| 不返回 `token_hash` / 明文 token / `revoked_at` | 见 §4.1、§4.2 |
| 认证 | 需登录（`CurrentUser`）；**只查 `user_id = 当前用户`**，别人的会话根本不出现在结果里 |
| 幂等/只读 | 纯读，无副作用 |

### 3.2 `DELETE /api/auth/sessions/{session_id}` —— 撤销**自己**的某个会话

| 情形 | 响应 | 理由 |
|---|---|---|
| 自己的存活会话 | `200 {"ok": true}`；若该会话**就是当前会话**，同时返回删除 Cookie（属性复用 `_session_cookie_attributes()`，与登出一致） | 撤销当前会话必须等价于登出，否则客户端会留着死 Cookie |
| 自己的**已撤销**会话 | `200 {"ok": true}`（幂等） | 与 Phase 2.4-b 的登出幂等语义一致；重复点击不该报错 |
| 别人的会话 id / 不存在的 id | **`404 {"detail": "会话不存在"}`**，两者**完全一致** | 沿用全项目 IDOR 规则（404 而非 403）；否则该端点会变成"某 id 是否存在"的探针 |
| 未登录 | `401` | — |

- **审计**：写入 `HistoryEvent(event_type="session_revoked", user_id=…, entity_type="user_session", entity_id=<id>, payload={"current": bool})`（无需 schema 变更，`history_event` 列已齐备）。
- **为什么用 `DELETE` 而不是 `POST /{id}/revoke`**：HTML 表单**不能**发起 `DELETE`，而表单可以发起 `POST`。当前 `SameSite=Lax` 已使跨站 POST 不带 Cookie（实际不可利用），但用 `DELETE` 是零成本的纵深防御；不要为了"统一风格"而选择可被表单提交的动词（§4.4）。

### 3.3 `POST /api/auth/sessions/revoke` —— 批量撤销（**需重认证**）

```
请求体：{"scope": "others" | "all", "current_password": "…"}
200 OK  {"revoked": 3, "scope": "others"}
```

| 设计点 | 决定与理由 |
|---|---|
| `scope: "others"` | 撤销该用户**除当前会话外**的全部（需要新的服务函数 `revoke_other_sessions(session, user, keep_session_id)`——现有 `revoke_all_sessions` 会连当前会话一起撤销，见 Phase 2.3 I1） |
| `scope: "all"` | 撤销**全部含当前**，并返回删除 Cookie（客户端随即登出）。语义上等价于"登出所有设备" |
| **必须带 `current_password`** | 见 §4.5：这是影响最大的会话操作（会把其他设备踢下线，包括合法设备），且是唯一能防住"被窃 Cookie 者反过来把用户全踢下线"的手段 |
| 为什么批量用 `POST` 而非 `DELETE /api/auth/sessions` | ①"全删"与"留当前"是同一操作的两种范围，用一个端点 + `scope` 比两个近乎重复的端点更清晰；②`POST` 可被表单提交，**正是因此才要求口令**——跨站表单不知道口令，纵深防御成立 |
| 审计 | 每个被撤销的会话写一条 `session_revoked`（`payload` 带 `scope`），或一条汇总事件 + 计数（见 §7.2 的取舍） |
| 未登录 / 口令错误 | `401` / `400 {"detail": "当前密码不正确"}`（与 `POST /api/auth/password` 的语义一致） |

### 3.4 "当前会话"如何识别（实现要点）

- 今天 `get_current_user`（`deps.py`）**解析出了会话行却丢弃了它**，路由只拿到 `User`。
- 建议新增依赖 `get_current_session()`：返回 `resolve_session` 得到的 `UserSession` 行；并让 `get_current_user` **依赖它**（FastAPI 在同一请求内缓存子依赖结果 → 仍只解析一次，既有端点的行为与开销不变）。
- `current` 字段 = `record.id == 当前会话行.id`（不是比较 token、不是比较 `token_hash`）。
- 撤销"当前会话"的分支必须显式处理（返回删除 Cookie），否则客户端会持有失效 Cookie 直到下次 401。

## 4. 安全分析

### 4.1 session id 能否暴露？

**可以，但必须严格满足两个条件**（[实测 4] 显示了代价）：

| 方案 | 评价 |
|---|---|
| **A. 暴露 `user_session.id`（推荐）** | 简单、与全项目"用主键寻址 + 归属校验 + 404"的风格一致。**代价 [实测 4]**：id 是**全表自增**而非按用户计数，所以任何已认证用户都能从自己的 id 推断"实例累计签发过多少会话"（实测新库上 1..5）。在 2 用户私有实例上可忽略；属于 **Informational** 级信息暴露 |
| B. 暴露 HMAC 派生 id | 能掩盖序列，但需要引入服务端密钥（配置项）+ 映射层；**当前不值得**（禁止过度设计） |
| C. 用 `token_hash` 前缀当 id | ❌ **明确否决**：把校验凭据的一部分当成公开标识，会诱导后续把它当密钥使用；且哈希前缀是离线比对材料 |

**不可协商的前提**：所有按 id 的查询**必须**带 `user_id` 过滤，且"别人的 id"与"不存在的 id"返回同一个 404（验收测试必测）。

### 4.2 API 是否需要返回 token 信息？

**不需要，且禁止。** 三条理由：

1. 明文 token 只存在于 HttpOnly Cookie，**从不落库**（[实测 5]）——服务端根本没有它可返回；
2. `token_hash` 是验证材料。返回它虽不能让攻击者直接登录（需要原像），但会：①让"会话标识"看起来像凭据；②若前端把它当 key 或写进日志，等于把凭据扩散；
3. 会话管理所需的一切（谁、何时创建、何时活动、何时失效、什么设备）都不依赖 token。

**规则**：响应字段白名单 = `id, current, created_at, last_seen_at, expires_at, user_agent`；**不得**出现 `token`、`token_hash`、`token_hash` 的派生值。

### 4.3 当前会话的识别（同 §3.4）

用"本次请求解析出的行 id"比较，**不做**任何基于 UA/时间戳的猜测（同 UA 会话无法区分 [实测 3]，靠猜会撤错设备）。

### 4.4 CSRF 风险

| 控制 | 现状 | 对本设计的影响 |
|---|---|---|
| `SameSite=Lax` | 已生效（2.2 起） | 跨站 `POST`/`DELETE` **不带 Cookie** → 请求到达时为未认证 → `401`。这是当前所有写端点的主控制 |
| 无 CORS 中间件 | 已生效 | 跨源 `fetch` **读不到**响应（`GET /api/auth/sessions` 无法被外部页面窃取内容） |
| **无 `Origin`/`Referer` 校验** | 仍缺失（Phase 2.3 B2，明确不在本阶段范围） | 新端点继承同一姿态；**不得**因此认为本设计引入了新的 CSRF 面 |
| 端点形态 | 本设计 | 单会话撤销用 `DELETE`（表单无法提交）；批量撤销用 `POST` **但要求口令** → 即使将来把 `SameSite` 放宽到 `None`，跨站仍无法凭"已登录"完成批量撤销 |
| 响应缓存 | `/api/auth/*` 已被 2.4-a 的中间件覆盖 | 列表响应不会被缓存复用 |

### 4.5 是否需要重新认证？

| 操作 | 是否要求口令 | 理由 |
|---|---|---|
| 列出会话 | 否 | 只读自己的数据，与 `GET /api/auth/me` 同级 |
| 撤销**单个**会话 | 否 | 与"登出自己"同级能力；要求口令只会增加日常负担（用户正是要在"发现陌生设备"时快速处理） |
| 批量撤销（`others`/`all`） | **是** | ①影响最大（可能把合法设备全部踢下线）；②能阻止"持被窃 Cookie 的攻击者反过来把用户踹下线"；③与 `POST /api/auth/password` 已有的"当前密码"模式一致；④成本仅一次 Argon2（≈70 ms），属罕见操作 |

**⚠️ 本设计引入的一个新风险（必须在实施时一并处理）**：要求重认证等于在**已认证**的路径上新增了一个**口令校验点**——`POST /api/auth/sessions/revoke`。`POST /api/auth/password` 已经存在同样的问题（无失败计数）。持被窃 Cookie 的攻击者可借此逐次试探口令（每次约 70 ms，无任何限速），以获得"用户撤销会话后仍能重新登录"的持久性。

**建议**：把 Phase 2.6-a 已有的按地址失败窗口（`app.services.limiter`）**同时应用于所有"校验当前口令"的端点**（登录、改密、批量撤销），或在实施批量撤销时明确接受该暴露面并记录（攻击者已持会话 → 已能读取全部数据，口令试探的边际收益是"持久化"）。**本阶段只提出，不实现。**

### 4.6 其它风险

| # | 风险 | 说明与建议 |
|---|---|---|
| R1 | **撤销当前会话的竞态** | 用户 A 在设备 1 撤销"设备 2"，同时设备 2 正在发请求：撤销后设备 2 的下一请求 401（Phase 2.2 的存活判定保证）。**无需额外处理**，只需测试覆盖"撤销后旧 Cookie 立即失效" |
| R2 | **`last_seen_at` 陈旧 5 分钟** [实测 6,7] | UI 不得宣称秒级精度；也不要据此自动判定"可疑设备" |
| R3 | **已撤销行会被 `prune` 删除** | 列表**只展示存活会话**，避免"刷新后条目消失"的迷惑；也不做"最近结束的会话"历史（那需要新的保留策略） |
| R4 | **批量撤销无"部分失败"语义** | 设计为单事务提交，返回实际撤销数 `revoked`；若为 0 也返回 200（幂等），不报错 |
| R5 | **`revoke_all_sessions` 现语义含当前会话** | 新端点必须使用**新的**"保留当前"函数，不要复用现有函数并依赖调用方传参兜底；现有调用点（改密/停用/改角色）**保持不变** |

## 5. 数量限制设计（会话上限）

### 5.1 是否需要？

**是，但优先级低于 §3 的三个端点。** 依据：

- 无上限是事实（[实测 1]：5 次登录 → 5 条存活）。
- 会话只能由**持有效口令者**创建，因此它不是未认证攻击面（与登录路径不同），不会被匿名放大。
- 但无上限意味着：①多设备/多脚本用户与"已获密码者"的会话无界累积；②没有"新登录挤掉最旧"的收敛机制；③用户界面会越列越长。

### 5.2 建议策略（不实现，仅设计）

| 项 | 建议 | 理由 |
|---|---|---|
| 上限对象 | **每个用户的存活会话数** | `prune` 已负责死行；上限只约束存活集合 |
| 默认值 | **10**（`VOCAB_MAX_SESSIONS_PER_USER`，**0 = 不限制**） | 个人应用的实际设备数远小于 10；对自动化脚本也足够宽松 |
| 超限动作 | **挤掉最旧的**，而不是拒绝新登录 | 拒绝新登录会造成"设备丢了 → 无法登录 → 无法去撤销那台设备"的死锁；这正是用户最需要登录的时刻 |
| 淘汰顺序 | ①先删/撤销**已死**的行（它们已不可用，属清理）；②再撤销 `COALESCE(last_seen_at, created_at)` **最早**的存活会话 | "最久未活动"是最不可能正在使用的设备 |
| 当前会话 | **永不淘汰**（显式断言；按"最早活动"排序理论上也不会选中它，但必须写成硬约束） | 否则新登录会立刻把自己踢出 |
| 实施位置 | `services/auth.py::create_session`（服务层） | 让 CLI/测试/未来所有登录路径共享同一语义 |
| 是否需要 schema | **不需要**（一次 `COUNT` + 撤销） | `user_id`、`revoked_at` 已索引 |
| 可观测性 | 淘汰时写 `HistoryEvent(event_type="session_evicted")` | 用户能解释"某设备为何被登出"（配合 §6 的 `revoke_reason` 更佳） |
| 风险 | 静默登出一台设备 | 属可接受取舍；务必**写审计事件**，否则用户只会看到"莫名掉线" |

---

## 6. 数据库分析

### 6.1 结论：**本设计推荐范围不需要任何 schema 变更**

| 需求 | 现有列是否足够 | 说明 |
|---|---|---|
| 列出会话 | ✅ | `user_id`（已索引）过滤 + 现有列投影 |
| 排序（最近活动优先） | ✅ | `COALESCE(last_seen_at, created_at)` 为表达式排序，无需索引（单用户会话数为十位数量级） |
| 撤销单个 / 批量 | ✅ | `revoked_at`（已索引） |
| 会话上限与淘汰 | ✅ | `COUNT` + `revoked_at` |
| 审计 | ✅ | `history_event`（`user_id`/`event_type`/`timestamp`/`entity_type`/`entity_id`/`payload` 齐备） |
| "当前会话"标记 | ✅ | 由请求上下文计算，不落库 |

**因此不产生 migration。** 这一点与 Phase 2.5/2.6-a 的结论一脉相承：会话管理可以在现有表上完成。

### 6.2 什么情况下才需要 schema（**只提出，不实现**）

| 若产品要求 | 需要的变更 | 代价与建议 |
|---|---|---|
| 会话**撤销原因**（"因修改密码被登出"/"被新设备挤掉"） | `user_session.revoke_reason`（可空 String(32)）→ **migration 0008** | 纯可选、显著提升 UI 诚实度；建议与 §5 的上限一起做 |
| 设备**名称**（"我的 iPhone"） | 可空 String 列 | 需要用户输入与前端交互；价值中等 |
| 展示**客户端 IP / 位置** | 新列 + 采集 | ⚠️ **建议不做**：Phase 2.5 已确定不存 IP（个人数据、且与最小化原则冲突）；一旦引入需要单独的隐私决策与保留策略 |
| **更精确的最近活动** | 无需 schema | 降低 `TOUCH_INTERVAL` 即可，但每次请求写入频率上升（Phase 2.2 的节流正是为了避免这一点），不建议 |
| **已结束会话的历史** | 需要独立表或保留策略 | **建议不做**：`prune` 会删除死行，而"谁在何时撤销了什么"已由 `history_event` 记录 |

## 7. 实施拆分建议

### 7.1 阶段划分（每步独立可发布、零 schema、零 migration）

| 阶段 | 内容 | 关键验收 |
|---|---|---|
| **2.7-b** | `GET /api/auth/sessions` + `get_current_session` 依赖（`get_current_user` 改为依赖它，行为不变） | 只列自己的；`current` 正确；排序符合"最近活动"；响应**不含** token 字段；匿名 401；带 `no-store`；空列表 `[]` |
| **2.7-c** | `DELETE /api/auth/sessions/{id}` + `session_revoked` 审计 | 自己的会话被撤销且旧 Cookie 立即 401；**别人的 id 与不存在的 id 都 404**（响应逐字相同）；撤销当前会话时返回删除 Cookie；重复调用幂等 200；不产生 `user_session` 之外的行 |
| **2.7-d** | `POST /api/auth/sessions/revoke`（`scope` + 口令） | `others` 不撤销当前会话且当前仍可用；`all` 撤销全部并清 Cookie；口令错 400；**无口令 422**；别人的会话不受影响；审计写入 |
| **2.7-e（可选）** | `VOCAB_MAX_SESSIONS_PER_USER` + 淘汰（§5） | 达到上限后新登录成功且总数不超限；被淘汰的是"最久未活动"的那条；当前会话永不淘汰；对已死行优先清理；`0` = 不限制 |
| **2.7-f** | 前端"登录设备"区块（`SettingsPage`）：列表 + 单条撤销 + "退出其他设备" + 二次确认 + UA 友好化（客户端解析） | 撤销当前会话后经既有 401 处理器回到登录页；列表刷新正确；批量操作有确认 |
| **2.7-g** | 文档：更新 Phase 2.3 审计的 L5 状态、把本设计的端点写入 README/交接文档 | 文档与实际一致 |

### 7.2 需要一并决定的三个小问题（实施时优先定调）

1. **审计粒度**：批量撤销是"每条被撤销会话一条事件"（信息全、行数多）还是"一条汇总事件 + `payload.revoked = n`"（省行）。建议**汇总事件 + 明细 id 列表上限（例如前 20 个）**，兼顾可查与可控增长。
2. **`scope=all` 的响应**：是否同时返回删除 Cookie（建议返回，语义与登出对齐），还是要求前端在成功后自行调用 `/api/auth/logout`（多一次请求，且登出已幂等）。建议**返回删除 Cookie**。
3. **是否给"撤销其他设备"加口令**（§4.5）：若决定加，请同时决定是否把 Phase 2.6-a 的失败窗口应用到"校验当前口令"的端点上；两者一起决策才自洽。
