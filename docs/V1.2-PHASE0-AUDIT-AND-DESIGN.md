**架构特征总结**：

1. **响应体没有 Pydantic 响应模型**，全部走 `api/helpers.py` 手写 dict。加 `user_id` 隔离时，必须逐个改这些 helper 的查询源，不存在「改一处全生效」的捷径。
2. **无仓储层**，路由直接持有 `Session` 并写查询。权限过滤需要落在每个路由的每个查询上。
3. **Provider 抽象做得好**：`OCRProvider` / `AIProvider` 都是 `Protocol`，云端停用 OCR 只需不调用，不需要改接口。
4. **业务写入全部 `session.commit()` 落在 service 层**，路由层通常不 commit（例外：`imports.py` 的 `_rebuild_batch_ocr` 路径由路由 commit）。

### A.3 数据库初始化路径（**Phase 1 首要风险**）

存在**两条互不相容的建表路径**：

| 路径 | 位置 | 行为 |
|---|---|---|
| 启动时自动建表 | `main.py:22` `Base.metadata.create_all(engine)` | 用**当前模型的全部列**建表 |
| Alembic 迁移 | `alembic/versions/0001_initial.py:18` `Base.metadata.create_all(bind=op.get_bind())` | 同样是**当前模型**，不是历史快照 |

后果：

- 0001 是「伪迁移」，它不描述 2026-09-21 那天的真实 schema，而是描述**运行时的最新 models**。因此无法从零重建历史。
- **只要先改 `models.py` 再跑迁移，`main.py:22` 会把新列提前写进真实库**，随后 migration 的 `add_column` 抛 `duplicate column name`。
- 现存库已在 `0003 (head)`，所以 0001/0002 实际不会再执行；但**新建测试库、新机器、云端首次部署都会踩到**。

### C.5 密码哈希方案（Phase 1 决策）

要求「成熟哈希方案」。推荐 **PBKDF2-HMAC-SHA256（`hashlib.pbkdf2_hmac`）**，理由：

- **标准库实现，零新依赖**——与「禁止过度设计」「2 个用户」完全匹配；
- 无 bcrypt/argon2 的原生编译依赖，Alibaba Cloud Linux 3 上空 `pip install` 即可，不需要 gcc/rust 工具链；
- 可自描述参数，便于日后升级：

```
存储格式:  pbkdf2_sha256$<iterations>$<salt_b64>$<hash_b64>
建议参数:  iterations = 600_000, salt = 16 随机字节, 输出 32 字节
校验:      hmac.compare_digest（常数时间）
```

若你更偏好 argon2，唯一代价是引入 `argon2-cffi`；**Phase 1 需你点头后我才实现**，默认按 PBKDF2 走。

#### D.3.7 `frequency_rank` 的诚实处理（重要）

总控第五节明确「禁止使用 AI 根据常识自行生成词频排名」。

因此迁移中：

```
lexicon_entry.frequency_rank  = NULL
lexicon_entry.frequency_count = NULL
lexicon_entry.frequency_source = ''
lexicon_entry.sequence        = NULL
```

**不给任何词编造排名。** 新词引入顺序的回落链设计为：

```
ORDER BY
  frequency_rank IS NULL,     -- 有真实词频的排前面
  frequency_rank ASC,         -- 升序：高频 → 低频
  sequence IS NULL,
  sequence ASC,               -- 真实资料缺失时的稳定顺序
  id ASC                      -- 最终稳定兜底，保证分页/顺序确定
```

外部词频资料就绪后，由**独立导入脚本**填 `frequency_rank` / `frequency_count` / `frequency_source`，该脚本需在 `frequency_source` 中写入资料名与版本以留痕。**Phase 1 不实现该脚本，只预留列与顺序逻辑。**

- `history_event` 补 `user_id`；`manual_backup` 这类实例级事件允许保持 `NULL`。

#### D.3.9 迁移幂等性与可回退

- 所有 INSERT 以「查存在再插」实现（`INSERT ... WHERE NOT EXISTS` 或先 SELECT），使迁移可重复执行而不产生重复行。

## E. 权限模型

### E.1 四类权限

| 类别 | 说明 |
|---|---|
| **P 公开** | 无需登录 |
| **A 已认证** | 需有效 Session，任意角色 |

## 6. SQLite 多用户安全性检查

> 结论：**继续用 SQLite + WAL 是安全的**，但必须补 3 个加固点，否则 2 人并发下会出现偶发 `database is locked`。

### 6.1 现状（已正确）

| 项 | 现状 | 评价 |
|---|---|---|
| 日志模式 | `PRAGMA journal_mode=WAL`（`db.py:25`） | 正确。读写不互斥，读不吃写锁 |
| 外键 | `PRAGMA foreign_keys=ON`（`db.py:24`） | 正确。但 SQLite 该 pragma 是**每连接**生效，现实现挂在 `connect` 事件上，已覆盖所有连接 ✔ |
| 连接池 | SQLAlchemy 默认 `QueuePool`（SQLite 文件库） | 可用，但需配合超时 |
| 事务 | 隐式事务，service 层 commit | 有大事务问题，见下 |
| worker | 单进程 Uvicorn | 符合总控要求；FastAPI 的同步端点跑在 threadpool，会有多线程同时写 |

### 6.2 加固点 1：`busy_timeout` 未设置（**必须修**）

`db.py` 的 connect hook **没有** `PRAGMA busy_timeout`。SQLite 默认超时极短，当一个线程持有写锁、另一线程提交时，会**立即**抛 `database is locked` 而不是等待。

```
修复：cursor.execute("PRAGMA busy_timeout=5000")
建议：设为 5000ms，并同时设置 connect_args={"timeout": 5}
```

2 个用户场景下，这基本消除偶发 500。

### 6.3 加固点 2：写事务跨越 AI / OCR 调用（**结构性隐患**）

现有代码里，**同一个 Session 在长耗时网络/计算调用期间保持打开，并在其后 commit**：

| 位置 | 长耗时调用 | 风险评估 |
|---|---|---|
| `services/imports.py:12-38 process_batch_ocr` | PaddleOCR `provider.extract()`（秒级~分钟级） | **已缓解**：每张图后立即 `session.commit()`（`imports.py:31`），锁被及时释放 ✔ |
| `api/imports.py:198-219 structure_import` | DeepSeek `structure_ocr`（可达 90s） | ⚠ **风险**：`_load_batch` 已开启读事务，await 期间事务存活；此后才 `batch.status=...` 并 commit |
| `api/articles.py:50-75 generate_article` | DeepSeek 生成（90s timeout） | ⚠ 先 SELECT 选词（无写），再 await，最后 INSERT — 风险较低但存在 |
| `api/articles.py:127-142 translate` | DeepSeek 翻译（90s） | ⚠ 同上 |
| `api/articles.py:109-124 lookup` | DeepSeek 查词（90s） | ⚠ `lookup_article_word` 内部先 SELECT 再 await 再 INSERT |

**WAL 下这些是读事务 + 延迟写，不会阻塞其他读者的 SELECT**，所以 2 用户场景不会立刻出问题。但若未来并发提高，会退化为 `SQLITE_BUSY`。

**加固方案（低风险、两阶段）**：
- **Phase 1 只做防御**：设 `busy_timeout`；在 AI 调用前显式结束当前事务（`session.commit()` 或新建短生命周期 Session 仅用于读取）。
- **Phase 2/3**：把「调用 AI」与「写库」明确分成两个阶段——先在短 Session 内取数据并关闭，AI 调用结束后用新 Session 写入。**不在 Phase 1 重构**，避免同时改变行为与结构。

### 6.4 加固点 3：迁移期间的批量重建表 + 外键

`alembic/env.py:35` 已设 `render_as_batch=True`，且既有迁移（0002/0003）已用 `batch_alter_table`。

- SQLite 的 `batch_alter_table` 会**重建表**（建新表→拷数据→删旧表→改名）。**在 `foreign_keys=ON` 时，DROP 旧表会触发外键动作**，可能级联删除或报错。
- 本次 Phase 1 的加列全部是「可空列」，`ALTER TABLE ADD COLUMN` **原地完成，不触发重建** → **无此风险**。
- 但 Phase 2 若需要给已有列加 NOT NULL 或改唯一约束，就必须重建表。届时要求：
  ```
  迁移开始时: PRAGMA foreign_keys=OFF
  重建全部完成后: PRAGMA foreign_keys=ON
  然后执行 PRAGMA foreign_key_check 确认无违规
  ```
  **注意**：SQLite 中 `PRAGMA foreign_keys` 在事务内无效，必须在事务外设置。
- `article_word_exposure` 有 `UNIQUE(article_id, word_id)` 与两个 FK，`word` 被 `review_event`/`article_word_exposure`/`article_word_lookup`/`import_candidate` 四处引用 —— **任何对 `word` 表的重建都要格外小心**，这是继续保留旧表而非删除的主要原因之一。

### 6.5 其他 SQLite 相关确认

| 项 | 结论 |
|---|---|
| `alembic.ini` 里的静态 URL | **已被覆盖**。`alembic/env.py:11` 用 `get_settings().database_url` 覆盖，`VOCAB_DATA_DIR` 生效 ✔ |
| 时区 | 全部 `DateTime(timezone=True)` + `datetime.now(UTC)`。**SQLite 不存储时区**，读出的是 naive datetime。现有代码比较的都是同源值，暂无症状，但跨用户/跨时区展示时需注意（Phase 3 前端处理） |
| 并发写 | 单文件 SQLite 串行写；2 用户 + 低频写入（复习、文章）完全够用 |
| 备份 | `sqlite3.backup()` API（`backup.py:16-17`），**在线热备份安全**，不会读到半写状态 ✔ |
| WAL 文件 | `vocab.db-wal` 当前 515 KB；备份走 `sqlite3.backup` 会**自动 checkpoint 内容**，无需手工处理 ✔ |

## 9. 备份逻辑审计

### 9.1 现状

```python
# services/backup.py
def create_backup(database_path, backups_dir, name=None):
    target = backups_dir / (name or f"{date.today().isoformat()}-vocab.db")
    if target.exists():
        return target        # ← 天级幂等，不覆盖
    with sqlite3.connect(database_path) as src, sqlite3.connect(target) as dst:
        src.backup(dst)      # ← 在线热备份，安全
```

调用点（**仅两处**）：

| 调用点 | 触发时机 |
|---|---|
| `main.py:23`（lifespan 启动） | **每次程序启动** |
| `api/settings.py:121`（`POST /api/settings/backup`） | 用户手动点 |

### 9.2 为什么「启动时备份」不适合 24h 云服务器

| # | 问题 | 后果 |
|---|---|---|
| S1 | **触发时机与业务无关** | 服务器 24 小时运行，可能数周不重启 → **数周没有任何新备份**。当前唯一保障是人工点按钮 |
| S2 | 备份时点落在「进程重启」而非「数据稳定期」 | 崩溃重启时可能正好处于异常状态，此时备份等于备份了坏状态 |
| S3 | 无保留策略 | 天级文件只增不减。40 GB ESSD 下短期无碍（19 词库约 380 KB），但无上限不符合长期维护要求 |
| S4 | **无异地/异盘副本** | 备份与数据库同盘（`data/backups/`）。**磁盘损坏或误删 `data/` 会同时丢失两者** |
| S5 | 无备份成功/失败的可见性 | 备份失败静默（`create_backup` 不抛异常也不记录） |
| S6 | 无 DB 完整性验证 | 备份后不执行 `PRAGMA integrity_check`，坏备份无法被发现 |

### 9.3 已具备的良好特性（保留）

- ✔ **天级幂等**：`target.exists()` 检查天然满足总控「不得覆盖同一天已有安全备份」。
- ✔ **在线热备份**：用 `sqlite3.backup()` API 而非文件拷贝，**不会复制到半写状态**，与 WAL 兼容。
- ✔ **手动备份保留**：`POST /api/settings/backup` 生成带时间戳的 `manual-YYYY-MM-DD-HHMMSS-vocab.db`，不冲突。

### 9.4 Phase 3 建议方案（本阶段不实现）

```
1. 新增 CLI: python -m app.cli backup --label daily
   → 复用 create_backup（保持幂等语义），但脚本层负责：
     a) 迁移/写入前确保当日备份存在
     b) 备份后执行 PRAGMA integrity_check
     c) 失败时以非零退出码结束（让 systemd 记录）
2. systemd timer（每日固定时刻，如 03:30 + Persistent=true 补跑漏过的）
   → 即使服务未运行也能备份（timer 独立于 service）
3. 保留策略：保留最近 N 份日备份（建议 30）+ 全部 manual 备份
   → 清理逻辑必须「只删自己生成的 daily-*.db」，绝不匹配 manual-*
4. 可选（推荐）：每日把当天备份再复制一份到项目外目录或对象存储
   → 解决 S4「同盘丢失」
5. 日志：每次备份写 history_event(event_type='scheduled_backup')，Dashboard 可展示
```

`word.anchor` 既是词库内容（人工校对结果）又是个人学习字段（`services/words.py:7` 的 `LEARNING_FIELDS`）。
**若只迁到 `anchor_override`**，一旦该用户锚点被清空，「原书/人工校对的锚点」就永久消失了。
**应对**：**同值双写两侧**（D.3.2），这是不可省略的一步。

### F6. 🟡 复习接口无归属校验，是最高危 IDOR 入口
`POST /api/study/words/{word_id}/review`（`services/study.py:19` 直接 `session.get(Word, word_id)`）。
多用户上线后，B 只要猜 word_id 就能**污染 A 的复习历史与调度**。
**应对**：必测项；返回 404。

### F7. 🟡 429 行 `helpers.py` 式手写序列化难以整体加固
响应体全为手写 dict，无统一出口。**一个遗漏的查询就会泄露他人数据。**
**应对**：不重构为 Pydantic 响应模型（那是大重构），而是**用 IDOR 测试矩阵覆盖每个端点**，以测试而非架构来保证。

### F8. 🟡 `history_event` 无 user 维度
个人事件（`article_word_lookup` × 5、`import_confirmed`）与实例事件（`manual_backup`）混在一张表。**应对**：加可空 `user_id`，实例级事件保持 NULL。

### F9. 🟡 Cookie `Secure` 与本地 HTTP 冲突
本地开发是 `http://127.0.0.1:8000`。硬编码 `Secure=true` → 本地登不上；硬编码 `false` → 云端不安全。
**应对**：由 `VOCAB_COOKIE_SECURE` 控制，云端 `true`。**Phase 1 必须同时验证两种配置。**

### F10. 🟡 `.env.example` 缺失
当前工作区该文件被主动删除（ZIP 里存在），而工程要求保留。
**应对**：Phase 1 恢复并补齐新变量（`VOCAB_COOKIE_SECURE`、`VOCAB_SESSION_DAYS`、`VOCAB_ENABLE_OCR`、`VOCAB_BOOTSTRAP_USERNAME`）。

### F11. 🟡 云端无 PaddleOCR 会导致启动崩溃
`main.py:21` **无条件**调用 `configure_paddle_environment()`，它内部会 `mkdir` 模型目录；未装 Paddle 时 `settings.py:66` 的 import 有 try/except，但启动路径没有。
**应对**：加 `VOCAB_ENABLE_OCR` 开关，默认本地 true、云端 false。

### F12. 🟡 无 migration 测试 = 数据迁移裸奔
现在**没有任何测试覆盖 Alembic**。而 V1.2 的核心约束是「不得丢失任何历史数据」。
**应对**：Phase 1 首先补两条测试：
1. 空库 `upgrade head` 成功
2. **用 V1.1 真实结构 + 种子数据 upgrade 到 V1.2，断言行数与关键字段逐项不变**

### F13. 🟢 时区语义（低危，记录备查）
SQLite 不存时区，`DateTime(timezone=True)` 读出为 naive。现有代码全部同源比较，无症状；跨时区展示时需处理。

## G. Phase 1 具体实施计划

### G.0 总体顺序原则

严格遵循总控要求：

```
① 先加新表/新字段（可空，纯增量，不改任何现有数据）
   ↓
② 迁移并回填真实数据
   ↓
③ 验证（行数 + 字段逐项比对 + 引用完整性）
   ↓
④ 切换业务读取到新结构（按 current_user 过滤）
   ↓
⑤ 最后才考虑废弃旧结构（本阶段不做）
```

**Phase 1 只做到 ④，绝不执行 ⑤。**
