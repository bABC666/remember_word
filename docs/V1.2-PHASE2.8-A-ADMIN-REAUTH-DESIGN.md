## 0. 结论摘要

1. **保护范围（本次产品定调）**：`POST /api/users` 与 `PATCH /api/users/{id}` 的**每一次调用**都必须携带调用者（管理员**自己**）的当前口令，**不按操作种类分档**——建号、改显示名、改角色、停用/启用、改他人密码、以及"什么都没改"的空更新，一律要求。与 `PROJECT_ROADMAP.md` §11 D1 的建议 (a) 一致。
2. **复用既有守卫**：`_require_password`（`backend/app/api/auth.py:131-187`）**一行未改**——四步顺序（预算检查 → 共享闸门 → 一次 `verify_user_password` → 审计/计数）保持原样；只新增两个动作枚举值。每用户预算、共享并发闸门、`reauth_failed` 审计、成功清零的语义完全继承。
3. **零 schema / 零新配置 / 零新机制**：不新建限流类、不新增 `VOCAB_*` 变量、不加字段、不加 migration；复用 `history_event` 既有列。
4. **契约变化**：两个请求体各新增**必填** `current_password`（`Field(min_length=1, max_length=256)`），与既有三个受保护端点（`POST /api/auth/password`、`POST /api/auth/sessions/revoke`、`DELETE /api/auth/sessions/{id}`）同名同义。
5. **失败行为**：无口令/空口令/`null` → **422**；口令错 → **400**`{"detail":"当前密码不正确"}`；预算耗尽或闸门饱和 → **429** + `Retry-After`；非管理员 → **403**（**先于**契约校验，能力判定优先）；未登录 → **401**。**校验通过之前，不修改任何账号行、不创建或撤销任何会话。**
6. **缓存**：把 `/api/users` 纳入既有 `no-store` 中间件的路径前缀（`backend/app/main.py:61-77`），使 201/200/400/422/429 与 `GET /api/users` 都带 `Cache-Control: no-store`。这正对应 `V1.2-PHASE2.7-D-A-REAUTH-DESIGN.md` §5.3 末尾标注的"注意点"。
7. **审计**：失败写 `reauth_failed`（`payload.action` 为固定枚举 `"create_user"` / `"update_user"`，不接受客户端文本）；成功沿用既有 `user_created` / `user_updated` 事件，但 `fields` 中**排除** `current_password`。**口令、token、`token_hash` 不进任何响应、不进任何审计。**
8. **前端**：**[实测] 当前仓库没有任何管理员用户管理入口**（见 §1.4）→ 本次**不新建页面**。契约变化只影响未来的客户端与测试调用方；本次只更新既有测试的调用参数。

## 2. 方案取舍

### 2.1 为什么守卫仍然是"路由里显式调用的普通函数"

沿用 `V1.2-PHASE2.7-D-A-REAUTH-DESIGN.md` §5.2 的结论，本次不改成 FastAPI 依赖：**口令是被操作的一部分，不是请求的前置条件**。做成 `Depends(...)` 就得再声明一份 body 模型，与路由自己的模型重复解析同一份 JSON，产生两个真相来源。因此两个端点各自在**函数体第一行**调用 `_require_password`。

### 2.2 为什么"每次操作都要口令"（而不是只保护建号/改角色）

| 方案 | 评价 |
|---|---|
| **A：两个端点的每次操作都要（采用）** | 判据单一可执行："这两个端点上的任何写操作都要口令"。不给"哪种字段组合需要口令"留下实现缝隙（例如将来新增字段忘记归类）；与设计文档 §3.2 的判据「会改变认证材料、会话集合、账号权限或安全设置的操作」一致——本端点的每个字段都属其中一类 |
| B：只保护 `role` / `password` / `is_active=False` | 需要"按请求体分档"的分支，`display_name` 之类会漏；且 `is_active=True`、空更新是否要口令会反复争议 |
| C：sudo 免密窗口（认证后 N 分钟免密） | 需要按会话/用户保存"已验证到何时"的状态 → 命中 §5.5「只有在以下情况才需要 schema」，属过度设计；本项目敏感操作极低频 |

**被否决的替代方案**：把管理员口令做成一次性 token / 挑战-响应（需要新表或新字段）、引入 TOTP / 邮件二次验证（无邮件基础设施、无恢复流程，属独立大议题）。均与"复用现有守卫、零迁移"的任务口径冲突。

### 2.3 校验发生在**任何读写之前**

两个端点的顺序固定为：**依赖（认证+能力）→ `_require_password` → 业务读取（404 判定）→ 业务写入**。

- 校验通过前**不查目标用户**（因此"目标 id 是否存在"在校验失败时不可能被观察到，见 §3.3 的不可区分性断言）；
- 校验通过前**不写任何行**（唯一例外是守卫失败时那条 `reauth_failed` 审计，以及认证依赖对**调用者自己**会话的既有心跳，见 §6"明确不做"）。

### 2.4 为什么本次**不**扩展到 `PUT /api/settings`

- `PUT /api/settings` 是**混合作用域**端点：普通用户用它保存自己的偏好（`daily_new_words`、`article_length`），管理员顺带改实例级字段（`settings.py:107-141`）。无条件加口令会**打断普通用户的日常保存**；按字段条件加口令会让契约随请求体形状变化，属另一类设计。
- `POST /api/settings/backup` 按设计文档 §3.1 #8 **明确不需要**口令（只读导出、无破坏性）。
- 两者都登记在 §8 剩余风险里，等待单独任务/产品决策。

## 3. 保护范围、契约与失败行为（本阶段的"明确承诺"）

### 3.1 范围（本阶段承诺保护的全部操作）

| 端点 | 方法 | 受保护的操作（**全部**） | 新增动作枚举 |
|---|---|---|---|
| `/api/users` | `POST` | 建号（含建管理员）、重名检查前的校验；**每一次调用** | `create_user` |
| `/api/users/{user_id}` | `PATCH` | 改显示名 / 改角色（升·降权）/ 停用·启用 / 改他人密码 / 空更新；**每一次调用** | `update_user` |

**不在本次范围**：`GET /api/users`（只读列表，不需要口令）、`PUT /api/settings`、`POST /api/settings/backup`、`POST /api/lexicons/...`、CLI（`app/cli.py` 是操作员路径，口令只从 `getpass` 读，**保持不变**，仍是管理员被锁时的逃生口）。

### 3.2 请求体契约

| 模型 | 新增字段 | 约束 |
|---|---|---|
| `CreateUserRequest`（`schemas.py:122-126`） | `current_password: str` | `Field(min_length=1, max_length=256)`，**必填** |
| `UpdateUserRequest`（`schemas.py:129-133`） | `current_password: str` | 同上 |

- 字段名与既有三个受保护端点**完全一致**（`ChangePasswordRequest` / `SessionRevokeRequest` / `SessionDeleteRequest`），语义都是"调用者自己的当前口令"。**不要**与 `UpdateUserRequest.password`（**被操作账号的新口令**）混淆——这正是必须另起一个名字的原因。
- `PATCH` 的"要改哪些账号字段"仍由 `exclude_unset` 决定；`current_password` **不参与** `changes`，因此既不会进入字段赋值，也不会出现在审计的 `fields` 里（实现见 §4）。

### 3.3 失败行为矩阵（**验收时逐格必须有测试**）

| 情形 | 状态码 | 响应体 | 账号行 | 会话 | 审计 | `Cache-Control` |
|---|---|---|---|---|---|---|
| 未登录（无 cookie/失效） | **401** | `{"detail":"请先登录"}` | 不变 | 不变 | 无新事件 | `no-store` |
| 已登录但非管理员 | **403** | `{"detail":"需要管理员权限"}` | 不变 | 不变 | 无新事件 | `no-store` |
| 管理员，**缺少** `current_password` | **422** | FastAPI 校验错误 | 不变 | 不变 | 无新事件 | `no-store` |
| 管理员，`current_password` 为 `""` / `null` | **422** | 同上 | 不变 | 不变 | 无新事件 | `no-store` |
| 管理员，口令**错误** | **400** | `{"detail":"当前密码不正确"}` | 不变 | 不变 | **+1 条 `reauth_failed`**（`payload.action` 为固定枚举） | `no-store` |
| 管理员，口令正确但**预算已耗尽** | **429** | `{"detail":"密码校验尝试过于频繁，请稍后再试"}` + `Retry-After: <秒>` | 不变 | 不变 | **不写**（防放大） | `no-store` |
| 管理员，口令正确但**闸门饱和** | **429** | 同上 + `Retry-After: 1` | 不变 | 不变 | 不写 | `no-store` |
| 管理员，口令**正确**、业务失败（重名 409 / 目标不存在 404 / 自我保护 400） | 409 / 404 / 400 | 各端点原有文案 | 不变 | 不变 | 仅原有事件（无） | `no-store` |
| 管理员，口令**正确**、业务成功 | 201 / 200 | `user_payload`（**不含** `password_hash`/token/`token_hash`） | 按业务变更 | 按业务变更（改密/停用会撤销**目标**会话） | `user_created` / `user_updated` | `no-store` |

**顺序保证（本次的核心安全承诺）**：

1. **能力先于契约**：非管理员即使不带口令也是 **403**，不是 422——既有 `test_authz.py:351-359` 的语义不被破坏。
2. **口令先于读写**：口令错误时，连"目标用户是否存在"都不查；因此**目标 id 存在与不存在时的 400 响应完全一致**（测试逐字节比对响应体）。
3. **不可区分的信息面**：400 的文案与既有三个受保护端点相同，不新增"该账号未设置口令""口令已过期"之类的可区分信息。

### 3.4 缓存语义

`main.py:61-77` 的 `no-store` 中间件今天只判断 `path.startswith("/api/auth/")`。本阶段把它扩展为**同一个判断里的第二个前缀 `/api/users`**：

- 覆盖 `POST /api/users`、`PATCH /api/users/{id}`、`GET /api/users` 的**全部**响应（含 401/403/404/409/422/429），因为中间件在异常处理之外，`require_admin` 抛出的 403 也经过它；
- 理由：这些响应描述的是账号（用户名/角色/停用状态）与会话状态，属"不可共享、不可复用"的答案；同时一个前缀规则不会漏掉同前缀下的新端点；
- 与 CSRF 中间件的关系不变：CSRF 仍是最外层（先拒绝），其 403 自带 `no-store`。

### 3.5 审计语义（失败与成功）

| 事件 | 触发 | 字段 | 禁止 |
|---|---|---|---|
| `reauth_failed` | 口令校验失败（每次） | `user_id=调用者`、`entity_type="user"`、`entity_id=调用者`、`payload={"action": "create_user"｜"update_user"}` | 不含口令、token、`token_hash`；不含客户端文本 |
| `user_created`（既有） | 建号成功 | `entity_type="user"`、`entity_id=新用户`、`payload={"by": 管理员名, "role": …}` | 同上 |
| `user_updated`（既有） | 更新成功 | `payload={"by": 管理员名, "fields": [账号字段名…]}`，**`current_password` 已从 `fields` 排除** | 同上 |
| 429 | 预算/闸门拒绝 | **不写事件** | 限流不能成为写放大路径 |

## 5. 测试策略

**新增 `backend/tests/test_admin_reauth.py`**（每条对应 §3.3 的一格或一条顺序保证；"每次操作"用参数化覆盖全部字段组合）：

1. **契约**：`POST`/`PATCH` 缺 `current_password`、`""`、`null` → 422，且账号与会话零变化。
2. **错口令**：400 + 文案一致 + 1 条 `reauth_failed`（`payload == {"action": …}`）+ 提交的口令不出现在审计里。
3. **对口令**：201/200，且新账号能用其口令登录、响应无 `password_hash`/token/`token_hash`。
4. **每种操作都要口令**（参数化 `display_name` / `role` / `is_active` / `password` / 空更新）：无口令 422、错口令 400、对口令成功。
5. **无副作用**：错口令时目标账号的 `password_hash` / `is_active` / `role` 不变、目标用户的**活跃会话仍在**（受害者客户端仍能 `GET /api/auth/me`）、不新增 `user_updated` / `session_revoked` 事件。
6. **权限顺序**：普通用户 *不带*口令 → 403（不是 422）；带正确口令 → 403；匿名 → 401。
7. **目标 id 不可区分**：`PATCH /api/users/不存在` 与 `PATCH /api/users/存在` 在**错口令**下返回**逐字节相同**的 400。
8. **预算与 429**：连续失败达阈值 → 429 + `Retry-After` + 不写事件；成功清零；**预算跨端点共享**（在 `/api/auth/password` 上烧掉后，`POST /api/users` 也 429——无法靠换端点绕过）。
9. **闸门**：槽位占满 → 429 且**一次校验都不发生**（spy 断言）。
10. **no-store**：201/200/400/422/429 与 `GET /api/users` 均带 `Cache-Control: no-store`。
11. **不泄露秘密**：所有响应文本中不出现提交的口令、`password_hash`、`token_hash`、会话 token。

**既有测试更新**（只加参数，不删断言）：`test_auth.py::test_admin_can_create_and_disable_users`、`::test_admin_cannot_lock_themselves_out`；`test_authz.py` / `test_csrf.py` 的相关断言**预期无需改动**（403/403 来自能力与 CSRF 层，先于契约校验）——若实际不符，说明顺序保证被破坏，必须修实现而不是改断言。

## 8. 风险与逃生口

| # | 风险 | 级别 | 说明与缓解 |
|---|---|---|---|
| R1 | **管理员操作摩擦增加**（每次多输一次口令） | 🟡 中 | 产品决策 D1 已选 (a)。缓解：预算 5 次/300 秒且只在敏感操作上；**登录与日常使用不受影响** |
| R2 | **恢复路径可被短暂封锁**（持被窃会话者烧预算，使合法管理员 300 秒内无法改密） | 🟡 中 | 与 S-3 同源；缓解：短窗口 + 登录不受影响 + **CLI 逃生口**（`python -m app.cli set-password` / `promote`，不经 API）+ 每次失败有审计 |
| R3 | **`PUT /api/settings` 仍无二次认证** | 🟠 应尽快 | 管理员可改 `deepseek_base_url`（把 Key 指向攻击者端点）与实例 OCR 配置。本次有意不做（§2.4），登记为**下一批候选** |
| R4 | **429 与登录共享并发闸门** | 🟢 低 | 登录洪水期间敏感操作也可能 429（槽位周转 ≈70 ms）；需要隔离时拆闸门，代价是内存上限翻倍（沿用 2.7-d-a R3） |
| R5 | **内存计数的既有取舍** | 🟢 低 | 重启清零、多 worker 各一份；单 worker 是架构硬约束 |
| R6 | **前端没有入口 → 能力对用户不可见** | 🟡 中 | 今天管理员只能经 CLI/脚本改账号；本次不建页面（任务口径），但契约变化使"将来建页面"必须带口令确认对话框（组件已存在） |
| R7 | **文档漂移复发**（I-1/I-5/I-6/I-7） | ⚪ 记录 | 已在本文件逐条登记，避免下次审查重新发现同一批 |

**回滚**：本阶段是"加一层校验"，回滚 = `git revert` 单个 commit（无数据、无 schema、无配置参与）。若线上需要临时放宽，只能改代码 —— **本次不提供"关掉 S-1"的环境变量**：一个能让管理员端点退回"仅凭会话"的开关，本身就是新的持久化后门面。
