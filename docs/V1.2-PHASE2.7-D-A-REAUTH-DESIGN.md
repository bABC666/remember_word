## 0. 结论摘要

1. **确实存在重复逻辑**：应用里有**两处**密码校验，且**策略不一致** —— login（等时校验 + 哨兵保护）与 `POST /api/auth/password`（裸 `verify_password`）。可抽出一个共享函数 `verify_user_password(user, password)`，两处只保留"失败后做什么"的差异。
2. **最严重的敏感操作缺口不在用户侧，而在管理员侧**：`PATCH /api/users/{id}` 与 `POST /api/users` **完全不需要任何口令**（仅凭管理员会话）就能**改他人密码、改角色、停用账号、创建新的管理员** —— 这是"账号接管 + 持久化"的完整链条。
3. **二次认证的失败保护必须独立于登录限流**：语义不同（匿名 vs 已认证），且共用会让"同一 NAT 出口的登录洪水"锁死合法用户的设置页、也会让用户在自己设置页上敲错两次密码就吃掉登录额度。**`LoginFailureWindow` 已按字符串键泛化，可用 `str(user_id)` 直接复用，零 schema。**
4. **资源闸门应当共享**：一次 re-auth 就是一次 Argon2（Phase 2.5 实测 **61–81 ms、64 MiB**）。若只保护 login，持被窃会话者可用设置页把 CPU/内存打满。因此**任何执行密码校验的端点都应经过同一个 `LoginGate`**（上限 8 ≈ 512 MiB）。
5. **推荐参数**：每用户 **5 次失败 / 300 秒** → `429 + Retry-After`；成功后清零；**不影响登录**。
6. **不需要任何 schema 变更**（内存计数 + 既有 `history_event` 列）。

## 2. 当前密码验证路径审查

### 2.1 全部校验点（[源码] 全仓库 grep `verify_password|password_is_usable|dummy_password_hash`）

| 位置 | 代码 | 策略 |
|---|---|---|
| `api/auth.py:202-208`（login，未知用户） | `verify_password(payload.password, dummy_password_hash())` | **等时**：不存在用户也付一次 Argon2 |
| `api/auth.py:205-208`（login，已知用户） | `usable = password_is_usable(...)`；`verify_password(pw, hash if usable else dummy)`；`if not usable or not matched or not user.is_active` | 哨兵账号**永不通过**；停用账号先校验再拒绝 |
| `api/auth.py:339`（`POST /api/auth/password`） | `if not verify_password(payload.current_password, user.password_hash): 400` | **裸校验**：无 `password_is_usable` 守卫、无 dummy 等时、无失败计数 |
| `api/auth.py:428-430`（管理员改他人密码） | `set_password(...)` + `revoke_all_sessions(...)` | **完全不校验口令**（仅凭管理员会话） |
| `api/auth.py:422-427`（管理员改角色 / 停用） | 直接改写 `role` / `is_active` | **完全不校验口令** |
| `api/auth.py:378-404`（管理员创建账号） | `hash_password(payload.password)` | **完全不校验口令** |
| `cli.py:79-123`（运维 CLI） | `hash_password` | 交互式 `getpass`，属操作员路径（不在本方案范围） |

### 2.2 回答："当前是否存在密码验证重复逻辑？是否可以抽象？"

**存在重复，而且是"看起来一样、实际不一样"的重复。** 三处差异：

1. **哨兵账号**（`password_hash == "!"`）：login 显式用 `password_is_usable` 拒绝；`change_password` 依赖 `verify_password` 内部的短路返回 False（`security.py:39`）—— 结果都正确，但**依赖了隐式行为**；
2. **等时性**：login 有（M2 修复的产物），`change_password` 没有 —— 已认证路径上无枚举意义，但**同一件事在两处用两套写法**是后续引入 bug 的温床；
3. **失败后的动作**：login 写 `login_failed` 审计 + 记地址计数 + 返回统一 401；`change_password` 只返回 400。

**可以抽象**，且抽象边界清晰：`security.py` 保持"原语层"（`hash_password` / `verify_password` / `dummy_password_hash`）不动；在 `services/auth.py` 增加**一个**应用层函数：

```
verify_user_password(user: User, password: str) -> bool
    """一次且仅一次 Argon2 校验；哨兵/空哈希账号永不通过。"""
    usable = password_is_usable(user.password_hash)
    matched = verify_password(password, user.password_hash if usable else dummy_password_hash())
    return usable and matched
```

- login 变成：`if not verify_user_password(user, payload.password) or not user.is_active: 拒绝`
- `change_password` 与未来所有敏感操作变成：`if not verify_user_password(user, password): 拒绝`
- 两处的差异**只剩**"拒绝之后做什么"（401+审计+地址计数 vs 400+审计+用户计数），这正是应当保留的差异。

> 注意：这不会削弱 M1/M2 —— 未知用户分支仍单独走 dummy 校验（login 里保留），哨兵/停用的判定顺序也不变。

## 3. 敏感操作识别

### 3.1 现状矩阵

| # | 操作 | 端点 | 当前是否要求口令 | 建议 | 理由 |
|---|---|---|---|---|---|
| 1 | 修改**自己**的密码 | `POST /api/auth/password` | ✅ **已要求**（且成功即撤销全部会话） | 保持，统一到共享校验 | 既有实现即标准做法 |
| 2 | **退出其他设备 / 全部设备** | 待实现（2.7-d） | — | ✅ **必须要求** | 会把其他设备踢下线；是唯一能阻止"持被窃 Cookie 者反过来把用户踹下线"的手段 |
| 3 | 管理员改**他人**密码 | `PATCH /api/users/{id}`（`password`） | ❌ **仅凭会话** | ⚠️ **建议要求**（管理员自己的口令） | 可**接管任意账号**；且改密会撤销受害者全部会话（受害者在用设备上被踢出） |
| 4 | 管理员改**角色** | `PATCH /api/users/{id}`（`role`） | ❌ | ⚠️ **建议要求** | 提权/降权；可把普通用户变管理员（横向 → 纵向） |
| 5 | 管理员**创建账号** | `POST /api/users` | ❌ | ⚠️ **建议要求** | 可创建**新的管理员** = 被窃会话的**持久化后门** |
| 6 | 管理员**停用/启用**账号 | `PATCH /api/users/{id}`（`is_active`） | ❌ | 🟡 可选 | 可逆、影响有限；但与 #4/#5 同属一个端点，一并做更一致 |
| 7 | 管理员改**实例 AI Key / OCR 配置** | `PUT /api/settings` | ❌ | 🟡 可选（独立议题） | 属配置完整性（可把 Key 指向攻击者端点），不直接危及账号 |
| 8 | 手动备份 | `POST /api/settings/backup` | ❌ | ❌ 不需要 | 只读导出、无破坏性；已有管理员门槛 |

### 3.2 未来可能加入的敏感操作（纳入同一策略）

| 操作 | 何时出现 | 归类 |
|---|---|---|
| 删除账号（含数据清理） | Phase 3+（当前无端点） | **必须要求** |
| 修改用户名 | 未计划 | **必须要求**（登录标识变更） |
| 数据导出 / 全量下载 | 未计划 | **必须要求** |

## 4. 失败保护设计（与 Phase 2.6-a 的关系）

### 4.1 资源消耗：**应当复用同一个并发闸门**

- 一次 re-auth = 一次 Argon2id（Phase 2.5 实测 **61–81 ms CPU、64 MiB 内存**；编码参数 `m=65536,t=3,p=4`）。
- 现状：`LoginGate` **只包住 login**（`api/auth.py:197-233`：`gate.acquire()` → `try … finally: gate.release()`）。持被窃会话者可以反复打 `POST /api/auth/password`（或未来的 revoke-all）**绕过登录限流**去消耗 CPU/内存 —— 该端点今天连失败计数都没有（`api/auth.py:336-355`）。
- **建议**：**所有执行密码校验的端点共用同一个 `LoginGate`**。资源上限与"是登录还是二次认证"无关；共享后最坏内存仍是 8 × 64 MiB ≈ 512 MiB（而不是各自 8 → 1 GiB）。
- **取舍（必须写明）**：共享意味着登录洪水会短暂占满槽位，使二次认证也被 429 拒绝（槽位周转 ≈ 70 ms 量级，实际影响很小）。若某天需要隔离，可拆成两个闸门，代价是内存上限翻倍 —— 不建议现在做。

### 4.2 口令预言机：**需要独立的失败预算**

| 维度 | 分析 |
|---|---|
| 威胁 | `POST /api/auth/password` **今天没有任何失败计数**：持被窃会话者可无限次试口令。成功后能**改密码**（接管）与**在用户撤销会话后重新登录**（持久化） |
| 与登录的区别 | login 是**匿名**路径（谁都能试）→ 限流的首要目的是防 DoS；re-auth 是**已认证**路径（必须先偷到会话）→ 首要目的是**限制预言机速率**，DoS 不是主要矛盾 |
| 是否共用计数 | ❌ **不共用**。①语义不同（匿名 vs 已认证）；②共用会让"同一 NAT 出口的登录洪水"锁死合法用户的设置页；③反过来，用户在设置页敲错两次密码就会吃掉自己的登录额度；④登录计数按 **IP** 键，而这里的正确键是**用户**（威胁是"某人持该用户的会话在猜口令"） |
| 独立计数怎么实现 | `services/limiter.py::LoginFailureWindow` **已经按字符串键泛化**（`client: str`），因此**零新类、零 schema**：新建一个实例，键用 `str(user.id)` |
| 键选 user_id 的理由 | 攻击者可能持有该用户的**多条**会话，但键相同 → 无法分散计数；合法用户自己的失误也只影响自己 |
| 是否按"每个操作"分别计数 | ❌ 不按操作分。**一个用户一份预算**更简单，且攻击者无法通过换端点绕过 |
| 成功即清零 | ✅ 与登录一致（`clear(str(user.id))`） |
| 是否会误伤 | 会：见 §4.4 的恢复路径问题 |

### 4.3 用户体验

- 合法用户确实会敲错密码。阈值必须宽松、窗口必须短，且**只影响敏感操作**，不影响登录与日常使用。
- 成功后立即清零（用户一旦输对，之前的手误不算数）。
- 不引入"重新认证后 N 分钟内免密"的 sudo 模式作为**必需**机制：本项目敏感操作极低频（改密、清设备），每次输入口令的摩擦可以接受；sudo 模式需要按会话维护"已验证到何时"的状态（内存或新列），属**过度设计**。若将来敏感操作变多（例如每页都可撤销设备），再评估 —— 见 §5.6。

### 4.4 必须写明的取舍：硬拒绝会短暂封锁"恢复路径"

若采用"失败 N 次 → 429"，则**持被窃会话的攻击者可以故意烧掉预算**，使合法用户在窗口内**无法改密码**（而这正是他驱逐攻击者的手段）。缓解：

1. **窗口取短**（建议 300 秒）——攻击者要持续封锁就必须不断重烧，代价与噪音都很大；
2. **不影响登录**（re-auth 预算独立）——用户在窗口内仍可正常登录、学习、查看设备列表；
3. **运维逃生口仍在**：`python -m app.cli set-password <user>`（操作员持有服务器访问权）；
4. **可观测**：每次失败的 re-auth 都写审计事件（§5.4），"有人在猜你的口令"是明确信号。

被否决的替代方案：**"递增延迟"而非硬拒绝**（Phase 2.5 §4.3 曾为 username 维度建议过）。这里不采用，因为延迟会占住同步端点的线程（anyio 线程池 40 个），把"口令预言机"问题转成"线程占用"问题；而 429 是立即返回、无占用的。代价是上面的恢复路径问题，用"短窗口 + 逃生口 + 审计"消化。

## 5. 推荐设计

### 5.1 验证函数（唯一入口）

```
# services/auth.py（应用层，唯一的口令校验入口）
def verify_user_password(user: User, password: str) -> bool:
    """一次且仅一次 Argon2；哨兵/不可用哈希永不通过。"""
```
- `security.py` 保持原语层不变；`dummy_password_hash()` 仍由它提供（哨兵与不存在用户都要付出同样的计算）。
- login 的**未知用户**分支仍单独 `verify_password(pw, dummy_password_hash())`（那里没有 user 对象，且必须保持等时）。

### 5.2 调用位置（统一守卫）

```
# api/auth.py
def _require_password(session, user, password, *, action: str) -> None:
    """敏感操作的统一入口。
    失败 → 记录 reauth_failed + 记一次用户失败计数 + 400
    预算耗尽 → 429 + Retry-After（不记录新事件，避免放大）
    成功 → 清零该用户计数
    """
```
- **当前调用点**：`POST /api/auth/password`（改造为使用它，行为对用户可见部分不变：错误口令仍是 400）。
- **即将调用点**：`POST /api/auth/sessions/revoke`（2.7-d：`others` / `all`）。
- **建议调用点（需产品确认）**：`PATCH /api/users/{id}`、`POST /api/users`（§3.1 #3–#5）。
- **为什么用普通函数而不是 FastAPI 依赖**：依赖要读请求体就得再声明一份 body 模型，与路由自己的模型重复解析同一份 JSON、产生两个真相来源；而"校验口令"是流程中的一步，不是请求的前置条件。路由显式调用更清晰、也更好测。
- **闸门**：调用点统一在 `login_limiter().gate`（共享）内执行，`finally` 释放（与 login 相同写法）。

### 5.3 失败响应

| 情形 | 响应 | 说明 |
|---|---|---|
| 口令错误 | `400 {"detail": "当前密码不正确"}` | 与今天 `POST /api/auth/password` 完全一致，不新增可区分信息（调用者已认证，无枚举风险） |
| 预算耗尽 | `429 {"detail": "密码校验尝试过于频繁，请稍后再试"}` + `Retry-After: <秒>` | 与 Phase 2.6-a 的 429 **同形状**，但文案区分"登录尝试"与"密码校验尝试"，便于前端给不同提示 |
| 未认证 | `401`（不变） | 由 `CurrentUser` 决定 |
| 账户无可用口令（哨兵） | `400`（同"口令错误"） | 不泄露"该账号未设置密码"（虽然调用者已认证，但保持单一文案更简单） |
| 响应缓存 | 已被 `/api/auth/*` 的 `no-store` 中间件覆盖 | 若未来给 `/api/users` 加二次认证，需要另行覆盖该路径（**注意点**） |

### 5.4 审计事件

| 事件 | 触发 | 字段 | 禁止 |
|---|---|---|---|
| `reauth_failed` | 口令校验失败（每次） | `user_id=<调用者>`, `entity_type="user"`, `entity_id=<用户>`, `payload={"action": "<端点标识>"}` | 绝不含口令、token、`token_hash` |
| （既有动作事件） | 敏感操作成功后 | 在 `user_password_changed` / `session_revoked` 等既有事件上增加 `payload["reauth"] = "password"` | 同上；无需 schema 变更 |

- 预算耗尽（429）**不写新事件**：否则限流本身成了未认证/低代价的写入放大器（虽在已认证路径，仍无必要）。
- `payload["action"]` 取固定枚举字符串（如 `"change_password"`、`"revoke_sessions"`），**不接受客户端输入**，避免把用户数据写进审计。

### 5.5 是否需要 schema

**不需要。** 计数在内存（复用 `LoginFailureWindow`，零新类），审计复用 `history_event` 现有列（`user_id`/`event_type`/`timestamp`/`entity_type`/`entity_id`/`payload`）。

**只有在以下情况才需要 schema（本阶段不实现、也不推荐现在做）**：
- 让"重新认证状态"跨重启保留（sudo 模式）→ 需要按会话/用户的 `reauthenticated_until` 列；
- 让计数跨多 worker 共享 → 需要共享存储或表；
- 记录"失败原因分类"到独立列 → 无必要（`payload` 已足够）。

### 5.6 明确不做的部分

- **不实现 sudo/免密窗口**（见 §4.3）；
- **不把 re-auth 做成全局中间件**（会成为"所有端点都可能弹密码"的黑箱，且与 §5.2 的依赖问题同源）；
- **不引入口令以外的第二因素**（TOTP/邮件/恢复码）：无邮件基础设施、无恢复流程设计，属独立大议题；
- **不做验证码**（Phase 2.5/2.6-a 已明确排除）。

## 6. 实施拆分建议

| 阶段 | 内容 | 关键验收 |
|---|---|---|
| **2.7-d-b** | 抽出 `verify_user_password`；login 与 `change_password` 改用它（**纯重构**，对外行为不变） | 279 用例全绿；M1/M2 的既有断言（四类失败响应一致、时间比 ≈1.0×、每路径只校验一次）不回归；新增断言"哨兵账号也恰好付出一次校验" |
| **2.7-d-c** | re-auth 失败预算（`reauth_failures()` 复用 `LoginFailureWindow`，键 `str(user_id)`）+ `_require_password` + `reauth_failed` 审计 + 共享闸门 | 连续 5 次错误 → 第 6 次 429 且带 `Retry-After`；成功即清零；**不影响登录**（同一账号仍可登录）；不同用户互不影响；限流路径**零数据库写入**；计数有界（键上限） |
| **2.7-d-d** | 实现 `POST /api/auth/sessions/revoke`（`others` / `all`）—— Phase 2.7-a §3.3 的端点，用 `_require_password` 守卫 | `others` 保留当前会话；`all` 连当前一起撤销并清 Cookie；口令错 400；无口令 422；只影响自己；审计事件 |
| **2.7-d-e**（**需你确认后再做**） | 把二次认证扩展到管理员操作（改他人密码 / 改角色 / 建账号 / 停用） | 本轮先不做：这会改变管理员的使用方式（每次多一次输入），是**产品决策**而非纯安全修复 |
| **2.7-d-f** | 前端：可复用的口令确认对话框 + 设置页接线（含 429 文案与 `Retry-After` 倒计时） | 撤销设备/改密走同一组件；429 有明确提示 |

**顺序理由**：先做 b（重构，无行为变化，锁住 M1/M2）→ 再做 c（保护机制本身）→ 最后 d（真正的新能力）。c 在 d 之前完成，意味着 d 一上线就带保护，不存在"先裸奔再补"的窗口。

## 7. 风险

| # | 风险 | 级别 | 说明与缓解 |
|---|---|---|---|
| R1 | **恢复路径被短暂封锁** | 🟡 中 | 攻击者持被窃会话可烧掉 re-auth 预算，使合法用户在窗口内无法改密码。缓解：窗口 300 s；**登录不受影响**；CLI `set-password` 逃生口；每次失败都有审计。**这是"硬拒绝"方案的固有代价**（延迟方案会把问题转成线程占用，已否决） |
| R2 | **管理员体验变更**（若采纳 §3.1 #3–#5） | 🟡 中 | 管理员每次改他人密码/角色/建号都要输口令。属产品决策，**本轮不实施**，先报告 |
| R3 | **共享闸门带来跨端点争用** | 🟢 低 | 登录洪水期间 re-auth 也可能 429（槽位 ≈70 ms 周转）。缓解：需要时可拆闸门（内存上限翻倍） |
| R4 | **重构触及 login 路径** | 🟡 中 | `verify_user_password` 抽取会改动 M1/M2 所在代码。缓解：2.7-d-b 定为**行为不变**的重构，且既有断言（四类失败一致、等时比、spy 计数）必须全绿 |
| R5 | **内存计数重启清零 / 多 worker 减半** | 🟢 低 | 与 Phase 2.5/2.6-a 同一取舍；重启是操作员动作，攻击者无法重置服务；多 worker 部署是已知触发条件 |
| R6 | **审计写入放大** | 🟢 低 | 每次失败 re-auth 写一行（受预算上限约束，最多 5 行/窗口/用户）；429 不写 |
| R7 | **`no-store` 覆盖范围** | 🟢 低 | `/api/auth/*` 已被覆盖；若未来把 re-auth 放到 `/api/users`，需显式处理该路径的缓存头（§5.3 已标注） |
| R8 | **`payload["action"]` 若接受输入会污染审计** | 🟢 低 | 设计上限定为固定枚举字符串，不接受客户端数据 |
