# Phase 2.8 G6 / S-6：`history_event` 保留策略设计审查

状态：**设计提案，未实现、未验收**。本文件不授权在生产库执行清理；G6/T10 仍为未完成。

## 1. 目的与现状证据

目标是在控制 `history_event` 长期增长的同时，保留登录与管理操作的可追溯性，并使 `verify_backup.py` 继续区分获准归档的行和意外丢失的行。此设计只涉及 `history_event`；`review_event`、`article_word_lookup` 等事实表不参与清理。

审查时 HEAD 为 `ba2d2b2`。`backend/app/models.py::HistoryEvent` 有 `id`、`user_id`、`event_type`、`timestamp`、`entity_type`、`entity_id`、`payload`；`timestamp` 由 `utcnow()` 写入。`backend/app/cli.py` 尚无历史清理命令。`tools/verified_db.py` 把 `history_event` 列为 `APPEND_ONLY_TABLES`，按基线冻结的 `identity_columns` 和 rowid 保存逐行 hash；其 `user_id` 不在行身份内，但其余列仍受比较保护。`compare_against_baseline` 只对 `user_session`、`user_lexicon` 容忍丢行，基线 `history_event` 行消失必定失败。`backend/tests/test_verified_db.py` 固定了分类和行容忍集合，并验证 append-only 行丢失会失败。`scripts/check.ps1` 的末步以现有 `data/recovery/baseline.json` 核验运行库；直接删行会让门禁失败。`tools/verify_backup.py --write-baseline` 可以生成新基线，但**不能用重录基线掩盖删除**。

当前事件写入方包括认证的 `login_failed`、`reauth_failed`、`user_login`、`session_revoked`、`session_evicted`、`user_created`、`user_updated`、`user_password_changed`，以及导入、阅读、翻译和 `manual_backup`。未知或旧版本事件也可能存在，因此资格必须使用显式白名单，不能用“非关键事件”这一反向条件。

## 2. 保留边界

| 类别 | 当前已知事件 | 在线保留与清理资格 |
|---|---|---|
| 高频认证与阅读轨迹 | `login_failed`、`reauth_failed`、`user_login`、`article_word_lookup` | 默认在线保留 **365 天**；期满后只可通过本设计的归档和验证流程清理。完整行在归档中长期保留。`article_word_lookup` 的独立事实表不清理。 |
| 权限、账户、设备和数据处置审计 | `user_created`、`user_updated`、`user_password_changed`、`session_revoked`、`session_evicted`、`import_image_removed`、`import_batch_removed`、`import_confirmed`、`manual_backup` | 长期保留在在线库；本 CLI 不提供删除资格。`session_evicted` 目前还是设备被挤下线的唯一原因线索。 |
| 其他阅读与内容变更 | `article_translated`、`article_word_added` | 长期保留在在线库。 |
| 未知事件类型、异常时间戳 | 任意未列入白名单的类型；NULL、无法解析或未来时间 | 不清理；预览列出数量和原因，待单独审查。 |

年龄只按 `history_event.timestamp` 计算，不按 `id`、备份时间或归档文件时间。CLI 在一次预览中固定 `cutoff = UTC now - retention_days`，只选严格早于 cutoff 的行；等于 cutoff 的行保留。SQLite 中由当前 ORM 写入的无时区文本按 UTC 解释；带偏移量的历史值转换到 UTC；解析失败即跳过并报告。建议配置 `VOCAB_HISTORY_EVENT_RETENTION_DAYS`，默认与最小值均为 365，`0` 表示禁用清理而非立即过期；负数和小于 365 的非零值拒绝启动清理。窗口缩短需另立决策，不能通过 CLI 临时参数绕过。上述窗口是本审查的产品建议，实施前须由负责人确认。

## 3. 方案比较与推荐

| 方案 | 工作方式 | 优点 | 代价与风险 |
|---|---|---|---|
| **A. 完整行归档 + 精确凭证 + 定向核验例外（推荐）** | 清理前保存一致性快照、完整行归档和逐行清单；核验器仅对凭证证明的 `history_event` ID 接受缺行，仍逐行验证其他行和全部其他表。 | 不修改项目原始基线；旧备份继续可验；无凭证丢失仍失败；归档可用于恢复与审计。 | CLI、归档格式和核验器必须一起实现；外部凭证与 DB 提交不能跨介质原子化，崩溃时须故障关闭并从清理前备份恢复。 |
| **B. 定期归档后滚动重录基线** | 把过期行导出后，对已删除行的库重新录制 `baseline.json`。 | 代码量较少，现有核验器无需理解归档。 | 新基线不再见到旧行，意外删除可被一并“合法化”；历史基线与旧备份的比较口径混乱。若没有逐行外部凭证，不能满足数据保护要求。**不采用**。 |
| C. 迁移至库内归档表 | 用新表保存完整行，主表删除；核验器跨表比对。 | 单个 SQLite 事务可覆盖移动。 | 主库大小不会随清理下降，仍需改核验器和迁移；不解决 S-6 的磁盘增长。暂不采用。 |

方案 A 的例外不进入 `ROW_TOLERANT_TABLES`，不修改原始基线，也不放宽 `review_event`、`article_word_lookup` 或其他表的现有断言。它是带**具体 ID、原始行内容和可独立复核凭证**的窄例外，不是“允许 `history_event` 缩小”。

## 4. 推荐方案的可执行协议

### 4.1 预览与生成证据

拟新增 `python -m app.cli history-retention preview`，默认只读。输出固定 UTC cutoff、窗口、数据库路径、各事件类型的总数与候选数、最早/最晚候选时间、被保护或时间异常的数量、当前最大 `id`，以及候选集合摘要；不打印含用户名、payload、凭据或 token 的完整行。支持机器可读 JSON 输出到显式指定的测试或运维证据目录。无候选行时直接结束，不创建空的清理凭证。

执行前，使用 SQLite online backup API 创建**唯一名称、拒绝覆盖**的清理前完整备份（含 WAL 中已提交内容），并用当前基线及此前已提交的归档链核验；失败则不继续。不能裸拷贝运行中的 `vocab.db`。从一致性备份生成全量 `history_event` 候选行归档，按 `id` 排序，逐行保存所有原始列、类型和 NULL 值，采用有版本的 UTF-8 JSONL 规范表示；记录每行全列 SHA-256，以及按**现有基线冻结列顺序**计算的行身份 SHA-256；基线之后新增的行则显式记录本次使用的列名与顺序。归档先写临时文件，关闭、重新读取、校验数量/摘要后原子改名；敏感审计数据只保存在受限的运维目录，归档与清理前备份各留一份独立副本。

同一运行的清单至少含：格式版本、运行 ID、操作者、UTC 时间和 cutoff、窗口与事件白名单版本、源库路径与 revision、原始基线 SHA-256、清理前**一致性备份** SHA-256、归档 SHA-256、选中 ID 与逐行双 hash、分类型计数、总数、预览摘要和批准记录标识。运行中库的裸主文件 SHA-256 不是 WAL 感知快照，不能用作这里的内容锚。清单与归档在删除前写定并复制到独立位置；不能只在删除后补造“证据”。哈希用于检测意外损坏，若要抵抗有写权限者伪造清单，需要另加外部只增存储或签名，这是上线清理前的运维风险决定。

SQLite `INTEGER PRIMARY KEY` 可能在删除最大 ID 后复用该 ID。CLI 必须始终留下当前最大 `history_event.id`，即使它已超过保留窗口，并在预览说明跳过原因；核验器遇到归档 ID 与在线行内容不同则失败。未来若改成 `AUTOINCREMENT` 或独立序列，需迁移和单独验收，不能在本任务顺手改 schema。

### 4.2 应用、失败与恢复

拟新增独立的 `history-retention apply --preview-id <id>`，明确显示本次将删的 ID 数和归档位置，要求操作者输入一次运行 ID 确认；无定时自动执行。CLI 先验证 schema revision、原始基线、清理前备份、归档和清单；在 `BEGIN IMMEDIATE` 写事务中重新计算候选集合及每行全列 hash，必须与预览完全一致（包括最高 ID 保留规则），否则回滚并要求重新预览。只用清单中的明确 ID 删除，并检查 SQLite 实际删除数。事务提交后，先用**仅供本次运行的待提交清单**只读核验归档、库完整性、外键及基线加凭证的比较；通过后以原子改名发布 `committed` 凭证，再用公开核验入口重验。公开核验器只接受 `committed` 凭证。不得用 `DELETE WHERE timestamp < ...` 直接执行未固定的集合。

归档/备份创建失败：数据库未改，删去本次不完整临时产物即可。事务内任何断言失败：回滚，保留凭证草案供排查。事务已提交但 `committed` 凭证未发布、归档损坏或后置核验失败：**核验必须失败**，不得通过改基线或补写凭证“修好”；停止进一步清理，先让实例停止写入，再从清理前的 SQLite 完整备份恢复到隔离副本、核验并按事故恢复流程决定恢复生产。运行实例若在清理后继续写入，不能简单用旧备份覆盖新数据；须先封存现状并比较期间新增记录。生产执行应安排维护窗口，避免这一恢复分叉。

### 4.3 核验语义

`verified_db.py` 保持 `history_event` 的 `append_only` 分类与现有基线原样。扩展比较时先核对全部已提交清单、归档 SHA、逐行全列 SHA、唯一 ID、白名单、cutoff 和每次运行的清理前证据；然后构造 `在线行 ∪ 已归档行` 的逻辑历史，同 ID 双份必须内容一致。原始基线中每个 `history_event` rowid 必须在该逻辑集合出现，且其**原始基线行身份 hash**相同；任何不在有效归档凭证中的缺行仍使核验失败。在线存活行仍按原有逻辑比对；其他表一字不改。报告单列 `history_event_archived` 的运行 ID、数量、ID 摘要和归档路径，不把它写成普通 `rows_pruned`。

当目标是清理前的旧备份时，某归档 ID 可能仍在目标库：若内容与归档一致便可核验，不要求其已经删除。若归档缺失、未提交、冲突、篡改或清单所指的前置备份不可核验，则不能给出 `VERIFIED BACKUP`。当前 v1 基线继续作为原始可信锚；不能自动重录、替换或删除它。为覆盖基线后新增又被清理的行，每次运行的清理前完整快照还必须和清理后的逻辑集合逐行比较，并把成功结果接入清单链；否则原始基线看不到这些新增行的意外损失。对当前库或新备份，核验器应验证整条链，而不只验证原始基线中出现过的 ID。

`verify_backup.py` 在不指定额外归档开关时，以及 `scripts/check.ps1` 的末步，都必须自动发现已提交凭证并执行上述严格核验；不存在清理凭证时维持今天的严格行为。不能要求操作者加 `--allow-history-loss` 才让门禁通过，也不能通过“有某个归档文件”就推断获准删除。`--json` 和控制台均应显示归档数量及凭证校验结果。清理后的新备份只有在原始基线、凭证链和归档均通过时，才可称 verified backup；交付与恢复时这些附件必须随备份一起提供。

## 5. 验收边界

1. **pytest 临时库**：建立含全部事件类别、UTC 边界、无效时间和基线前/后行的夹具；覆盖 dry-run 零写入、严格 `< cutoff`、白名单、最高 ID 保留、预览后数据漂移拒绝、归档与备份故障拒绝、事务回滚、提交后清单缺失的故障关闭、ID 复用/冲突、归档损坏、未授权删除仍 FAIL、合法清理 PASS、旧备份 PASS、其他表缺行和改行仍 FAIL。保持现有 `ROW_TOLERANT_TABLES` 等值断言和 `history_event` 分类断言。
2. **`data/staging/` 副本**：从生产库用 SQLite online backup API 建**新的、唯一命名**副本，在该副本上预览、归档、清理、验证、故意删一条非候选行以确认 FAIL，再从清理前备份恢复副本并核验。现存 staging 文件及其被引用证据不覆盖、不清理；所有产物按运行 ID 单独列出。此阶段不得连到 `data/vocab.db` 执行 apply。
3. **完整门禁**：按仓库标准运行 `scripts/check.ps1`，同时核对 `tools/prove_test_isolation.py` 的 `data/` 前后指纹无变化。测试证据放 `test-artifacts/` 或 pytest 临时目录，避免测试本身写入真实 `data/`。门禁还须在没有清理凭证的当前生产库上继续通过。
4. **生产清理**：只有代码评审、上述 pytest 与 staging 验收、恢复演练、归档存储/访问权限及独立副本检查完成，并得到项目负责人对**具体预览报告和运行 ID**的明确批准后，由本机/实例运维负责人在维护窗口通过 CLI 执行。执行前后保存核验报告和完整备份；普通 Web 用户与 API 不提供清理入口。设计评审本身不触发生产清理。

## 6. 对历史证据与现有基线的影响

- `data/recovery/baseline.json`、此前归档的旧基线、0007 verified backup、迁移与事故恢复记录保持原样。清理前备份和归档/清单属于新增的独立运行证据，不回填历史记录。
- 旧备份因仍含待清理行，可继续用原始基线核验；新备份额外依赖归档链。仅复制新 `.db` 而漏掉清单/归档将不能称为 verified backup，这须写入未来的备份与异地交接规程。
- `check.ps1` 不得绕过末步，也不得降低 `verify_backup.py` 的失败条件；实施时只接入默认严格的归档凭证核验。测试隔离证据应继续证明生产 `data/` 未被 pytest 改写。
- G6/S-6 只有在清理 CLI、凭证核验、自动和副本测试、恢复演练及生产执行规程均完成后才能标为完成；本设计提交不改变路线图状态。

## 7. 未决风险与实施顺序

1. **保留窗口决策**：365 天和仅四类可归档事件是保守建议；需确认用户可见阅读轨迹及安全事件的实际查询需求。未经确认保持默认禁用生产 apply。
2. **证据保管**：同一磁盘上的 SHA-256 不能抵抗有写权限者同时篡改数据库与清单；上线前选定独立副本、最小文件权限及是否使用不可变存储/签名。归档含用户名等个人信息，访问、备份与最终销毁策略需单独批准；在该策略确定前长期保留，不自动删除归档。
3. **提交与文件系统的原子性**：SQLite 事务不覆盖外部归档；崩溃窗口按故障关闭和备份恢复处理，须用注入故障测试证明。生产无维护窗口时不得执行。
4. **实现顺序**：先补严格核验器的红灯测试和归档格式；再做只读预览与一致性备份；随后实现固定候选集合的事务清理及恢复故障测试；最后做 staging 全流程、`check.ps1` 与运维规程审查。每阶段仅在前阶段数据保护断言通过后继续。
