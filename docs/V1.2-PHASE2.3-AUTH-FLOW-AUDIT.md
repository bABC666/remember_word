## 3. 发现问题

> 未发现 **Critical** 与 **High**。以下每条均附实测或源码证据；`[实测]` 行号对应 `test-artifacts/phase23-probe-output.txt` 的用例编号。

### Medium

**M1 · 哨兵账号的专属错误文案构成用户名枚举旁路 [实测 A4][源码 `api/auth.py:71-83`]**

- 现状：未知用户、密码错误、账号停用共用 `用户名或密码不正确`；但 `password_hash == "!"`（未初始化密码）的账号走独立分支，返回
  `该账号尚未设置密码，请在服务器上运行 python -m app.cli set-password audit-sentinel`。
- 影响：① 任何人可确认某用户名**存在**；② 得知其尚未初始化；③ 泄露服务器运维命令与用户名。前端 `LoginPage.tsx:26` 会把该文案原样显示给用户，`api.ts:36-37` 也会把 `detail` 透传到 UI。
- 与代码自述矛盾：同文件 `INVALID_CREDENTIALS` 的注释声称"deliberately identical ... cannot be used to enumerate accounts"。
- 既有测试未覆盖：`test_auth.py:109` 只比较"错误密码 vs 不存在"两条文案。

**M2 · 响应时间构成用户名枚举旁路 [实测 G1/G2/G3][源码 `api/auth.py:71-83`]**

- 现状（生产 Argon2 参数，各 8 次取中位数）：未知用户名 **1.2 ms**；已存在用户名 + 错误密码 **43.7 ms**；比值 **≈41×**。
- 根因：用户不存在时立即返回，从不执行哈希；存在时执行一次 Argon2id 校验。
- 影响：攻击者无需响应体差异即可枚举用户名（远程可测，无需认证）。公开部署时风险升高。
- M1+M2 合并即构成完整的账号枚举能力。

### Low

**L1 · 删除 Cookie 与设置 Cookie 的属性不对称 [实测 A6b/A7/C1b][源码 `api/auth.py:54-64, 108`]**
- 设置：`HttpOnly; Max-Age=2592000; Path=/; SameSite=lax`（`Secure` 随环境）。
- 删除（Starlette `delete_cookie` 默认值）：`expires=...; Max-Age=0; Path=/; SameSite=lax` —— **无 `HttpOnly`、无 `Secure`**。
- 名字/Path/SameSite 一致 → 当前删除**有效**（Cookie 身份只由 name+domain+path 决定，且删除响应经 HTTPS 传递）。风险在将来：若改用 `__Host-`/`__Secure-` 前缀，缺少 `Secure` 的删除 Cookie 会被浏览器拒绝，导致"登出后 cookie 仍在"。

**L2 · 会话失效后无法通过 API 清除 Cookie [实测 C2/C3]**
- `logout` 依赖 `CurrentUser` → 已撤销会话或匿名调用得到 `401`，且**不返回**删除 Cookie。
- 影响有限：前端 `auth.tsx:67-75` 无论服务端结果如何都本地清状态；残留 Cookie 只是每次请求多带一个无效 token（服务端恒 401）。

**L3 · 认证响应无缓存控制（且全后端无任何安全响应头）[实测 H1/H2/H3][源码 grep]**
- `/api/auth/me` 200 实测除 `content-type/length/date/server` 外**无任何头**；登录 200 只多一个 `set-cookie`。
- 全后端 grep 无 `Cache-Control` / `no-store` / `Strict-Transport-Security` / `X-Frame-Options` / CSP / 中间件。
- 影响：`/api/auth/me` 含用户与设置数据却未声明 `no-store`，依赖浏览器默认启发式（无 `Last-Modified` 时通常不缓存）；HSTS 缺失使 `Secure` Cookie 的保护依赖部署侧跳转。

**L4 · 登录审计不完整 [实测 A9][源码 `api/auth.py:89-96`]**
- 成功的 `user_login` 事件**不带 `user_id`**（`HistoryEvent` 只传了 `entity_type="user"` 与 `entity_id=user.id`，未传 `user_id`；实测 2 条事件 `user_id` 全为 `NULL`）→ 审计无法按用户检索登录行为（与 `imports.py`/`reading.py` 的写法不一致）。
- **失败登录完全不写事件**（`auth.py:71-83` 无失败分支）→ 密码爆破无任何痕迹。
- 注：限流/锁定按本阶段要求**不处理**，此处仅记录缺口。

**L5 · 会话无上限、无轮换、无管理入口 [实测 A8/D3b]**
- 同一用户可并存多条有效会话（实测曾同时存在 6 条未撤销行）；无接口列出/撤销单个会话，也没有"登出其他设备"。账号泄露时无法从界面踢出（只能改密，而改密会撤销全部会话）。

### 已确认正确、无需改动的部分（防止后续误改）

1. **统一 401**：匿名/撤销/绝对过期/闲置/停用五种状态的响应体与 `WWW-Authenticate` 完全一致（B7/B7b），不泄露会话状态。
2. **token 只存 `sha256`**，明文仅存在于 HttpOnly Cookie（A6f/A6g、`test_auth.py:141`）。
3. **Cookie 属性**：`HttpOnly` ✓、`SameSite=lax` ✓、`Path=/` ✓、`Max-Age=30d` ✓、`Secure` 由 `VOCAB_COOKIE_SECURE` 控制（实测置 true 时出现）✓、**无 `Domain`（host-only）** ✓。
4. **Cookie 名单一常量**（Phase 2.2 已修）：应用代码内字面量仅 `services/auth.py:14` 一处，读取/写入/删除三处均引用 `COOKIE_NAME`（§4 证据）。
5. **无 session fixation**：登录总是签发新随机 token，且 Cookie 只有能匹配库中 `token_hash` 时才有效。
6. **前端不落任何凭据**：无 `document.cookie`、无 localStorage/sessionStorage 存储（`auth.test.tsx:272`）。
7. **闲置超时端到端生效**（Phase 2.2）：有效请求写 `last_seen_at`，闲置 7 天后 401（B2b/B5）。
