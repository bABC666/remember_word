### 迁移编号

`backend/alembic/versions/` 实测为 `0001`–`0007`，因此**实施时下一个可用编号是 `0008`**，即 `0008_public_lexicon_import`。这与设计 §4.1 的裁定一致：编号不写进文档，实施时从目录取 `max + 1`；`revoke_reason` 与 Phase 5 T7 顺延。

新增 **7 个外键**（`public_import_run` 2、`public_import_run_source` 2、`entry_source_evidence` 3），所以迁移到 head 后的物理外键总数从 **26 → 33**。`backend/tests/test_downgrade_guard.py` 的断言随之更新并写明了理由；该测试同时验证 `downgrade` 到 `0006` 后仍回到 **17**，这才是"重建精确"的那一半。

### 对设计稿的两处有意偏离

1. **`entry_source_evidence.lexicon_entry_id` 由 `CASCADE` 改为 `ON DELETE SET NULL`**：证据是审计记录，删词条不该抹掉它；`normalized_word` 保留了词身份。与 migration 0007 自己的删改语义一致。
2. **证据唯一键由 `evidence_sha256` 改为 `(evidence_sha256, import_run_id)`**：原设计让"重新裁定"只能二选一——做不到，或改写历史。加运行维后：同一运行内一条证据仍只记一次；跨运行裁定相同则跳过不写，裁定**不同**则**追加新行**，旧行一个字节不动。

## 2. 契约（都有测试固定）

| 契约 | 行为 |
|---|---|
| 重试幂等 | 同一 `plan_sha256` 再次确认 → 返回 `already_applied` 与原结果，**不写任何新内容**；该判断在重新读取来源文件**之前**，所以文件事后被改动/删除也不影响重试结果 |
| 同文件同映射 | 已入库的证据不再重复写入；`source_artifact` 按 `(file_sha256, mapping_sha256, role)` 复用，不按文件名重复建档 |
| 库内同词 | 目标库已有同 `normalized_word` → 记为 `already_in_lexicon` 冲突、计入 `entries_matched`，**既有行一个字段都不改**；且不为它写证据（没有发生采纳） |
| 文件变化拒绝 | 重新读取每个来源，比对字节 SHA-256 与映射指纹，再按 `(line, field)` 逐条比对计划里的原值；任一不符 → 拒绝，不"适应"新内容 |
| 计划完整性 | 摘要不符（被编辑过）或 `confirmation_ready` 非真 → 拒绝 |
| 权限 | 非管理员 / 已停用账号 → 拒绝；CLI 还要求管理员**本人当前口令**（`getpass`，绝不进 argv） |
| 事务原子性 | 写事务中途失败 → **整体回滚**；失败报告在事务外写入，独占创建、不覆盖既有报告 |
| 不可变历史 | 确认路径**不发出任何 `UPDATE`/`DELETE`**（`lexicon_entry` 不更新、证据与来源不更新不删除）；重新裁定追加新行 |
| 不写学习状态 | 不创建 `UserWordState`、不创建 `ReviewEvent` |
| 不写缓存列 | 不更新 `lexicon.entry_count`；不写 `default_anchor`、不写 `frequency_*` |

### 过程中修掉的三个真实问题

1. **静态守卫抓到我自己引入的 BOM。** 我用 PowerShell 重写 `test_public_lexicon_plan.py` 时写入了 UTF-8 BOM，`test_static_guards.py` 的三项用 `ast.parse` 解析源码因而报 `invalid non-printable character U+FEFF`。已去掉 BOM，并把该文件恢复为无 BOM 的 UTF-8。**这是安全资产按预期工作的例子，不是放宽它们。**
2. **CLI 的两个 `args.report` 写成了不存在的属性**（`--report` 的 `dest` 是 `report_path`），导致拒绝路径在写失败报告时抛 `AttributeError`、掩盖了原本的 `ConfirmRefused`。已修，两个 CLI 拒绝路径现在都正确写报告。
