## 1. 项目定位

### 1.1 一句话定位

**拾词不是传统背单词软件。**

传统背单词软件的核心循环是「给出中文释义 → 用户记忆 → 测试是否记得释义」，学习对象是**释义文本本身**。拾词的核心假设不同：**词义不是被记住的标准答案，而是在多次真实语境中逐渐长出来的东西**。因此系统给出的 anchor 只是**提取线索**，不是需要背诵的释义。

### 1.2 核心学习模型（不可偏离）

```
英文词形（拼写 / 发音）
      ↓
   anchor
      ↓
  主动提取
      ↓
 阅读再次遇见
      ↓
  语义丰满
```

| 环节 | 含义 | 系统里的对应物 |
|---|---|---|
| **英文词形** | 学习的起点是词本身，不是释义句 | `lexicon_entry.word` / `normalized_word` |
| **anchor** | 一个够用的提取线索：短、具体、能在脑中触发那个意思 | `lexicon_entry.default_anchor`（词库侧默认） / `user_word_state.anchor_override`（个人覆盖） |
| **主动提取** | 合上释义，凭线索自己把意思拉出来；评分记录真实表现 | 学习页 1/2/3 评分 → 每次写一条 `review_event` |
| **阅读再次遇见** | 在 AI 生成的真实语境文章中再次遇到同一个词，验证线索是否可用 | `article` / `article_word_exposure` / 阅读后测试 |
| **语义丰满** | 用完整中文释义校正、扩展、修正锚点；词义随遇见次数变厚 | `source_meanings` / `source_raw` / `semantic_note` / 点词解释 / 全文翻译 |

**关键推论**：学习闭环的终点是**完整释义**，不是 anchor。系统必须始终能在任何时刻把用户带回完整的中文释义原文。

### 1.3 anchor 的定位（硬约束）

> **anchor 不替代完整释义。**
> - anchor 是**线索**，完整中文释义是**内容**；两者不可互换，也不可互相替代。
> - 完整中文释义（`source_meanings`、`source_raw`、原书 OCR 文本、逐图 OCR JSON）**永久保留**，永远可查、可回到。
> - anchor 是 **AI 生成物**，因此可重生成、可被用户覆盖（见 §6）；释义是 **Source 数据**，AI 永远不得覆盖。
> - 任何「只有 anchor、无法回到完整释义」的流程或界面，都视为**架构缺陷**，必须修复。

## 2. 产品形态

### 2.1 演进方向（最终形态已确定）

| 形态 | 定位 |
|---|---|
| **V1.0 – V1.2（现状）** | **Windows 单机工具**：以 `127.0.0.1:8000` 在本机浏览器使用；V1.2 已加入账号、会话与多用户能力，但仍只监听回环地址 |
| **目标形态** | **Cloud + Web + PWA + Multi-user**：Caddy + HTTPS 的公网服务，多个用户共用一套实例，前端以 PWA 形式安装到手机主屏 |

转向的技术含义：**从「一个进程 + 一个本机浏览器」变成「一个对外可访问的服务 + 两种使用终端」**。数据仍然只落在一个 SQLite 数据库里，仍然由自己掌控（不做多租户 SaaS 拆分）。

### 2.2 双终端分工（产品形态的核心约束）

| 终端 | 角色 | 应该承担的职责 |
|---|---|---|
| **手机** | **学习终端** | 一次一词的主动提取与评分、阅读生成后的阅读与测试、点词解释、查看完整释义。场景是碎片时间、单手操作、可能网络不稳 |
| **电脑** | **管理终端** | 单词书图片导入、OCR、人工校对、词库管理、私人词库组织、设置、账号与登录设备管理、备份 |

对架构的推论（后续所有前端工作都必须满足）：

1. 学习与阅读路径**必须能在手机分辨率下完成**，不能依赖宽屏才可见的面板（现存 ≤900px 隐藏单词详情面板等缺陷属已知未修项）。
2. 导入、校对、批量管理等重操作**允许只在管理终端可用**（宽屏）。
3. 因此 **PWA（§8 Phase 3）不是"打包壳"**，而是"学习终端真正可用"的交付形式；只做 manifest 而移动端流程不可用，不算完成。
4. 同一份代码服务两个终端：**不做两套前端**、不做单独的管理后台工程。

### 2.3 形态层面不变的约束

1. **单一实例、单一数据库**：一个部署服务一批用户，共享同一份公共词库内容（§4），学习状态各自独立（§5）。
2. **数据自主**：数据落在自己掌控的服务器与数据库中；不引入托管型数据库或第三方数据平台。
3. **账号由管理员创建**：不开放注册、不接 OAuth（见 §5.4、§9）。

## 3. 技术架构

### 3.1 技术栈（当前与目标形态一致）

| 层 | 选型 | 说明 |
|---|---|---|
| **Frontend** | **React 19 + Vite + TypeScript** | React Router、TanStack Query、Lucide、自定义 CSS；测试为 Vitest + Testing Library |
| **Backend** | **FastAPI**（Python） | SQLAlchemy 2、Pydantic v2、Alembic、httpx；口令哈希 pwdlib(Argon2id) |
| **Database** | **SQLite（WAL）** | `data/vocab.db` 是**唯一事实来源**；`busy_timeout` 已设；WAL 下仍是**单写者** |
| **AI** | **DeepSeek API** | OpenAI 兼容接口，默认模型名 `deepseek-flash`；Key 为实例级配置，只回掩码 |
| **Deployment** | **Caddy + HTTPS，FastAPI 只监听 localhost** | Caddy 终止 TLS、提供静态资源并反向代理到 `127.0.0.1:8000` 的 FastAPI |

### 3.2 部署形态

```
                 Internet (HTTPS)
                        │
                 ┌──────▼──────┐
                 │    Caddy    │  TLS 终止 / 静态资源 / 反向代理
                 └──────┬──────┘
                        │  127.0.0.1:8000（仅回环，不对外暴露）
                 ┌──────▼──────┐
                 │   FastAPI   │  API + 业务逻辑（单进程 / 单 worker）
                 └──────┬──────┘
                        │
                 ┌──────▼──────┐
                 │   SQLite    │  data/vocab.db（WAL，唯一事实来源）
                 └─────────────┘
```

当前（V1.2）形态是上图去掉 Caddy 的退化版本：FastAPI 同时提供 API 与 `frontend/dist`，只监听 `127.0.0.1:8000`。

**部署目标（用户决策快照，非当前运行事实）**：阿里云 ECS `ecs.e-c1m1.large`、2 vCPU / 2 GiB、40 GB ESSD Entry、1 Mbps 公网带宽、Alibaba Cloud Linux 3.2104 LTS 64 位、华北 1；预期约 2 位用户。实际服务器、域名、备案与资源余量在 Phase 4 上线前核实。该资源选择以**服务器不运行 OCR、不运行本地 LLM、保持单 worker**为前提；电子词库由 §3.6 的导入交付链路进入 SQLite。

### 3.3 每层的架构含义（后续改动不得违反）

1. **Caddy 是唯一对外入口**：TLS、HTTPS 跳转、静态资源与预压缩由它负责。**FastAPI 不得直接监听公网地址**。
2. **前端与 API 同源**：不引入 CORS；前端请求保持 `credentials:'same-origin'`；跨站写请求默认不带 Cookie。CSRF 防御为**三层且互不依赖**：Cookie 的 `SameSite=Lax`、请求体只接受 `application/json`（FastAPI `strict_content_type` 默认）、**写请求同源校验**（`backend/app/csrf.py` + `main.py` 中间件：对所有非安全方法比对 `Origin`/`Referer` 与 `Host` 的 host:port，缺失即 403）。因此**新增写端点不需要额外的防 CSRF 处理**；反之，**放宽其中任何一层都必须先修改本文件**——例如为端点引入表单体、把 Cookie 改为 `SameSite=None`、或开启 `VOCAB_CSRF_ALLOW_MISSING_ORIGIN`。设计细节与边界见 `docs/V1.2-PHASE2.8-B-CSRF-DESIGN.md`。
3. **HTTPS 下必须启用 `VOCAB_COOKIE_SECURE=true`**；`Secure` 与 HTTPS 必须同时成立，配错会导致登不上或弱化安全。
4. **反向代理后必须正确传递客户端 IP**：`uvicorn --proxy-headers --forwarded-allow-ips <代理地址>`。否则所有用户共用一个限流计数桶（`PROJECT_HANDOFF.md` §9.4）。
5. **SQLite 是唯一事实来源**，且 WAL 下只有单写者 → **uvicorn 单 worker**。多 worker 会让内存限流与并发闸门各持一份计数（等效阈值×worker 数），属于当前**明令禁止**的架构变更。
6. **静态资源在目标形态由 Caddy 托管**（`frontend/dist`），FastAPI 不再承担静态托管职责；两者不得同时成为权威来源。
7. **AI 调用不落地本地模型**，且**不得跨写事务持有**（§6.3 第 5 条）。

### 3.4 当前阶段明确不使用的技术（有意识的排除）

| 不使用 | 排除理由（一句话） |
|---|---|
| **PostgreSQL** | SQLite 单机单写者已覆盖当前规模；换库会替换掉整套已验证的迁移、备份与三级数据库流程，而收益只在多实例/高并发——当前瓶颈不是吞吐。详见 §9 |
| **Redis** | 唯一需要跨进程共享的状态是限流计数，而单 worker 不需要；内存计数无 schema、重启清零，取舍可接受。详见 §9 |
| **Docker 集群 / 容器编排** | 单实例单进程，编排只增加运维面与故障面。详见 §9 |
| **本地 LLM** | DeepSeek API 已满足生成需求；本地模型带来显存/内存、模型分发与升级成本，且与「服务器只需 SQLite + 一个 Python 进程」的简洁形态冲突 |
| **OCR 服务** | PaddleOCR 是**本地能力**而非服务（§3.5）；云端不提供 OCR 端点 |

> **规则**：引入上表任何一项，都属于架构级变更——必须先修改本文件并说明触发条件已满足，再动代码。

### 3.5 OCR 的架构位置

- PaddleOCR/PaddlePaddle 是**本地能力**，用于电脑（管理终端）侧的图片导入流程，不属于服务化组件。
- 云端部署时以 **`VOCAB_ENABLE_OCR=false`** 关闭；本地图片 OCR 流程仍可在本地实例使用。云端管理终端通过 §3.6 的电子词库导入流程提供词条，**不能假设浏览器里的管理页面会在用户电脑上运行 PaddleOCR**。
- `OCRProvider.extract(path) -> OCRDocument` 是稳定接口：替换 provider 不需要改变上层流程。

### 3.6 云端词条来源与外部公共词库（待实现）

**产品决策**：云端关闭 OCR 后，以来源可核验的**外部电子词库**作为公共词库的主要初始数据源；手机继续以学习、复习和阅读为主，电脑管理终端负责词库导入与校对。已有 OCR 代码、历史数据和本地图片导入能力保留，不因云端停用而删除。

外部词库导入的目标关系是 `Lexicon(owner_user_id=NULL, visibility=public)` → `LexiconEntry`。导入**不得**直接写旧 `word` 表、`user_word_state` 或 `review_event`，也不得把“给现有词条补 `frequency_*`”当作建立词库。多个用户共享公共词条内容，通过各自的 `UserLexicon` 启用词库；个人学习状态始终隔离。

**Source 与确认边界**：导入前须记录资料名称、版本、授权/使用范围及原始文件指纹；保留原始词形与完整释义，映射为可检查的候选词条。字段映射、词形规范化、去重、冲突和错误行应先产生预览/报告，由管理员确认后才写入公共 `LexiconEntry`。AI 可建议 anchor 或解释，不能覆盖原始释义，也不能编造词频。具体文件格式、来源、导入入口与幂等规则须在实施前的独立设计中定稿。

**部署依赖**：Phase 4 公网交付前，必须用一份授权与格式均已确认的真实外部词库，在隔离副本验证导入、重复导入、错误行、人工确认、双用户共享内容与学习状态隔离；再按发布流程将公共词库交付到服务器。单纯设置 `VOCAB_ENABLE_OCR=false` 只解决运行依赖，**不等于**解决词条来源。任务与验收见 `PROJECT_ROADMAP.md` Phase 2.9。

## 4. 核心数据模型原则

### 4.1 两层结构（必须始终区分）

| 层 | 表 | 语义 | 归属 |
|---|---|---|---|
| **词库内容层** | **`Lexicon`、`LexiconEntry`** | 词的**内容**：词形、音标、词性、完整中文释义（`source_meanings` / `source_raw`）、词库侧默认 anchor、semantic note、频率数据 | 共享。`owner_user_id IS NULL` 为**系统公共词库**；`visibility` 决定是否 public |
| **学习状态层** | **`UserWordState`、`ReviewEvent`** | 某个人对某个词的**学习过程**：状态、排期、成功/失败计数、锚点覆盖、笔记，以及每次复习的事实 | **私有**，属于单个用户 |

### 4.2 关系链（单向、顺流）

```
Lexicon             一个词库（系统公共 或 用户私有）
   │  1:N
   ▼
LexiconEntry        词条内容（内容层，唯一约束：lexicon_id + normalized_word）
   │  1:N
   ▼
UserWordState       某用户对该词条的学习状态（唯一约束：user_id + lexicon_entry_id）
   │  1:N
   ▼
ReviewEvent         每次复习的事实记录（append-only）
```

桥接关系：`UserLexicon`（`user_lexicon`）是**用户与词库的启用关系**（含 per-lexicon 每日新词节奏）——用户只能「启用」词库，不能改写词库内容。

### 4.3 硬约束

1. **公共词库数据与用户学习状态必须分离**：
   - 同一份公共词库被多个用户使用时，**内容是同一份**，每个人的进度**各自独立**；
   - 修改词库内容**不得**影响任何人的学习状态；
   - 删除用户**不得**损害公共词库；删除含学习记录的词库会被 **409** 拒绝（Phase 2.1 守卫）。
2. **内容层不存任何人的学习状态**；学习状态层**不存词义内容**。`user_word_state.anchor_override` 是「用户对 anchor 的个人覆盖」，属于**学习状态**，为空时回退 `lexicon_entry.default_anchor`。
3. **复习事实只增不改**：每次复习必须写一条 `review_event`。`recall_success`、`recall_fail`、`status`、`next_review_at`、`context_exposure` 等都只是**可由事件重算的缓存**。
4. **Schema 变化必须新增 Alembic migration**：永远不能要求用户删库重建；migration 链必须保持线性（当前 `0001 → … → 0007`，唯一 head）。
5. **学习状态的锚点是 `lexicon_entry_id`**；`legacy_word_id` 与 `word` 表是 V1.1 的**迁移桥／退场路径**，新功能不得依赖它们。
6. **未确认的内容不进词库**：`import_candidate` 未经人工确认，绝不能自动成为 `lexicon_entry`。

### 4.4 关键字段归属速查

| 数据 | 表 / 字段 | 谁能写 |
|---|---|---|
| 完整中文释义 | `lexicon_entry.source_meanings` / `source_raw` | 导入 + 人工确认（**AI 不可写**） |
| 逐图 OCR 原文 / 原始图片 | `import_image` / `data/uploads/` | OCR 流程（**AI 不可写**） |
| 词库侧默认 anchor | `lexicon_entry.default_anchor` | AI 生成 + 人工确认 |
| 个人 anchor 覆盖 | `user_word_state.anchor_override` | 用户本人 |
| 学习排期与计数 | `user_word_state.*` | 用户的学习动作（评分、阅读测试） |
| 复习事实 | `review_event` | 用户的学习动作（append-only） |
| 词频数据 | `lexicon_entry.frequency_rank / frequency_count / frequency_source` | **只能来自导入的外部词频资料**（AI 不得编造） |

### 4.5 数据库安全约束（2026-09-22 事故后确立，永久生效）

**三级数据库环境（强制）**：

| 级别 | 位置 | 用途 | 规则 |
|---|---|---|---|
| **Level 1** | pytest 临时目录 | 单元 / API / migration 测试 | 只允许存在于 pytest 临时目录 |
| **Level 2** | `data/staging/*.db` | 用**真实数据内容**演练迁移与多用户验收 | 唯一允许拿真实数据做演练的地方；可随时删除重建；**不是生产** |
| **Level 3** | `data/vocab.db` | **生产** | 开发期间**禁止迁移、禁止写入** |

**永久生效的安全规则**（全部有代码或工具兜底）：

1. 测试进程**不得**触碰真实 `data/`（`backend/app/testing_guards.py` fail-fast）。
2. 测试夹具中**禁止**出现 `drop_all`（`tests/test_static_guards.py` 静态拦截）。
3. 破坏性操作只允许发生在带测试标识的临时目录或 `data/staging/` 副本内。
4. Alembic 测试必须在子进程里跑并显式传 `-x db_url=`，事后校验真正被迁移的文件。
5. 只有通过 `tools/verify_backup.py` 全部校验的备份，才可称为 **verified backup**。
6. 应用启动校验数据库 revision 与代码 head 一致，不一致**直接拒绝启动**（失败关闭）。
7. `alembic downgrade` 只允许对一次性副本执行。

规则背后的原因：V1.2 Phase 1 期间，测试夹具对应用模块级 engine 执行了 `Base.metadata.drop_all(engine)`，而该 engine 绑定到了真实数据库，导致 `data/vocab.db` 全部业务表被删除并造成**永久性数据丢失**。此约束不接受任何"临时方便"的例外。

## 5. 多用户设计原则

### 5.1 唯一归属来源：`current_user`

1. **所有私人数据的归属只来自服务器端会话**——`backend/app/api/deps.py` 的 **`CurrentSession` / `CurrentUser` / `AdminUser`** 是归属判定的**唯一入口**。
2. **禁止前端传 `user_id`**：任何端点都**不得**接受客户端提供的 `user_id` 来决定数据归属。需要"某个用户"时，一律从会话取。
3. 私有数据访问必须走 **owner-scoped 入口**（`backend/app/services/userdata.py`）：资源不属于调用者时**一律 404**（不泄露存在性），只有能力缺失才 403。
4. 未登录访问受保护端点 → **401**（响应体一致，不透露会话状态）。

### 5.2 必须隔离的数据（逐项清单）

| 数据 | 表 / 位置 | 隔离要求 |
|---|---|---|
| **学习状态** | `user_word_state` | 按 `user_id` 隔离；他人词条的状态不可读不可写 |
| **文章** | `article`（及 `article_word_exposure`、`article_word_lookup`） | 按 owner 隔离；他人文章 id 一律 404 |
| **复习历史** | `review_event`（及用户可见的 `history_event`） | 按 `user_id` 隔离；不得泄露他人复习轨迹 |
| **设置** | `user_settings`（每用户一行）；`app_setting` 为实例级 | 用户设置互不可见；实例级设置（如 DeepSeek Key）仅管理员 |
| **私人词库** | `lexicon.owner_user_id` | 私人词库仅 owner 可见可用；系统公共词库（`owner_user_id IS NULL`）对普通用户**只读** |
| 导入批次与候选 | `import_batch` / `import_candidate` / `data/uploads/` | 按 owner 隔离 |
| 会话 | `user_session` | 仅本人；列表**绝不返回 token 或 `token_hash`** |
| 备份与实例运维 | `data/backups/` 等 | 实例级，仅管理员 |

### 5.3 隔离的三条硬规则（新增端点必须同时满足）

1. **归属只来自会话**——不接受客户端 `user_id`；
2. **越权与不存在返回同一个 404**——不泄露资源存在性；
3. **公共词库内容不可被普通用户改写**——内容修改属于导入/人工确认流程（§4.1）。

### 5.4 多用户的边界（有意保留的限制）

- **不开放注册、不接 OAuth / 第三方登录**：账号由管理员或 CLI 创建（这是有意的，见 §9）。
- **公共词库 v1 不提供"用户贡献 / 共享编辑"**：公共词库的内容治理属 §8 Phase 2 的范围。
- **认证不变量**（改动认证相关代码必须保持）：明文口令永不落库（只有 Argon2id 哈希）；会话 token 只存 SHA-256，明文仅在 HttpOnly Cookie；失败登录/敏感操作的审计与响应**不得**包含口令、token 或 `token_hash`。
- **S-1 已完成**：`POST /api/users` 与 `PATCH /api/users/{id}` 的每次调用均要求管理员输入自己的当前口令，包括空更新；前端尚无管理员用户管理入口。逐次二次认证的契约与边界见 `docs/V1.2-PHASE2.8-A-ADMIN-REAUTH-DESIGN.md`。

## 6. AI 原则

### 6.1 AI 只能生成什么

| AI 生成物 | 说明 |
|---|---|
| **anchor** | 提取线索（词库侧默认 anchor、个人 anchor 的候选值） |
| **文章** | 阅读材料；`actual_used_words` 必须由后端校验，不能只信模型自述 |
| **解释** | 点词解释、全文翻译、semantic note 等面向理解的补充 |
| **辅助数据** | 导入结构化候选值（`import_candidate`）、判断辅助（如 `possible_issue` 提示） |

### 6.2 AI 绝对不能覆盖什么

| 对象 | 谁能写 | AI 的角色 |
|---|---|---|
| **原始词义**（`source_meanings` / `source_raw`） | 导入 + 人工确认 | ❌ 只读；可**建议**，不可写入 |
| **OCR 原文**（逐图 OCR JSON、批次 OCR 文本、原始图片） | OCR 流程 | ❌ 只读 |
| **用户确认过的数据**（已确认的词条内容、用户的学习状态、笔记、anchor 覆盖） | 用户 / 人工确认流程 | ❌ 只读，不得自动改写 |
| 词频数据（`frequency_*`） | 外部词频资料导入 | ❌ **不得依据常识编造词频排名** |
| 学习状态与复习历史 | 用户的学习动作 | ❌ AI 不得写入 |

### 6.3 落地规则

1. **AI 输出默认是候选值**：`import_candidate` 未经人工确认，绝不能自动进入词库。
2. **AI 生成物必须可重生成、可丢弃**：它们不参与"原始数据"的定义，因此可以被覆盖或删除。
3. **用户的修改优先于 AI**：用户确认过的字段不再被 AI 自动改写。
4. **AI 失败不得损坏数据**：AI 调用失败要保留失败现场（失败批次保留），不能留下半成品数据。
5. **AI 调用不得跨写事务持有**：SQLite 在 WAL 下仍是单写者，长事务会阻塞其他用户；网络调用不得包在写事务里。
6. **AI 不得写 `review_event`**：复习事件的唯一写入者是用户的学习动作（评分、阅读后测试）。

## 9. 不做什么

> 这份清单是**架构约束**，不是待办：下面每一条都写明了「为什么不做」与「什么条件下才重新评估」。要引入其中任何一项，**必须先修改本文件**。

| 暂不 | 原因 | 重新评估的触发条件 |
|---|---|---|
| **PostgreSQL** | SQLite 单机单写者已覆盖当前规模（单实例、单 worker、单用户量级、19 个词条量级的生产数据）；换库要连带替换 Alembic 流程、备份/校验工具链、三级数据库环境与启动期 revision 校验——这些是**事故后花代价建立起来的**安全资产。收益只在多实例/写入并发瓶颈，而当前瓶颈是产品形态（手机可用、公网可访问）与学习闭环质量，**不是吞吐** | 出现真实的多实例部署或写并发瓶颈，且限流共享问题已解决（§3.3 第 5 条） |
| **Redis** | 唯一需要跨进程共享的状态是限流计数（登录失败窗口、二次认证预算、并发闸门），而**单 worker 下内存计数就是够的**：无 schema、无运维、重启清零（可接受）。引入 Redis 会新增一个必须备份/监控/容错的组件，换取一个当前不存在的需求 | 真正启用多 worker 或横向扩展时，作为共享计数的载体一并评估 |
| **原生 APP（iOS / Android）** | 双终端分工（§2.2）已由 Web + PWA 覆盖：手机只需学习终端能力，而 PWA 可安装到主屏。原生意味着两套代码、两套发布流程、商店审核与版本分裂，换来的系统级能力（后台同步、离线写队列）**恰恰是本项目明确不需要的**（离线写会破坏"每次复习必须留痕"与单一事实来源） | 出现必须在系统级后台运行的硬需求（当前不存在） |
| **社交** | 学习数据是**私人的**（§5.2 全部隔离），社交会把产品从"工具"推向"内容平台"，引入内容审核、隐私合规、举报与滥用治理成本，且**不服务于 §1 的核心学习模型** | 产品定位被明确改变时（需先修改本文件 §1） |
| **排行榜** | 排行榜把注意力从「我是否真的把词义提取出来了」转向「我与他人比较」，与 §1.2 的核心学习模型**直接冲突**；同时会诱导刷量式行为，污染复习事实（§4.3 第 3 条），使学习数据不再可信 | 不做（除非 §1 的学习模型被重新定义） |
| **复杂 SaaS** | 不做多租户、订阅计费、组织/团队、权限矩阵、用户自注册。产品定位是「**数据自主、自己掌控的单一实例**」（§2.3），账号由管理员/CLI 创建即可满足；SaaS 化会重塑 §4 的数据分层与 §5 的隔离模型，并牺牲数据自主这一核心承诺 | 明确要做对外商业化运营时（属于产品战略变更，需先改本文件 §1/§2） |

**同类排除项**（已在 §3.4 声明，此处一并归档）：**多 worker 横向扩展**、**OCR 服务化**、**本地 LLM**、**Docker 集群**。以及**开放注册 / OAuth / 第三方登录**、**离线写入队列与后台同步**（PWA 只缓存静态资源，§9 原生 APP 一行同理）、**用 AI 编造词频排名**（§6.2）。

## 附录 A：改动前的架构自检清单

动手前逐条确认；任何一条答不上来，先停下来读对应章节。

1. 这次改动是否触碰 Source（`source_*` / OCR 原文 / 原始图片）？→ §6.2，AI 不得写入。
2. 是否新增/修改了用户私有数据？→ §5.1：归属必须来自 `current_user`，**不接受前端传 `user_id`**。
3. 是否把学习状态写进了词库内容层（或反之）？→ §4.3 第 1、2 条。
4. 是否绕过了 `review_event` 直接改累计数字，或修改/删除了历史事件？→ §4.3 第 3 条。
5. 是否改了 schema 却没有新增 Alembic migration？→ §4.3 第 4 条；并遵守 §4.5 三级数据库环境。
6. 是否新增了对外端点却没有考虑越权/不存在统一 404？→ §5.3。
7. 是否引入了 §3.4 / §9 中排除的组件（PostgreSQL、Redis、容器编排、本地 LLM、OCR 服务、多 worker）？→ 先修改本文件。
8. 改动是否让**手机上的学习路径**更差，或把学习/阅读变成只有宽屏可用？→ §2.2。
9. 是否让"从 anchor 回到完整中文释义"变得更难？→ §1.3（anchor 不替代完整释义）。
10. AI 调用是否被包进了写事务，或 AI 失败可能留下半成品数据？→ §6.3 第 4、5 条。

## 附录 B：本文件的维护规则

**必须更新本文件的变更**：

1. 引入或移除 §3.4 / §9 中的任何技术组件；
2. 改变产品形态（§2）、终端分工、目标形态；
3. 改变数据模型分层（§4.1 的两层结构、§4.2 的关系链）；
4. 改变 AI 的写权限边界（§6.1 / §6.2）；
5. 改变归属判定方式（§5.1）；
6. 新增/重排 §8 的阶段划分；
7. 出现新的、必须长期生效的安全约束（参照 §4.5 的写法：规则 + 兜底手段 + 原因）。

**不必更新本文件的变更**：任务拆分、进度、提交记录、测试数量、数据库行数——这些属于 `PROJECT_ROADMAP.md` / `PROJECT_HANDOFF.md`。§7 只是快照，更新它不构成架构变更。

**更新方式**：修改时保留"基线（分支 / HEAD / revision）"头部信息与生效日期；删除约束时必须写明**为什么原约束不再成立**，而不是静默移除。
