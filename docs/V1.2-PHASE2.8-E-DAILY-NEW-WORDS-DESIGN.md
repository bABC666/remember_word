## 1. 问题与现状实测

P-5 登记的是功能正确性缺陷，不是技术债：设置页把 `daily_new_words` 呈现为「每日新词目标」，但它对学习队列**没有任何影响**。实测证据：

| 事实 | 位置 |

## 2. 核心判定：什么算「今天已经用掉的新词额度」

**采用**：当天（UTC 窗口内）`status_before == 'new'` 的**不同 `lexicon_entry_id`** 数。

| 方案 | 判定内容 | 结论 |
|---|---|---|
| A. 数 `user_word_state.first_seen` 在今天的行 | 「今天进入我列表的词」 | **不采用**。导入/入库即建状态，与「今天真的开始学」无关；昨天入库、今天才学的词完全不计，额度可被完全绕过 |
| B. 数 `status == 'new'` 的剩余行 | 「还剩多少个 new」 | **不采用**。它不随时间前进，多刷几次请求数字不变；复习后也无法区分「今天学的」与「以前学的」 |
| C. 新增当日计数列 / 当日表 | 精确的「今日已学」 | **不采用**。需要 schema 与 migration，本批明确禁止 |
| **D. 数当天 `status_before == 'new'` 的复习事件（采用）** | 「今天第一次学、并因此离开 `new` 的不同单词数」 | 事实表已有该列且为 append-only；每次复习一行、按 `user_id` 归属、`timestamp` 有索引；额度随复习**单调递增**，与请求次数无关 |

D 为什么可靠：

1. `services/study.py::_apply` 在写事件前取 `before = state.status` 并原样写入 `status_before`；调度器把 `new` 推向 `familiar`（`fail` 则推向 `weak`），因此「离开 `new` 的那一刻」就是该词**第一次被真正学习**。四种结果（`know`/`fuzzy`/`fail`）都算，`fail` 不是「没学」。
2. 计数用 `DISTINCT lexicon_entry_id`，同一个词当天复习多次只占一个额度。
3. 过滤条件是 `user_id` + `timestamp` 窗口（两者都有索引），不需要扫描用户全部历史。
4. `lexicon_entry_id` 在 V1.2 中必然非空（`record_review` 从 `state.lexicon_entry_id` 复制，而该列 NOT NULL）；历史 V1.1 事件可能是 NULL，但时间为过去，落在今天的窗口之外。删除词库会先被 409 守卫拦住（有学习记录的词库不可删），所以「今天的事件被置 NULL」不成立。

**语义结论**：额度限制的是「今天最多能**开始学**多少个不同的新词」，而**不是**「一次请求最多返回几条 new」。这一条是 P-5 要求的核心：设置不再随每次请求重新计数。

## 3. 用户级与词库级如何共同生效

两层同时生效，规则一句话：**每个词库各自最多贡献它自己的日额度；一天的总量再被用户级设置封顶。**

```
用户级剩余  = max(0, user_settings.daily_new_words - 今日已学新词数(全部词库))
词库级剩余  = max(0, user_lexicon.daily_new_words  - 今日已学新词数(该词库))
当日可用新词 = min(用户级剩余, Σ_词库 词库级剩余)
```

- 取 `min` 而不是让某一层覆盖另一层：用户级那行是用户能看见、能改的「每日新词目标」，它必须是硬上限；词库级那行是「这个词库每天给我多少」的节奏，缩小某本词库的额度不应该反而让总量变大。
- 该词库没有 `user_lexicon` 行时，按用户级额度作为它自己的节奏（并且总量仍受用户级约束）。这样**不会**因为缺一行成员关系就把已有的学习状态从队列里藏掉。
- **事实纠正**：P-5 写「`user_lexicon.daily_new_words` 可经 `/api/settings` 与词库启用写入」与实际不符——两个接口都不写它，它目前只有模型默认 15（以及 0005 迁移的初始化值）。本批**不新增写入接口**（见 §8）：队列按上面的规则读取它，将来给词库页加「每库新词数」时直接生效。
- 响应里的 `remaining` 就是上面这个 `min` 的结果，它是**额度**而不是「一定还有这么多词」：候选数可能更少（用户本来就没那么多没学过的词）。它是加法字段，`GET /api/study/today` 原有的 `total` / `words` 一字未改。

## 4. 队列构成：优先级与 `limit`

队列分成两组，两组条件之和与旧查询**完全等价**（旧查询里 `status IN ('new','weak')` 的非 new 部分就是 `weak`）：

| 组 | 条件 | 组内顺序 |
|---|---|---|
| 到期/积压组 | `status != 'new'` AND (`next_review_at IS NULL` OR `next_review_at <= now` OR `status = 'weak'`) | `status != 'weak'`（weak 先）、`next_review_at`、`first_seen`、`id` |
| 新词组 | `status == 'new'` | `first_seen`、`id` |

返回顺序 = **到期组在前**，然后是受当日额度限制的新词组；`limit` 仍然是**整份队列的长度上限**。

- 旧的排序让 `next_review_at IS NULL`（= 新词）排在到期词前面，于是 `limit` 先被新词占满。[实测] 3 个到期词 + 5 个 new、`limit=2` 时旧实现返回 2 个 new、0 个到期词；这正是「到期词被新词吞掉」。
- 「到期词不被新词额度吞掉」有两层含义，都在这里成立：①额度只作用于新词组，永远不减少到期组；②到期组优先占用 `limit`，新词只能用剩下的位置。
- 代价（明确接受）：到期积压多于 `limit` 时，本次看不到新词。这是刻意的——每日新词是**额外**材料，不应挤掉当天该复习的词；把 `limit` 调大即可同时看到两者。

## 5. 一天的时间边界

- 窗口 = **[UTC 当日 00:00:00, 次日 00:00:00)**，与 dashboard 现有的 UTC 日定义共享同一个函数（`backend/app/services/day.py::day_bounds`），不让两处各写一份。
- 边界比较直接以数据库中的 `timestamp` 文本进行（SQLAlchemy 把带时区的 Python 值写成 UTC 墙上时间，与表内存储格式一致），不用 `date()` 转换，避免 SQLite 时区语义再引入一层解释。
- **取舍**：没有存储用户时区，所以额度在 UTC 零点（本机 UTC+8 的早上 08:00）重置，而不是本地零点。要做到「本地日」需要新增时区设置（新 schema + UI），属**另一次决策**；本批选择与既有 dashboard 口径一致，并在 §6 明确写出。
- 跨日边界测试：前一日 23:59:59.999Z 的事件不计入今天，当天 00:00:00Z 的事件计入。

## 6. 边界与失败模式

| 边界 | 行为 |
|---|---|
| 多用户隔离 | 两个计数查询都带 `user_id = 当前用户`，队列本身也按 `user_id` 过滤；A 的复习不会消耗 B 的额度，A 的队列里不会出现 B 的词 |
| 无学习记录 | 今日已学 = 0，额度全满（正常路径，不报错） |
| 跨日 | 额度自动重置；不写入任何状态、不需要定时任务 |
| 同一词当天多次复习 | `DISTINCT` 只算一次 |
| `fail`/`fuzzy`/`know` | 只要 `status_before == 'new'` 就消耗额度；把「不会」当作没学过会让额度失效 |
| 复习后继续刷队列 | 额度随事件单调消耗；已用满时返回的 new 数量为 0，而不是重新给一批 |
| 并发/多标签页同时请求 | 每个请求都重新计算已学数，没有「预留」语义；两次请求可能各拿到剩余额度的一部分，但**总量不可能超过额度** |
| `daily_new_words` 越大 / 越界值 | 设置接口限制 1–100；库里若存在更大的值（直接改库）也只是放宽上限，不会越出候选词集合 |
| 词条被删除 | 事件里的 `lexicon_entry_id` 被置 NULL 时该事件不再计数；有学习记录的词库受 409 守卫保护，所以这只在守卫被绕过时发生 |
| 迁移遗留状态（V1.1 的 `learning` 词，无任何复习事件） | 它今天第一次被复习时会消耗一个额度。这是**有意保守**：该词在系统里确实还没有任何一次学习记录；宁可少给一个新词，也不让额度被"没有事件的历史状态"绕过 |
| 禁用词库（`user_lexicon.enabled = False`） | **本批不改变候选范围**：队列依旧不看 `enabled`（与改动前一致），禁用词库的新词仍按其自身词库额度计费。原因是「禁用」的含义（退出队列 vs 只是不推荐）需要产品决策，且一旦过滤会让已有学习状态静默消失。当前也没有 UI 设置它。**这是一条已知的、未改变的边界**，见 §8 |
| 队列失败时的降级 | 额度计算与队列在同一个只读查询序列里；任何异常都会让请求 500，不会「先给一批再算额度」 |

**这个设计挡不住什么（写明，避免误解）**：

- 它不阻止用户通过文章/查词看到新词，也不限制「加入我的词库」——那些路径不写 `review_event`，本来就不是「开始学习」。
- 它不改变「哪些词是候选」（公开/私有/禁用词库一视同仁），只改变每天能**开始学**多少个。
- 它不是速率限制：用户仍可以一天学完积压的到期词。
- 客户端把整批队列缓存在内存里逐一复习时，本批内的新词数已经受额度限制，所以不会越额；但**当天已经取走的队列**不会被服务端撤回（换新的一天自然重置）。
- **候选窗口**：新词候选只读取本次可返回的条数（`limit` 减去到期词占用的位置，最多 200）。若某个词库的词库级额度先耗尽，它排在更前面的候选会被跳过，而窗口外、属于另一个词库的候选读不到——于是本次返回的新词可能**少于**额度允许的数量（永远不会多于），且要在下一个 UTC 日才自动恢复。只有当某词库的 `daily_new_words` 小于用户级额度时才会出现这一情形（当前没有接口写该列，所以实际取默认 15 = 用户级默认）。将来给词库页加「每库新词数」时，应改为按词库分别取候选或使用窗口函数分页，本批不做。
