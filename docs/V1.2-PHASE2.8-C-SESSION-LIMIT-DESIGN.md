## 0. 结论摘要

1. **设计早已存在**：`V1.2-PHASE2.7-A-SESSION-MANAGEMENT-DESIGN.md` §5 给出了完整策略（默认 10、`0` = 不限制、超限挤最旧、当前会话永不淘汰、先清理已死行、写 `session_evicted`）。本阶段**实现它**，而不是重新设计。
2. **实现位置与设计一致**：`backend/app/services/auth.py::enforce_session_limit`，由 **`create_session` 调用**——设计 §5.2 明确要求放在服务层，"让 CLI/测试/未来所有登录路径共享同一语义"。
3. **新登录永不因超限被拒**：超限时撤销 `COALESCE(last_seen_at, created_at)` 最早的那条存活会话；被撤销的设备下一次请求即 401。拒绝新登录会造出"设备丢了 → 登不上 → 撤销不了"的死锁，正是设计 §5.2 否决的方案。
4. **当前会话是硬排除**：按 id 排除刚签发的会话（不是"排序上通常不会选中"）。
5. **零 schema**：只做 `SELECT` + `UPDATE (revoked_at)` + `DELETE`（死行）+ 一条 `history_event`。无新列、无 migration、无新表。
6. **配置**：`VOCAB_MAX_SESSIONS_PER_USER`（默认 **10**，`0` = 不限制，非法值回落 10，负值等同 0），已写入 `.env.example`。
7. **审计不含秘密**：`session_evicted`，`user_id` = 账号、`entity_type="user_session"`、`entity_id` = 被撤销会话、`payload={"reason": "session_limit", "limit": N}`；**无 token、无 `token_hash`、无客户端文本**。
8. **与限流机制的关系**：本上限**不依赖内存计数**，每次登录都从行里读——重启、多 worker 都不会让它失真（这与 S-4 的内存限流是相反的取舍，是有意的）。
9. **测试**：先补 16 项（实现前 **13 failed / 3 passed**，3 项是"不该淘汰"的恒真守卫），实现后 **16 passed**；全量后端 **408 passed**（392 → +16），无回归。

### 1.3 设计与实际代码的差异，以及本次裁定

> 说明：设计文档本身是**冻结的历史文档**（Phase 2.7-a 的只读设计审计），本文不改写它；下列差异是"照着设计实现时"，设计与代码现状之间必须补齐的判断。**D-1 ~ D-16 每条都在本阶段做了明确选择。**

| # | 差异 | 本次裁定 |
|---|---|---|
| **D-1** | 设计只给"先删已死行"的顺序，没说清理范围 | **账号内清理**（`user_id` 过滤），不做全局 `prune`。理由：登录是某个人的动作，顺手删掉别人的死行是意外副作用；全局清理仍由启动/CLI 负责 |
| **D-2** | 设计把 ① ② 写成"超限时的淘汰顺序"，但没写"未超限时是否也清理" | **只在 `存活数 > 上限` 时执行**（含其中的死行清理）。理由：§7.1 的验收写的是"**达到上限后**…对已死行优先清理"；未超限时不动任何行，也让本功能对既有测试与既有数据零影响 |
| **D-3** | 设计写 "`0` = 不限制" | **`0` 时整段逻辑直接返回**：既不淘汰，也不清理死行（死行仍由启动/CLI 的 `prune_sessions` 处理）。理由：`0` 应等于"本功能关闭"，而不是"部分仍然生效" |
| **D-4** | 设计只说"`COALESCE(...)` 最早"，**没说并列怎么定** | 沿用 `list_user_sessions` 的排序（`… DESC, id DESC`）反过来取，于是**并列时淘汰 id 最小（最早建的行）**。有专项测试 `test_a_tie_on_activity_time_evicts_the_oldest_row` |
| **D-5** | 设计说"先删**/撤销**已死的行"（两者都算） | **删除**（与 `prune_sessions` 一致）。理由：死行永不可再用，留着只占空间；"谁在何时被登出"由 `history_event` 记录，不依赖该行 |
| **D-6** | §7.1 的"被淘汰的是最久未活动的那条"容易被读成"每次至多淘汰一条" | 真正的语义是"**登录后存活数 ≤ 上限**"，因此**淘汰条数 = 登录后的存活数 − 上限**，上限被调小时可能一次淘汰多条。有专项测试 `test_lowering_the_limit_takes_effect_on_the_next_login`（5 条存活、上限降到 2、再登录 → 一次淘汰 4 条、4 条事件） |
| **D-7** | 设计 §6.1 提到"一次 `COUNT` + 撤销" | 实现**不做 SQL `COUNT`**：直接取该账号的存活行（十位数量级），既得到数量也得到顺序，**数量与顺序出自同一个定义**（`session_is_live` + `list_user_sessions`），无法互相漂移 |
| **D-8** | 设计 §7.3 预计测试放在 `test_session_management.py`（并注明"仅供参考"） | **新建 `backend/tests/test_session_limit.py`**：本批次的行为独立成文件，既有文件的安全断言一行不动 |
| **D-9** | 设计只说事件类型 `session_evicted` | 事件形状对齐既有 `session_revoked`：`user_id=账号`、`entity_type="user_session"`、`entity_id=被撤销会话`、`payload={"reason": "session_limit", "limit": N}`。`reason` 是**服务端固定值**，不接受客户端文本 |
| **D-10** | 设计 §6.2 把 `revoke_reason` 列为"可选、建议与上限一起做" | **不做**（本轮任务明确排除）：UI 仍无法直接解释"这台设备为何被登出"，但审计事件里有固定 reason |
| **D-11** | 设计 §1.4 / §5.1 描述"会话无上限"是当时的**事实陈述** | 实现后该陈述**过时**——已在交接/状态/路线图里就地更正（见 §6） |
| **D-12** | 设计与代码都没讨论：淘汰要不要二次认证 | **不要**。淘汰不是用户发起的操作，而是服务端为**保住新登录**做的取舍；口令与 re-auth 预算与本功能无关 |
| **D-13** | 并发边界：设计未讨论 | [推断] 两个**同时**的登录可能各自判定"超限"从而各淘汰一条（最坏结果：存活数 = 上限 − 1，或一次淘汰两条）。**永远不会超过上限，也永远不会淘汰调用者自己那条**；单 worker + SQLite 串行写使窗口极小。已知并接受，不引入锁 |
| **D-14** | 与并发闸门的关系：设计未讨论 | 淘汰的 DB 工作发生在登录**持有 `LoginGate` 槽位期间**（`api/auth.py::login` 的 `try/finally` 之内）。它不额外消耗 Argon2，但若数据库被写锁住，槽位会被多占一会儿。已知并接受（SQLite busy timeout 远小于登录超时） |
| **D-15** | "死"的定义会不会出现第三份实现 | 全局清理仍是 SQL 谓词（为了不把全表读进内存），账号内清理走 `session_is_live`。两者由既有测试 `test_prune_and_the_live_check_agree_on_the_boundary` 钉在同一个边界上——**本阶段没有改动 `prune_sessions`** |
| **D-16** | 设计的 §7.1 验收里"总数不超限"没说是"行数"还是"存活数" | 明确为**存活数**（§5.2 表 1 的原文）。死行不计入额度，且会在超限时被清理 |

## 2. 本阶段实现

### 2.1 判定顺序（`services/auth.py::enforce_session_limit`）

```
create_session：建行 → commit → refresh → enforce_session_limit(keep_session_id=新行)
enforce_session_limit：
    0) limit = VOCAB_MAX_SESSIONS_PER_USER；limit <= 0 → 直接返回（不做任何事）
    1) live = list_user_sessions(user)          # 存活、按最近活动倒序
    2) len(live) <= limit → 直接返回             # 未超限：零写入
    3) 清理该账号的死行（session_is_live 判否）   # ① 先把不可用的行清掉
    4) 从 (3) 之前的 live 反向取，排除 keep_session_id，
       淘汰前 (len(live) - limit) 条             # ② 再撤销最久未活动的存活会话
    5) 每条淘汰：revoked_at = 本次判定时刻 + 一条 session_evicted 审计
    6) 一次 commit
```

**为什么"先建行、后判定"**：只有新行已经存在，"当前会话永不淘汰"才是一条**可执行的硬约束**（按 id 排除），而不是"排序上大概不会选中"。这也让"新登录一定成功"成为事实：淘汰发生在会话已经签发之后。

**为什么"未超限就零写入"**：登录是最热的写路径之一。默认上限 10 意味着绝大多数登录**一个多余的行都不碰**（不清理、不计数写、不写事件）。

### 2.2 排序与并列

- 排序键 `COALESCE(last_seen_at, created_at)`：**"最近一次活动"**，而不是"创建时间"。一个两天前建、十分钟前刚用过的会话，比一个六小时前建、五小时前就不动的会话更该留下（有测试）。
- 并列（同一时刻的活动时间）：淘汰 **id 最小**的那条（最早建的行）。同一张表重复执行得到同一个结果。
- `last_seen_at` 为 NULL（登录后从未使用）时回落到 `created_at`——与列表接口、闲置超时用的是同一个回落。

### 2.3 审计

| 事件 | 字段 | 不含 |
|---|---|---|
| `session_evicted` | `user_id=账号`、`entity_type="user_session"`、`entity_id=被撤销会话`、`payload={"reason":"session_limit","limit":N}`、`timestamp` | token、`token_hash`、口令、客户端文本、UA |

- 一条淘汰一条事件（不是汇总）：`history_event` 是 append-only 证据，汇总会丢掉"具体是哪条会话没了"。
- 被淘汰的行**不会立刻消失**：它被写成 `revoked_at`，要等 `prune_sessions` 在下次启动/CLI 时删除。因此"被挤掉"与"自己撤销"在数据上**都是 `revoked_at`**，区分它们的唯一依据是 `history_event`（`revoke_reason` 未做，见 D-10）。

已写入 `.env.example`（会话与 Cookie 段）。**没有新增其他配置项**，也没有引入内存计数器。

## 3. 失败与边界（**明确写出挡不住什么**）

1. **用户会"莫名掉线"**：被挤掉的设备下一次请求得到 401，前端只知道"会话失效"。缓解：审计事件 + （将来可选）`revoke_reason`。**这是本设计接受的代价**（§5.2 表 9 原文：务必写审计事件）。
2. **不做锁，因此不是强一致上限**（D-13）：并发登录下可能出现"一次多挤一条"或"暂时落后一条"。**任何时刻都不会超过上限**，也**不会淘汰调用者自己**。个人应用 + 单 worker + SQLite 串行写下，这个窗口可以接受。
3. **不保护"刚被挤掉的用户"**：如果攻击者已持有口令，他可以用"反复登录"的方式把合法用户的设备挤下线（上限 10 → 每次登录挤掉最久未活动的那条）。这与"拒绝新登录"相比是一个**方向相反**的取舍：设计选择"让合法用户永远能登录"，代价是攻击者能制造登出骚扰。前者是死锁，后者是可恢复的骚扰，且有审计。
4. **无前端可见性**：前端没有"我的会话被挤掉了"的提示，也没有管理员可调的上限入口（上限只能改环境变量 + 重启进程读取）。本批次不新建 UI。
5. **不改变"多 worker"结论**：上限本身与 worker 数无关（读行），但内存限流（S-4）仍然要求单 worker；本阶段**不触碰该约束**。
6. **`0` 不等于"什么都不清理"**：`0` 只是关闭本功能，死行依旧由启动/CLI 的 `prune_sessions` 删除。
7. **不覆盖"会话数量攻击"的极端情形**：持口令者仍可高频登录（每次登录挤掉一条旧会话），这属于认证/自助服务层面的固有面，上限只约束存量。

> 一个实现前暴露的设计要点：**创建一条会话本身也要受上限约束**。测试最初把"2 条存活 + 1 条已撤销"布置在上限 2 之下，结果发现**创建那条"已撤销"会话时就把一条存活会话挤掉了**（创建瞬间它是存活的）。现在所有需要"先布置状态再观察"的测试都**在上限关闭时布置，再调低上限**——这既符合真实运维动作（运营者调低上限），也避免了自相矛盾的夹具。

## 6. 明确不做

1. **不做 `revoke_reason`**（需 migration 0008），因此 UI 仍无法直接解释"为何被登出"（D-10）。
2. **不建前端 UI**：既没有"被挤掉"的提示，也没有上限的可视化设置。
3. **不改 `prune_sessions` / 启动清理 / CLI 行为**：上限是登录路径的收敛机制，不是新的清理调度。
4. **不引入会话内计数、内存计数或跨 worker 共享状态**：上限从行里读。
5. **不关闭/放宽任何既有约束**：单 worker、内存限流语义、re-auth 预算、CSRF 三层、IDOR 404 语义全部保持。
6. **不重启运行实例、不迁移生产库**：本阶段全部工作在 Level 1（pytest 临时库）内完成。
