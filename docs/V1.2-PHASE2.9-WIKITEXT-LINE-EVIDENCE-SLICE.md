## 2. 新结构

新表 `source_wikitext_line`，一行 = 某来源某页面固定修订的某一行。既有表一字未改，无回填。

| 列 | 含义 |
|---|---|
| `source_artifact_id` | 保全工件（FK → `source_artifact`，`ON DELETE RESTRICT`）——「这行是从哪份字节读出来的」 |
| `source_id` | **已声明**来源 ID（如 `zhwiktionary-pinned-oldid`），不是定位串简称 |
| `page_revision` | 页面固定修订（oldid），非空且**只能是数字串** |
| `line_number` | 该修订 wikitext 中的 1 起行号 |
| `raw_text` | 该行原文，逐字；不 trim（缩进与列表符在 wikitext 里是内容），不截断，不含 CR/LF |
| `language_path` | 所记语言小节（如 `英語`）；`''` 表示未判定 |
| `heading_path` | 统辖该行的标题路径（如 `英語 > 形容詞`），与 `language_path` 用 `' > '` 连接 |
| `pos_heading_key` | 该行**本身是**词性标题时对应的词性键（复用 `CONCISE_MEANING_POS_KEYS` 闭集）；否则 `''` |
| `pos_heading_text` | 该词性标题的原文（如 `形容詞`），与键同生共死 |
| `page_text_sha256` | 整页原文指纹（绑定**页面版本**的内容，而非只绑一个编号） |
| `line_sha256` | 本行指纹，公式见 `models.source_wikitext_line_sha256`（source_id、revision、页面指纹、行号、原文，以 `\n` 连接后 SHA-256） |
| `created_at` | 写入时刻 |

键与约束：

- 唯一位置 `uq_source_wikitext_line_position (source_id, page_revision, line_number)`：同一修订的同一行只能有一行记录；`source_id` 在键内，因为 oldid 只在签发它的 wiki 内唯一。
- 外键 1 个：`source_artifact`（`RESTRICT`）。
- 20 条命名 CHECK：来源 ID 非空／已 trim／不含 `:`（定位串分隔符）／单行；修订非空／已 trim／**全数字**；行号 ≥ 1；原文非空／单行；两条路径已 trim／单行／**标题路径必须在所记语言之下**（用 `substr` 前缀比较，不用 `LIKE`，避免 `%`/`_` 被当通配符）；词性键属闭集／已 trim；键与标题文本同生共死；标题文本已 trim／单行；两条指纹必须是 64 位小写十六进制。

## 3. 「固定 wikitext 行」与「转换 CSV 行」如何区分

不是靠字符串前缀猜，而是靠**两张表各自的键与字段形状**：

| | 转换 CSV 物理行 | 固定 wikitext 行 |
|---|---|---|
| 表 | `entry_source_evidence`（既有） | `source_wikitext_line`（本片） |
| 键 | `(evidence_sha256, import_run_id)` | `(source_id, page_revision, line_number)` |
| 位置列 | `row_locator`，含表头的物理行号 | `line_number`，该修订内的行号 |
| 页面版本 | `source_revision`（可为空，取决于映射是否声明） | `page_revision` 必填且全数字 |
| 原文 | 整个单元格（可汇总多义项） | 单行，且不含 CR/LF |
| 内容指纹 | `evidence_sha256` | `page_text_sha256` + `line_sha256` |

因此「把 CSV 行号写成语 wikitext 行」这件事在形状上不可表达：`70dc6b68` 这类版本串过不了全数字约束，多行单元格过不了单行约束，而 CSV 侧没有页面指纹可填。测试 `test_a_csv_position_keeps_its_own_row_and_its_own_key` 把同一个整数同时当成 CSV `row_locator` 与 wikitext `line_number` 存下，断言两行互不混淆。

### 4.1 `test_entry_source_block.py` 那一处冲突怎么处理

`test_the_concise_meaning_reports_the_evidence_row_it_was_proposed_against` 用 `source_locator="meaning:2"` 走 `propose` + `confirm`，而 `0e60f14` 之后确认入口会拒绝这个定位串（`concise_meaning.py:828`）——它既不是 WikDict 的 CSV 物理行，也不是固定 wikitext 的 `oldid:行`。已实测确认该失败在起点 HEAD 上就存在（把本片改动 `git stash` 掉后同样失败），与 0012 无关。

处理方式：**不放宽确认服务**，也不把合成位置伪装成已核实的 WikDict，而是把该测试**明确改成已确认旧数据的读侧夹具**——直接写入两行 `entry_concise_meaning`（`status='confirmed'`、具名确认人、`pos_source='reviewer'`、`language='en'`），保留它原本要验证的断言：`concise_meanings[]` 与来源块指向**同一个证据 ID**，自拟补充为 `None`。理由写在测试 docstring 里，也是读路径自己的口径（`load_concise_meanings`：写在该规则之前的行正是会落到这里的那批，读路径必须自己把关）。

夹具的诚实边界：`source_evidence_id` 指向的是**真实导入**产生的、被采用的证据行；`meaning:2` 只保留为**旧数据的定位串形状**（`<字段角色>:<行>`，其行号 2 与该证据行的 `row_locator` 一致，测试里有这条对照断言）。合成位置就写着它是合成的；没有伪造 WikDict 定位串，也没有伪造证据链。

### 4.2 存储契约修复：四条缺陷（同一未发布修订内改，不新开 0013）

复核 0012 发现四条「结构说得比数据库做得多」的缺陷。`0012` 未发布（生产在 `0007`），且仓库已有先例——`18325e0` 就是直接改未发布的 `0011` 修订而不是叠加新编号——因此这四条在 **`0012_source_wikitext_line.py` 内就地修复**，不加 `0013`。每条都先在临时 SQLite 库上复现，再验证修复（脚本 `C:\Temp\p29-0012-probe\probe_defects.py`，库全部建在 `tempfile.mkdtemp` 下，不碰仓库与 `data/`）。

| # | 复现（修复前） | 修复 | 修复后 |
|---|---|---|---|
| 1 | `UPDATE source_wikitext_line` 改掉 `raw_text`：**成功**；`DELETE`：**成功** | 触发器 `trg_source_wikitext_line_no_update` / `_no_delete`（`BEFORE UPDATE`／`BEFORE DELETE` → `RAISE(ABORT, …)`） | 两者都被拒；拒绝信息以触发器自身命名开头（SQLite 的 `RAISE` 只报文本、不像 CHECK 那样报约束名），行保持原样 |
| 2 | `line_number='abc'` 存成 **text**、`15.5` 存成 **real**：**成功** | 新增 CHECK `ck_source_wikitext_line_number_integer`（`typeof(line_number) = 'integer'`） | 两者都被拒；`'15'` 经 INTEGER 亲和性变成整数 15，仍可存——存进去的是数字就是数字 |
| 3 | 同一 `(source_id, page_revision)` 的两行可以有**两个不同**的 `page_text_sha256`：**成功** | 触发器 `trg_source_wikitext_line_one_page_fingerprint`（`BEFORE INSERT`，`WHEN EXISTS` 同修订不同指纹 → `ABORT`） | 第二个指纹被拒；同指纹的多行仍可存，另一个修订或另一个来源用同一指纹也仍可存。不覆盖先记的值：分歧本身才是要人看的东西 |
| 4 | 数据库已有外键违规时升级：**先建表**，再在 `_verify` 里发现违规并中止——版本号停在 `0011`，表却已经留下（SQLite 无事务性 DDL） | 把外键违规检查**移到 DDL 之前**（`_require_consistent_database`，升级与降级都先问一次） | 违规数据库在第一条语句之前就被拒：不建表、不改版本号、违规行在信息里点名，数据库原样不动 |

为什么用触发器而不是别的：`CHECK` 只看得到自己这一行，表达不了「同一修订不许有第二个指纹」；「这张表永不被改写/删除」更不是行的形状。这是本 schema 第一次用触发器，所以每个都**命名**、由迁移自己的 `_verify` 断言存在（`EXPECTED_TRIGGERS`）、并有测试去尝试那条必须被拒的写。**已知代价**：SQLAlchemy 表达不了触发器，所以由 `create_all` 建的库只有列、CHECK 和外键，没有这三条规则——测试把这一差异显式断言出来（`trigger_names(built) == set()`），而不是留给读者去发现；用户拿到的 schema 始终来自迁移。

保留的边界（不声称已经解决）：数据库仍然无法证明 `page_text_sha256`／`line_sha256` 就是重读保全包会得到的值（指纹只被保存、比对和重算，不被 SQLite 校验），也无法证明工件是保全 wikitext 包、`page_revision` 上游真的存在。`raw_text` 等文本列没有 `typeof` 检查：TEXT 亲和性会把数字转成文本，所以不会出现「文本列里放着非文本」的同类问题（BLOB 是残余边角，未处理也未声称处理）。

## 5. 下一片要把哪些字段绑定到确认入口

确认入口（`app/services/concise_meaning.py` 的单一确认路径）在下一片需要把这些字段接进来，本片只保证它们**可持久回查**：

1. **定位串别名与解析**：定义 `zhwiktionary` → `zhwiktionary-pinned-oldid`、`wikdict` → `wikdict-en-zh-2026-06-23` 的显式别名表（不得按前缀猜），并把 `source_id:revision:line` 解析为三元组。解析失败即拒绝。
2. **位置存在性**：按 `(source_id, page_revision, line_number)` 查 `source_wikitext_line`，必须唯一命中；查不到即拒绝该来源支持的确认。查到的那一行**不会被改写或删除**（§4.2 第 1 条），所以确认时解析到的原文与显示时读到的是同一份。
3. **版本与指纹**：用 `page_text_sha256` 与重新读取的保全页面原文核对，并用 `models.source_wikitext_line_sha256` 重算 `line_sha256` 比对；两者不一致即拒绝（这是「某一页某一行当时是什么」的可复核点）。同一 `(source_id, page_revision)` 只可能有一个页面指纹（§4.2 第 3 条），因此这一步不会因为"同一修订的两行各说各的"而无从判定。
4. **原文匹配**：`raw_text` 必须含被引文字的逐字片段（`provenance_kind='source'`）；`derived` 走同一条证据链加 `derivation_note`，不做逐字要求。
5. **语言路径**：`language_path` 必须是目标语言（`en`），空或他语言一律拒绝——`fertiliser` 的「使肥沃；施肥」在 `法語 > 動詞` 下，正是这条挡住的。
6. **词性标题依据**：`pos_source='pos_section'` 时，被引位置必须是**标题行**且 `pos_heading_key` 等于所报 `pos_key`、`pos_heading_text` 属于该键的标题拼写闭集，且拟议释义行的 `heading_path` 位于该标题所辖路径内；`pos_heading_key=''` 的行（如 `發音`）一律不通过。`pos_source='reviewer'` 时，依据必须是目标语言的释义行本身，且该行已作为引用被核实。
7. **绑定列（本片未加）**：`entry_concise_meaning.source_evidence_id` 与 `entry_concise_meaning_citation.source_evidence_id` 目前只能指向 CSV 证据行。下一片需要为「指向逐行证据」补一条绑定（新增 `source_line_id` 外键列，或一张带判别列、`ON DELETE SET NULL` 的绑定表），并加 CHECK 保证两条列**恰好一条**非空、加唯一键防止同一引用位置重复；`ai_supplement` 仍然必须两条都为空。
8. **仍然缺的来源级事实**（数据库管不到，需下一片补齐）：被引工件必须是**保全 wikitext 包**（`role`／`format`／映射）而非转换 CSV；冻结映射是否声明 `revision`；以及正式来源清单里的修订声明。这些是跨表事实，SQLite 不能校验，只能在确认路径上核对。

**下一片不要顺手做的**：不把 `pos_section` 自动降级成 `reviewer`，不从 `zh_oldid` 猜补证据行，不把跨语言行改标 `en`，不为 WikDict 推断逐义词性。
