## 1. 负责人已定的产品口径（本切片的验收依据）

1. 本轮先供**本人和家人两个账号**使用。
2. 学习页**优先显示 1–3 个常见、简体的核心义项**；**允许不覆盖全部义项**。
3. **来源完整原文始终可回查**。
4. **AI 自拟补充只能作为候选，须人工确认，不能冒充来源原文。**

本设计把这四条变成四个可测试的性质：

| 口径 | 落地为 | 由什么强制 |
|---|---|---|
| 1–3 个核心义项 | `display_order between 1 and 3` + `length(text) <= 40` | 数据库 CHECK + 服务层可读拒绝 + 前端只渲染已确认项 |
| 允许不覆盖全部义项 | 短释义是**独立**的展示值，不要求与 `source_meanings` 等长或一一对应 | 短释义不写回 `source_meanings`；来源默认释义原样保留 |
| 原文始终可回查 | `source_raw` / `source_meanings` / `entry_source_evidence.raw_text` 一概不被本切片写入 | 服务层不发出对这三处的任何写；迁移预演逐词比对 19 条 `lexicon_entry` 的来源文本 |
| 自拟补充须确认、不得冒充原文 | `provenance_kind='ai_supplement'` 的结构被限制为**不得携带任何来源指针**；未确认的候选读路径取不到 | 数据库 CHECK（形状不可表示）+ 唯一读路径 `status='confirmed'` 过滤 |

## 2. 四个必须分开的东西

同一句"这个词是什么意思"，在本仓库里有四处不同的记录。本切片的全部设计就是把它们分开放，并让每一处都能被单独检验：

| # | 是什么 | 存在哪里 | 可变性 | 谁能写 |
|---|---|---|---|---|
| 1 | **来源证据**：某来源在某一行原样说了什么 | `entry_source_evidence.raw_text` | 只追加，永不 UPDATE/DELETE | `0008` 的确认写入 |
| 2 | **来源默认释义**：人工裁定的来源默认快照 | `lexicon_entry.source_meanings` | 导入时写入，既有词条**不被覆盖** | `0008` 的确认写入 |
| 3 | **来源完整原文**：主来源那一行 | `lexicon_entry.source_raw` | 同上，永不改写、永不跨来源拼装 | `0008` 的确认写入 |
| 4 | **简短展示值**：学习页显示的那 1–3 个词 | `entry_concise_meaning.text` | 内容层，可撤回后重提 | **本切片** |

外加一处只追加的历史：`entry_concise_meaning_revision`，记录"谁在什么时候提了什么、确认了什么、撤回了什么"。

**为什么不塞进 `default_anchor`**：`default_anchor` 是"最小语义锚点"，`UserWordState.anchor_override` 覆盖它，`View` 层把两者合成一个 `anchor` 字段。把短释义放进去会立刻产生两个问题：(a) 无法表达"1–3 个"；(b) 一个用户改自己的锚点就会改变"这个词的短释义"的语义——而短释义是**共享内容**，不是某个人的学习状态。本切片因此让 `default_anchor` 一字不动（`test_proposing_changes_no_source_field` 断言它仍是原值）。

**为什么不覆盖 `source_raw`**：`source_raw` 是"回查"的唯一锚点。一旦被短释义覆盖，"来源原文始终可回查"这条口径就没有载体了，而且繁体来源会被静默简体化——P03「農村的」这类差别正是唯一能被人复核的东西。

## 3. Schema 0009（两张表，纯增量）

### 3.1 与尚未发布的 `0008` 的关系（**必读**）

**裁定：`0009` 叠加在 `0008` 之上，就地不改 `0008`。**

- `0008_public_lexicon_import` **未发布、未在任何真实库上应用**：仓库现有记录把生产定在 `0007`，Phase 2.9 的全部预演都在合成库或副本上跑（见 `V1.2-PHASE2.9-CONFIRM-WRITE-DESIGN.md` §9.5 与各切片记录）。
- `0009` 的 `source_evidence_id` 指向 `entry_source_evidence`，**没有 `0008` 就毫无意义**。因此 `down_revision = "0008_public_lexicon_import"`，两者**要么一起发布，要么都不发布**。
- `0008` 已经就地加强过一次（授权元数据 CHECK，设计 §9.5）。第二次就地改动会让一个**已经被另一条未发布分支预演并成文描述**的 revision 静默变形：`codex/phase29-target-readonly-preflight` 记录了 `0008` 的形状，`tools/rehearsal_migration_0008.py` 按 `0008` 断言外键数量。新增 `0009` 让 `0008` 保持**逐字节不变**，依赖关系写进链条本身。
- 若 `0008` 在发布前改号或改内容，`0009` 的 `down_revision` 必须跟着改。这不是负担：`backend/tests/test_concise_meaning.py::test_0009_follows_the_unpublished_0008_and_keeps_one_head` 会把不一致直接测出来。
- **行为上是纯增量**：停在 `0008` 的库只是没有短释义，读路径回退到来源释义——这正是设计好的回退行为（§5）。

### 3.2 `entry_concise_meaning`（当前展示值）

一个词条、一个展示位、一行。

| 列 | 作用 |
|---|---|
| `lexicon_entry_id` | → `lexicon_entry.id`，**`ON DELETE CASCADE`**：展示值是词条的**内容**，词条没了就没有可显示的东西 |
| `display_order` | 1–3 |
| `text` | 实际显示的短值，≤ 40 字 |
| `provenance_kind` | `source` \| `derived` \| `ai_supplement` |
| `source_evidence_id` | → `entry_source_evidence.id`，可空，`SET NULL` |
| `source_locator` | 人可读的来源位置（如 `zhwiktionary:12`）。独立成列，因此证据行被删除后仍能回查 |
| `derivation_note` | 改了什么 / 为什么补充 |
| `status` | `candidate` \| `confirmed` \| `rejected` |
| `proposed_by_username` / `proposed_at` | 谁提的、什么时候 |
| `confirmed_by_user_id` / `confirmed_by_username` / `confirmed_at` | 谁确认的、什么时候 |

约束：

```sql
-- 一个展示位一行；rejected 不占位，所以撤回一个显示值不会连带删除它的记录
CREATE UNIQUE INDEX uq_entry_concise_meaning_slot
    ON entry_concise_meaning (lexicon_entry_id, display_order) WHERE status <> 'rejected';

CHECK length(trim(text)) > 0
CHECK length(text) <= 40
CHECK display_order between 1 and 3
CHECK provenance_kind in ('source','derived','ai_supplement')
CHECK status in ('candidate','confirmed','rejected')
-- 引文必须有来源位置
CHECK provenance_kind = 'ai_supplement' OR length(trim(source_locator)) > 0
-- 不是逐字引用，就必须写明改了什么
CHECK provenance_kind = 'source' OR length(trim(derivation_note)) > 0
-- 自拟补充不得携带任何来源指针：形状不可表示，因此不能冒充引文
CHECK provenance_kind <> 'ai_supplement'
      OR (length(trim(source_locator)) = 0 AND source_evidence_id IS NULL)
-- 没有任何具名的人，就不存在已确认的展示值
CHECK status <> 'confirmed'
      OR (confirmed_at IS NOT NULL AND length(trim(confirmed_by_username)) > 0)
```

三种 `provenance_kind` 与草案 20 词的对应：

| kind | 含义 | 必须写 | 草案例子 |
|---|---|---|---|
| `source` | 该来源自己就有的取值 | `source_locator` | P01 who→谁、P08 ambassador→大使 |
| `derived` | 对来源取值的**有记录改动**：繁转简、删噪声、重新措辞、抽取单个义项 | `source_locator` + `derivation_note` | P03 rural→农村的（来源「農村的」）、P06 reduction→减少；缩减 |
| `ai_supplement` | **没有任何来源这么说** | `derivation_note`，且**不得**有来源指针 | P14 recruit→招募；新兵、P17 seemingly→看似；似乎 |

### 3.3 `entry_concise_meaning_revision`（修改/确认记录，只追加）

每次 propose / confirm / reject 追加一行，携带当时的取值快照、动作、执行人和备注。

- `lexicon_entry_id` 是 `ON DELETE SET NULL`，`normalized_word` 保留词身份——与 `0008` 的证据行同一理由：**某个人对某个词做过什么决定，这条记录应当比词条活得久**。
- `concise_meaning_id` / `source_evidence_id` / `actor_user_id` 都是 `SET NULL`；`actor_username` 是不可变快照，删账号不会抹掉"谁确认过共享词库显示什么"。
- 服务层**从不**对这张表发出 UPDATE 或 DELETE，并有测试用 SQLAlchemy 语句钩子强制这一点（`test_no_path_updates_or_deletes_the_history`）。

### 3.4 删改语义小结

| 事件 | 结果 |
|---|---|
| 删除一个词条 | 展示值随之删除（它是内容）；历史行保留，`lexicon_entry_id` 置 NULL |
| 删除一个用户 | `confirmed_by_user_id` / `actor_user_id` 置 NULL，用户名快照保留 |
| 删除一条证据行 | 展示值仍可显示，`source_locator` 仍指向来源位置 |
| 撤回一个显示值 | 该行 `status='rejected'` 并保留原值，展示位空出，可重新提候选 |
| 覆盖一个显示值 | **不可能**：直接 propose 到已确认的位置会被拒绝，必须"先撤回、再重提、再确认" |

## 4. 三个写操作与一个读操作

服务层：`backend/app/services/concise_meaning.py`。写操作每一步都要求 **active administrator**：显示值是共享内容，普通用户的确认不能改变别人正在学的东西。

### 4.1 `propose` —— 提交候选（什么都看不到）

- 校验：类型已知、文本非空且 ≤ 40 字、位置 1–3、同一文件内位置不重复、来源指针与类型自洽、`source_evidence_id` 必须属于**本词条**。
- 同一位置已有 **candidate**：把它标为 `rejected`（理由"被同一位置的更新候选取代"）并写下历史，再放新候选——草案阶段可以改稿。
- 同一位置已有 **confirmed**：**拒绝**，并明确告诉操作者"先撤回它，再重新提交候选并确认"。
- 一次调用最多 3 条；整份提案文件中只要有一个词不在目标词库里，**整份都不写**（半份提案在复核时会看起来是完整的）。

### 4.2 `confirm` —— 人工确认（这一步之后才会显示）

候选 → 已确认，写入确认人与时间。重复确认同一行是幂等的（返回原行，不追加第二条 `confirmed` 历史），所以复核跑第二遍是安全的。

### 4.3 `reject` —— 撤回 / 拒绝（必须写理由）

候选或已确认行 → `rejected`。撤回一个已确认值会把它从学习页撤下并空出展示位；**行本身与它的确认人保留**，因此"曾经显示过什么、谁批准的"不会因为撤回而消失。修改一个显示值 = 撤回 + 重提 + 确认，三步各自留痕。

### 4.4 `load_concise_meanings` —— 唯一读入口

`status='confirmed'`、按 `display_order` 排序、一次查询取完一个响应里的所有词条（50 个词一条 SQL，不是 50 条）。**这是候选与页面之间唯一的闸门**，因此"未确认候选不可展示"不是任何调用方需要记住的习惯——候选到响应之间没有代码路径。

## 5. 展示链路与回退

### 5.1 API

`word_dict_from_view(view, concise_meanings)` 在既有字段旁新增：

```json
"concise_meanings": [{
  "text": "农村的",
  "display_order": 1,
  "provenance_kind": "derived",
  "provenance_label": "据来源改写",
  "is_source_verbatim": false,
  "is_supplement": false,
  "source_locator": "zhwiktionary:12",
  "derivation_note": "来源为「農村的」，此处为简体转换",
  "confirmed_by": "owner",
  "confirmed_at": "2026-09-26T00:00:00Z"
}]
```

- **`concise_meanings` 与 `source_meanings` 是两个字段，不合并。** 客户端必须能区分"已复核的短值"和"来源默认"。
- `is_source_verbatim` 由服务端从存储的 kind 推导，**不让客户端猜**：客户端要以"这是来源自己的话"来呈现之前，唯一该判断的字段就是它。
- **空数组是回退信号本身**，服务端**永不**用 `source_meanings` 去填这个空——否则客户端无法分辨"复核过的值"和"没人复核过的值"。回退是客户端的决定。

接在三条既有读路径上：`GET /api/study/today`（批量）、`GET /api/words`（批量）、`GET /api/words/state/{id}`（单词）。

### 5.2 前端

`frontend/src/components/ConciseMeaningList.tsx`：`source` 不贴标签（它就是来源原文）；`derived` 贴「据来源改写」并显示改动说明；`ai_supplement` 贴「自拟补充」并显示补充理由。来源位置一并显示，补充项**没有**来源位置，也不假装有。列表下方注明"已由 X 人工确认"。

- **学习页**（`StudyPage.tsx`）：有已确认短释义时，`核心释义` 排在第一位；最小语义锚点保留在下方且行为不变；原书完整释义收进 `<details>`，**收起而非移除**——"可回查"不等于"始终展开"。没有短释义时，渲染与改动前**逐字相同**（锚点 + 原书完整释义展开）。
- **词条详情**（`WordDetailPage.tsx`）：短释义单独成节；原书完整释义仍默认展开。
- **词库列表行**：本切片不动（行内不显示释义）。

### 5.3 一个明确的取舍（待负责人裁定）

学习页现在可能同时出现「核心释义」和「最小语义锚点」两块，两者语义相邻。本切片选择**保留锚点、把短释义排在前面**，理由是删除锚点会改变既有行为并影响 `anchor_override` 的个人覆盖功能，超出本轮口径。如果负责人认为二者重复，正确的做法是单独一个切片决定"锚点在有了短释义之后还意味着什么"，而不是在这里顺手删掉。

## 6. 管理员入口（CLI）

沿用 `public-lexicon confirm` 的成例：**没有对外写端点**，口令用 `getpass` 交互输入，因此不涉及 `tests/test_authz.py` 的 IDOR 矩阵；三个写命令都要求管理员本人当前口令。

```
# 1) 只读复核：打印来源字段、候选、完整历史
python -m app.cli concise-meaning status --lexicon NAME [--word WORD]

# 2) 提交候选：什么都不会显示
python -m app.cli concise-meaning propose --file PROPOSALS.json --lexicon NAME --admin USER

# 3) 人工确认：按 status 给出的 id 逐条确认
python -m app.cli concise-meaning confirm --id 12 --id 13 --lexicon NAME --admin USER [--note ...]

# 4) 撤回 / 拒绝：必须写理由
python -m app.cli concise-meaning reject --id 12 --note "负责人复核：应为「周转」" --admin USER
```

提案文件（`--file`）：

```json
{
  "format_version": 1,
  "lexicon": "考研英语核心词",
  "entries": [
    {"word": "rural",
     "meanings": [
       {"text": "农村的", "provenance_kind": "derived", "display_order": 1,
        "source_locator": "zhwiktionary:12",
        "derivation_note": "来源为「農村的」，此处为简体转换"}
     ]}
  ]
}
```

- `display_order` 可省略，缺省为数组下标（1 起）。
- `source_evidence_id` 可省略：只有在 `0008` 的确认导入已经为该词条写下证据时才存在；`source_locator` 才是始终可回查的那个字段。
- **未知字段一律报错，不忽略**：把 `provenance_kind` 拼错会拒绝整份文件，而不是安静地按默认值处理。
- `status` 命令**刻意**把未改动的来源字段（`source_default_meanings`、`source_raw`、`default_anchor`）与候选并排打印，让"复核"是一次比对而不是记忆测试。

退出码：`0` 成功；`1` 拒绝（**什么都没写**）；`2` 文件不可用或目标库/库 revision 不可用。

## 8. 本切片明确不做 / 挡不住什么

**不做**：

- 不导入任何真实来源，不生成可确认计划，不运行 `public-lexicon confirm`。
- 不迁移、不打开生产 `data/vocab.db`，不推送、不合并、不起正式实例。
- 不提供对外写端点（确认只有 CLI）。
- 不新建 `exam_frequency_observation`，不写 `frequency_*`。
- 不改 `0008`，不改 `0001`–`0007`，不更新 `lexicon.entry_count`。
- 不处理 `default_anchor` 与短释义的语义重叠（见 §5.3）。

**挡不住**（必须由人或后续设计承担）：

- **"简体"没有机械化校验。** 本切片强制"非逐字引用必须声明改了什么"（`derivation_note`），并保留 `source_locator` 供人核对，但**不检测**文本究竟是不是简体。识别繁体需要映射表，而那会引入新的正确性假设；这里选择"强制声明 + 保留可核对定位"，不假装能验证。
- **`derivation_note` 的内容不被校验**，只被要求非空。一个不诚实的说明无法被代码识破。
- **释义质量本身**：本切片只保证"这段文字被谁在什么时候确认过、它的措辞来自哪里"，不保证它是对的。
- **来源授权**：与 `0008` 相同，本切片不涉及。三人以上、公开使用、署名与修改标注仍待负责人单独审阅来源的 `use_scope` / `display_scope`。
- **候选人选仍取决于主词表**：本切片可以在无真实资料时用合成数据完成验收，但"哪 20 个词、短释义写什么"仍是 §9 的待决项。

## 9. 待审查事项

1. **§5.3 的取舍**：学习页同时出现「核心释义」与「最小语义锚点」是否可以接受？若否，应另开切片定义"有了短释义之后锚点意味着什么"。
2. **40 字上限**：目前是数据库 CHECK。若负责人希望允许更长的短释义，需要一次迁移（这正是把它放进 CHECK 的理由：改口径应当是显式决定）。
3. **确认人门槛**：当前只有 active administrator 能改共享显示值。若第二轮要让家人也能标注"这个词我看不懂"，那应是**另一个功能**（个人备注），不能是改共享短释义。
4. **`ai_supplement` 的可见度**：目前它在学习页与 `source` 同样大小显示，只多一个橙色标签。是否需要更弱的视觉权重（例如默认折叠），待产品判断。
5. **真实来源下的 CLI 工作流**：本切片只验证了合成数据下的 propose/status/confirm。真实 20 词的复核节奏（一次确认多少条、`--note` 怎么写）应在真实来源获批后单独走一遍。
