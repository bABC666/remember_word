# 拾词 V1.2 · Phase 2.5 登录防滥用策略设计与审计

> 阶段：Phase 2.5（**只审计与设计，不实现**）
> 基线：分支 `feat/v1.2-phase1-safe`，HEAD `3e7f0f4`（Phase 2.4-b 完成）
> 目标：针对认证链路中已确证的资源消耗风险，给出可直接实施的限流/防滥用设计
> 证据口径：**[实测]** = 本次运行探针得到（`test-artifacts/phase25-cost-probe-output.txt`）；**[源码]** = 代码位置；**[推断]** = 由实测数据推导
> **本阶段未修改任何业务代码、未创建 migration、未新增数据库字段。**

---

## 0. 结论摘要

1. 一次失败登录的实测成本：**Argon2id ≈ 61–81 ms + 审计写 ≈ 1.0 ms + HTTP ≈ 10 ms**，合计 **≈ 72–90 ms**。瓶颈是 **CPU 与内存（每次 64 MiB）**，不是数据库写入（占 1.5%）。
2. 由于 Phase 2.4-a 的修复，**未知用户名也必须执行一次校验** —— 这消除了时间侧信道，同时把"零成本的枚举洪水"变成了"每次尝试 64 MiB / 约 70 ms"的**资源放大入口**。这是本阶段要解决的核心问题。
3. 12 个并发校验实测把进程工作集从 **92 MiB 推到 861 MiB（+769 MiB）**；单 worker 的 anyio 线程池上限为 **40**，理论峰值 **≈ 2.5 GiB**。
4. 推荐方案：**方案 C（IP 维度执行 + username 维度减速）+ 全局并发闸门**，**内存计数、零 schema、零 migration**；`history_event` 已足够做取证与按账号回溯，不参与限流判定。
5. **不需要任何数据库 schema 变化。** 只有在"DB 持久化 IP 限流"或"持久化账号锁定"时才需要新列/新表，二者本阶段均**不实现、不推荐**（理由见 §5）。

## 1. 当前风险分析（实测）

### 1.1 一次失败登录的成本分解

生产参数为 pwdlib 推荐的 Argon2id：实测编码头部 `m=65536,t=3,p=4`（即每次校验声明 **64 MiB** 内存）。

| 项 | 实测 | 占比 | 说明 |
|---|---|---|---|
| Argon2id 校验本身 | **61.0 / 71.5 / 81.2 ms**（三次运行） | ≈ 85–90% | 数字随机器负载浮动，同一次运行内部一致 |
| `history_event` 插入 + commit | **0.9 / 1.0 / 1.2 ms** | ≈ 1.5% | Phase 2.4-b 后每次失败写一行 |
| 完整 HTTP 失败请求（未知用户名） | **73.2 / 89.4 ms** | 100% | = 校验 + 审计写 + 框架/HTTP 开销（≈10 ms） |
| 完整 HTTP 失败请求（已知账号+错密码） | **71.8 / 89.1 ms** | 100% | 与上一行差 ≤ 2 ms → **M2 的等时性仍然成立** |

**关键结论：限流要保护的是 CPU 与内存，审计写入不是瓶颈。** 因此限流必须发生在**哈希之前**，否则保护无意义。

### 1.2 并发与内存放大（实测）

| 项 | 实测 | 含义 |
|---|---|---|
| 24 次失败登录，串行 | 1.85 s（77 ms/次） | 基线 |
| 24 次失败登录，8 线程并发 | 1.08 s（**45 ms/次**） | 吞吐 ×1.7 |
| 8 次纯 Argon2 校验，8 线程 | 0.36 s vs 串行 0.59 s | 加速 **1.65×** → 部分并行，**攻击者可用多核** |
| 12 个并发校验期间的工作集 | 92 MiB → **861 MiB（+769 MiB）** | ≈ 64 MiB × 12，与 `m=65536` 完全吻合 |
| 单 worker 的 anyio 线程池上限 | **40** | 同步端点并发上限 |
| ⇒ 理论峰值内存 | **40 × 64 MiB ≈ 2.5 GiB** | 若 40 个并发请求全是登录 |

**[推断]** 在无任何限制的情况下，一个未认证攻击者可以：占满 CPU（多次尝试并行）＋ 把常驻内存推到 GB 级（并发校验）＋ 让 `history_event` 无限增长。

### 1.3 写放大（实测）

| 项 | 实测 |
|---|---|
| 审计表单行体积 | **129 字节/行**（2000 行直接插入 → 文件增长 258,048 字节） |
| 一次失败 = 一行 | 实测 48 次洪水请求 → 48 行，**每次尝试恰好一行** |
| 40 行小样本的页级增长 | 0 字节（小于一页，页分配粒度掩盖） |
| **[推断]** 持续 20 次/秒 | ≈ 2.5 KB/s ≈ **9 MB/小时 ≈ 216 MB/天** |

且 `history_event` 在验证工具中被归类为 **`append_only`**（`tools/verified_db.py`），仓库内**没有任何保留期/清理策略**。

### 1.4 攻击者可控变量

| 变量 | 可控性 | 当前有无约束 |
|---|---|---|
| `username` | 完全可控（1–64 字符，服务端 `casefold()`） | 无（未知用户名不再短路，**每次都触发一次 64 MiB 校验**） |
| `password` | 完全可控（1–256 字符） | 无 |
| 请求频率 / 并发度 | 完全可控 | **无任何限制** |
| `User-Agent` | 完全可控 | 仅在**登录成功**时写入 `user_session.user_agent[:300]`（失败不写） |
| 客户端 IP | 不可伪造（除非部署层配置错误） | 应用**完全不记录、不使用**（见 §5） |

### 1.5 未认证可写面（逐条确认）

| 端点 | 未认证可写？ | 证据 |
|---|---|---|
| `POST /api/auth/login` | **是** —— 审计写 1 行 + Argon2 资源 | 本次实测 |
| `POST /api/auth/logout` | **否** | Phase 2.4-b 改为匿名安全：**不带 cookie／token 不匹配时不写任何行**（实测：匿名 logout 前后 `history_event` 行数变化 = 0），只返回 200 与删除 Cookie |
| `GET /api/health`、SPA 兜底 | 否 | 只读 |
| 其余 40 条 API | 否 | 全部依赖 `CurrentUser`/`AdminUser`（Phase 2 审计已 AST 全量确认） |

⇒ **登录是唯一的未认证写入与资源消耗入口**，限流只需盯住这一个端点。

### 1.6 现状已具备的缓解（设计时不应重复造）

1. **等时失败语义**（Phase 2.4-a）：未知/错密码/未设密码/停用四种失败响应体完全一致（实测同批 `401`，耗时差 ≤2 ms）。
2. **失败审计**（Phase 2.4-b）：`login_failed` 事件已按"能解析到账号"归因 `user_id`，未知用户名只留空 payload 计数行 —— 这是限流之外**唯一的攻击可观测面**。
3. **部署形态**：`scripts/start-vocab.ps1:68` 为 `uvicorn app.main:app --host 127.0.0.1 --port 8000` —— **单 worker、仅回环地址**（本机不可从网络访问）；无 `--proxy-headers`。

## 2. 方案比较（A/B/C/D）

| 方案 | 优点 | 缺点 | 适用性 | 本项目匹配度 |
|---|---|---|---|---|
| **A. 按 IP** | ①天然覆盖"不存在用户名"的洪水（无需账号存在） ②与账号无关，无法被用来针对某个账号 ③实现简单（一个 key） | ①NAT/同网段共享出口会误伤好用户（家庭/办公/校园网都可能是同一 IP） ②**在反向代理后拿到的是代理 IP**（除非正确配置 `--proxy-headers` + `--forwarded-allow-ips`） ③IPv6 前缀轮换可绕过粗限流 ④本机部署（回环）下所有访问者同 IP → 一旦误配就是"自己封自己" | 公网部署的**执行维度** | ★★★★☆（作为执行维度） |
| **B. 按 username** | ①直接保护"某个账号被爆破" ②与来源无关，分布式攻击也有效 | ①**硬锁定 = 送给攻击者的 DoS**：任何人反复用错误密码打某账号就能把它锁住（对 2 用户系统是灾难） ②只能限制**已存在**账号；未知用户名的枚举洪水完全不受控 ③键是攻击者可控字符串 → 内存键空间需要额外约束（哈希+上限） | 只适合做**减速**，不适合做**封禁** | ★★★☆☆（仅减速维度） |
| **C. username + IP** | ①两个维度互补：IP 挡洪水、账号挡定向爆破 ②可按维度采取不同动作（IP 封、账号缓） ③单一维度被绕过时仍有另一层 | ①实现最复杂（两个计数器 + 两套参数） ②仍受 NAT 与代理 IP 影响（若用 IP 做执行维度） ③需要谨慎设计以免两个维度的响应差异泄露账号存在性 | 通用推荐 | ★★★★★（推荐） |
| **D. 全局限制** | ①实现最简 ②**唯一能直接给内存/CPU 设硬上限**的方案（并发闸门） ③不受 IP/NAT/代理影响 | ①**所有用户共享额度**：一个攻击者可以拖慢/阻断全部合法用户（DoS 同源风险） ②对 2 用户系统虽可接受，但公网部署下过于粗暴 | 适合做**兜底**（并发/总量闸门），不适合单独使用 | ★★★★☆（作为兜底） |

**结合本项目（Windows 本机应用、SQLite、单用户/小规模、uvicorn 单 worker、当前仅监听 127.0.0.1）：**

当前部署形态下**外部攻击者根本不可达**（回环绑定），因此本阶段的真实价值是：①为将来公网/局域网部署预置设计；②阻断"已能访问 Web 界面的人/被诱导的浏览器"造成的资源耗尽；③让"什么时候必须做限流"有明确触发条件。据此：

> **推荐：方案 C（IP 执行 + username 减速）+ 方案 D 的并发闸门作为唯一硬上限。**
> 分两步落地：**核心（必做）= 并发闸门 + 按 IP 失败计数**；**可选（第二步）= 按 username 的指数减速**。

## 3. 存储方案分析

| 方案 | 重启影响 | 数据增长 | 并发安全 | 实现复杂度 | 需要 schema？ |
|---|---|---|---|---|---|
| **1. 内存计数器**（推荐） | 计数清零。**可接受**：进程由操作员掌控，攻击者无法重启服务；重启本身即一次运维动作 | 零增长。需**显式上限**（如最多跟踪 10k 个键 + LRU 淘汰），否则攻击者可用海量不同 username 撑爆字典（每个键 ≈ 100 字节 → 10k ≈ 1 MB） | 需 `threading.Lock`：登录是同步端点，跑在 anyio 线程池（默认 40 线程）→ **存在真并发**，不可用裸 dict | 低（纯内存，无 IO） | **否** |
| **2. SQLite 新表** | 计数留存 | 每个计数 upsert 一行/一列 → 与审计表同量级增长，且需要一个清理机制 | SQLite 串行写，弱并发下可用（`busy_timeout=5000` 已设） | 高（迁移 + 清理 + 事务） | **是**（新表或新列 → 本阶段禁止） |
| **3. 复用 `history_event`** | 留存 | 已在增长（每次失败 129 字节），计数不额外写 | 只读计数，O(窗口内行数) 的 `COUNT`；`event_type`+`timestamp` 有索引 | 中（每次登录多一次查询；表无限增长 → 窗口查询越来越慢，需要保留期策略） | **否**（列已齐全） |

**方案 3 的能力边界（重要，实测/源码确认）：**

- ✅ 能做：**按已知账号**统计窗口内失败数（`login_failed` 行带 `user_id`）。
- ❌ 不能做：按 IP 统计 —— **schema 中根本没有任何 IP 列**（全仓库 grep `remote_addr|client_host|client_ip|ip_address|x_forwarded|forwarded_for` = 0 命中；`user_session` 只有 `user_agent`）。
- ❌ 不能做：按"提交的用户名"统计未知账号尝试 —— Phase 2.4-b **刻意不把攻击者可控字符串落库**（未知用户名行的 payload 为空）。这是隐私设计，不应为限流而推翻。

⇒ **结论：`history_event` 用于取证与事后回溯，不作为限流判定来源；限流用内存计数器（零 schema）。**

## 4. 推荐设计

### 4.1 分层结构（执行顺序即防护顺序）

```
POST /api/auth/login
  1) 并发闸门（全局，硬上限）      → 饱和即拒（不做哈希）
  2) IP 维度失败计数（滚动窗口）    → 超阈值即拒（429 + Retry-After）
  3) username 维度减速（可选）      → 先 sleep 再哈希（不拒）
  4) 既有流程（M1 统一语义 + M2 等时校验 + L4 审计）—— 完全不改
  5) 成功后：清零该 username 计数；IP 计数按权重衰减（不要求清零）
```

- **顺序理由**：闸门与 IP 判定都在 Argon2 之前 → 被拦下的请求 CPU/内存成本 ≈ 0；减速在哈希之前 → 直接削减攻击者吞吐。
- **不改动既有第 4 步**：Phase 2.4-a/2.4-b 的等时性与统一语义必须原样保留（否则会重新引入 M1/M2）。

### 4.2 各维度职责

| 维度 | 键 | 动作 | 为什么这样分工 |
|---|---|---|---|
| 并发闸门 | 全局 | 非阻塞获取信号量，失败即 **429/503** | **唯一能给内存设硬上限的机制**。必须**非阻塞**：阻塞式获取会把"CPU 耗尽"变成"线程池耗尽"（同样是 DoS） |
| IP | `request.client.host` | 窗口内失败数超阈值 → **429 + Retry-After** | 执行维度：不受账号是否存在影响，能挡住不存在用户名的洪水 |
| username | `sha256(casefold(username))[:16]` | 连续失败 → **递进延迟**（不封禁） | 只做减速：**硬封禁会被用来锁死真实账号**（方案 B 的致命缺点）。键用哈希：内存中不留攻击者明文 |
| 账号（可选，事后） | `history_event.user_id` | 只读统计/告警 | 取证，不参与判定（见 §3） |

### 4.3 参数建议（起始值，需按真实流量校准，非代码定论）

| 参数 | 建议起始值 | 理由 |
|---|---|---|
| 并发闸门上限 | **8** 次同时在跑的校验 | 8 × 64 MiB ≈ **512 MiB** 上限（实测 12 并发已达 +769 MiB）；把 anyio 的 40 线程上限与实际内存解耦 |
| IP 失败窗口 | **5 分钟** | 足够长以形成约束，足够短以免长期误伤 |
| IP 失败阈值 | **10 次 / 5 分钟** → 429，`Retry-After: 300` | 2 用户规模下正常人手误不会到 10 次/5 分钟；NAT 共享出口也不会被一次误伤封死 |
| IP 次生阈值 | **30 次 / 15 分钟** → 429，`Retry-After: 900` | 对持续爆破给出更长冷却 |
| username 减速 | 连续失败 **5** 次起：+250 ms，逐次翻倍，**上限 4 s**；成功即清零 | 上限 4 s 让攻击者吞吐降到 ~1/50，同时合法用户仍可完成登录（"忘记密码"场景不会被锁死） |
| 计数键上限 | **10,000** 键，LRU 淘汰 | 内存上界 ≈ 1 MB；防止海量不同 username 撑爆字典 |
| 是否计入成功 | **不计入失败预算**；正确密码永远放行（除非撞上并发闸门） | 避免"攻击者用错误密码把合法用户挡在门外"（这正是方案 B 硬锁定的问题） |
| 恢复方式 | **自动**：窗口滑动过期 / 成功清零 | 不引入任何"解锁"API 或运维介入（也就不需要持久化锁定状态） |

### 4.4 响应语义与不泄露约束

1. 失败仍返回既有的 `401 {"detail": "用户名或密码错误"}` —— **不变**。
2. 被限流返回 `429` + `Retry-After`；**两个维度使用同一文案**，不区分"因 IP"还是"因账号"。
3. **关键约束**：429 的触发条件必须只依赖"提交的用户名 + IP"，**不得依赖账号是否存在**。测试必须验证：对存在与不存在的用户名，在同等失败次数下得到**完全相同**的 429（否则限流本身会成为新的账号枚举旁路，等于把 M1/M2 的修复推翻）。
4. `Cache-Control: no-store` 已由 Phase 2.4-a 覆盖 `/api/auth/*`（含 429）—— 沿用，无需额外处理。

### 4.5 实现落点（若后续实施）

| 层 | 文件 | 内容 |
|---|---|---|
| 限流器 | **新增** `backend/app/services/limiter.py` | 纯内存、线程安全（`threading.Lock`）、有键上限与 LRU 淘汰、可注入时钟（便于测试窗口过期）、零 DB 访问 |
| 配置 | `backend/app/config.py` | 按既有 `VOCAB_*` property 风格新增（如 `VOCAB_LOGIN_MAX_CONCURRENT`、`VOCAB_LOGIN_IP_FAILURES`、`VOCAB_LOGIN_IP_WINDOW_SECONDS`、`VOCAB_LOGIN_USERNAME_DELAY_AFTER` …），全部有安全默认值 |
| 接线 | `backend/app/api/auth.py::login` | 在 `find_user_by_username` **之前**插入第 1–3 层；第 4 层原样不动 |
| 依赖 | 无新增第三方包 | 只用标准库（`threading`、`time.monotonic`、`hashlib`） |
| 测试 | **新增** `backend/tests/test_login_limiter.py` | 见 §4.6 |
| 部署 | `scripts/start-vocab.ps1` | 若将来置于反向代理后，需加 `--proxy-headers --forwarded-allow-ips <代理地址>`；**否则 `request.client.host` 只会是代理 IP，IP 维度会误伤全部用户** |

### 4.6 实施后的验收测试清单（本阶段不写）

1. 并发闸门：N+1 个并发登录时，超出的请求**立即**返回 429/503，且**不执行** Argon2（可用 spy 断言校验未被调用）。
2. IP 阈值：第 11 次失败在 5 分钟窗口内 → 429；窗口过期（注入时钟）后恢复 401。
3. username 减速：第 5 次起出现延迟，延迟上限 4 s；成功后计数清零。
4. **不泄露账号存在性**：存在/不存在的用户名在同等尝试次数下得到完全相同的 429 与相同文案。
5. **不写入数据库**：限流路径对 `history_event`/`user_session` 零写入（断言行数不变）。
6. **不误伤**：正确密码在未被限流时永远 200；被限流期间返回 429 而非 401（避免"密码错了"的误导）。
7. **内存有界**：灌入 50,000 个不同用户名后，跟踪键数不超过上限（直接断言内部计数）。
8. 线程安全：多线程并发打同一 key，最终计数正确（无丢失更新）。
9. 隔离：全部用例使用 pytest 临时库，`tools/prove_test_isolation.py` 必须仍显示 `data/` 零变化。

## 5. 是否需要数据库 schema

**不需要。** 推荐设计（内存计数 + 并发闸门）**不新增任何字段、不新增表、不创建 migration**。

只有在下列**明确不被推荐/本阶段不实现**的方向上才需要 schema：

| 若是这种设计 | 需要的 schema | 为什么本阶段不做 |
|---|---|---|
| DB 持久化的 **IP 限流** | 新表（`login_attempt`）或 `history_event` 新增 IP 列 | ①需要 migration（本阶段禁止）②**存储客户端 IP 属于个人数据**，与项目"Source / Learning / History 三者分离且最小化"的原则冲突；当前全库无任何 IP 列是**有意的现状**，不应为限流顺手引入 |
| 持久化的**账号锁定** | `user.locked_until` 等列 | ①需要 migration ②硬锁定会把限流变成针对合法账号的 DoS（见 §2 方案 B） |
| 跨 worker 共享计数 | 共享存储（DB/Redis） | 当前为**单 worker**（`start-vocab.ps1:68` 未传 `--workers`）；引入共享存储属过度设计 |

**触发条件（若出现，需要重新评估并可能引入 schema）**：部署改为 `--workers > 1`、置于负载均衡之后、或对外公开且出现真实滥用。

## 6. 实施建议

**建议顺序（每步独立可回滚，均不涉及 schema）：**

| 步 | 内容 | 价值 | 成本 |
|---|---|---|---|
| **1（必做）** | **并发闸门**（非阻塞信号量，上限 8） | 唯一能给内存/CPU 设硬上限；挡住"并发哈希"这一最有效的放大手法 | 极低（约 20 行 + 配置项 + 测试） |
| **2（必做）** | **按 IP 的失败计数**（内存 + LRU，429 + `Retry-After`） | 挡住单源洪水，且不依赖账号是否存在 | 低（约 60 行 + 测试） |
| **3（可选）** | **按 username 的指数减速**（不封禁） | 显著降低定向爆破吞吐，且不会锁死账号 | 低—中（需谨慎处理键哈希、上限与成功清零） |
| **4（可选，独立议题）** | `history_event` 的**保留期/清理策略** | 应对 129 字节/次的无界增长（当前 `append_only` 无清理） | 中（需产品决策：保留多久、删哪些类型） |
| **5（部署前置）** | 反向代理场景下的 `--proxy-headers` / `--forwarded-allow-ips` 与文档 | 否则 IP 维度在代理后失效或误伤全体用户 | 低，但**必须与公网部署同批完成** |

**优先级理由**：Phase 2.4-a 之后，每次未认证尝试的成本从"近零"升到"64 MiB + 一核 70 ms"，收益最高、最便宜的护栏就是"限制同时在跑的校验数"；IP 失败计数是第二层；username 减速属于体验与定向爆破之间的权衡，可后置。

**建议同时明确"不做"的清单**（避免范围蔓延）：验证码、账号锁定、密码策略调整、session 变更、权限模型变更、跨 worker 共享计数、IP 落库。

**风险与注意事项（实施时）**：

1. **限流本身不能成为新的枚举旁路**（§4.4 第 3 条）—— 这是本次设计最容易被做错的地方，必须有专门测试。
2. **不能误伤 NAT/代理后的合法用户**：阈值需按部署形态校准；家庭/办公共享出口下建议仅减速不封禁（把 IP 维度阈值调高、把 username 维度当作主要减速手段）。
3. **阻塞式信号量是反模式**（会把 CPU DoS 变成线程耗尽 DoS）—— 必须非阻塞。
4. **内存字典必须有界**，否则"防滥用"变成新的内存放大入口。
5. **同步端点的真实并发**来自 anyio 线程池（默认 40），因此计数器必须加锁；不要假设请求是串行的。
6. **不要在限流路径写库**（否则给攻击者增加了一条未认证写入路径）。
7. 计数器重启清零是**已知取舍**：单 worker + 操作员掌控进程的前提下可接受；多 worker 部署时该取舍失效（见 §5 触发条件）。
