# 2026-09-24 OCR 模型缓存事故报告

## 摘要

在将本地应用更新到 GitHub `main` 分支版本后，单词书导入页面的 OCR 无法启动。PaddleOCR 报错：识别模型 `PP-OCRv6_medium_rec` 缺少 `inference.yml`。词库数据库、上传图片和本机配置均未丢失或改写。

这是一次本地更新流程中的模型缓存不完整事故，不是对上游版本缺陷的归因。

## 影响

- 影响范围：本机的“单词导入 → 开始 OCR 识别”功能。
- 用户影响：导入的四张图片保留在队列中，但在模型恢复前无法执行 OCR。
- 未受影响：`data/vocab.db`、已上传图片、用户设置和词库内容。

## 时间线

1. 下载 GitHub `main` 分支并替换应用程序文件。
2. 保留本机 `data/` 目录时，OCR 识别模型缓存中留下了一个存在但不完整的 `PP-OCRv6_medium_rec` 目录。
3. PaddleX 将该目录判定为已缓存模型，并在读取缺失的 `inference.yml` 时失败。
4. 停止本地服务，删除不完整的识别模型缓存。
5. 重新下载模型五个文件，确认 `inference.yml`、`inference.json` 和参数文件齐全。
6. 重新初始化 PaddleOCR；引擎成功创建，并对一张已保存图片完成识别（85 行文本）。
7. 重启服务并通过 `/api/health` 健康检查。

## 根因

PaddleX 以“模型目录是否存在”作为缓存命中条件，未在初始化前验证模型关键文件是否完整。更新期间，旧缓存中的识别模型目录无法完整复制，留下空目录；这使运行时既不重新下载，也无法读取模型配置。

## 处置与验证

- 删除的仅是可重新获取的、不完整 OCR 模型缓存；未删除学习数据。
- PaddleOCR 重新下载并缓存了完整的 `PP-OCRv6_medium_rec` 模型。
- PaddleOCR 引擎初始化成功；实际图片识别返回 85 行文本。
- 本地服务重启后健康检查返回 HTTP 200：`{"status":"ok","app":"拾词"}`。

## 预防措施

1. 更新时将 OCR 模型缓存视为可再生资产：复制后应验证关键模型文件，或直接让 PaddleOCR 重新下载。
2. 在 OCR 初始化前检查每个已有模型目录是否**可用**——不只是「关键文件存在」：`inference.yml`、`inference.json` 必须仍能解析为完整文档，参数文件必须存在且不小于模型应有的量级；不完整时删除该目录并重新下载。**2026-09-25 修订**：最初的实现只判断「文件存在且字节数非零」，因此**非零但被截断**的配置或参数文件仍会被当成完整缓存；现已改为解析与量级校验。
3. 清理必须只在能证明「该目录确属 PaddleX 模型缓存、且当前没有别的进程在读或写它」时才执行：目录名须在 PaddleX 官方模型清单内、内容须确为模型文件、不能是符号链接或目录联接、在写宽限窗口内被修改过就跳过、并且要先拿到 PaddleX 自己的跨进程下载锁；删除时先原子改名再删除改名后的路径，正在使用的缓存不会被抽走。范围限定在 `official_models/` 内部，同级 `locks/`、`temp/`、`func_ret/` 不参与。**2026-09-25 修订**：最初的实现会删除 `official_models/` 下任何「看起来不完整」的目录，既可能误删无关目录，也可能删掉另一个进程正在下载的目录。**同日再次修订**：官方模型清单**读不到时不得退回按名字形状猜测**——PaddleX 未安装、清单导入失败或清单为空，都必须跳过清理并记录原因。两种错误的代价不对称：少清理一次只是多一次可人工处理的 OCR 启动失败，删错目录则真的丢数据。
4. 更新流程继续先停止服务、保留数据库与上传图片、完成迁移后再启动，避免在活跃写入时替换文件。
5. 模型缓存修复的验证必须使用隔离临时目录：`backend/tests/test_ocr_model_cache_repair.py` 全部在 `tmp_path` 下构造缓存树，覆盖完整缓存、空目录、截断文件、无关目录、同级缓存目录、链接、最近写入与被下载锁占用的并发情形；**不得对真实模型缓存或生产库运行清理**。
